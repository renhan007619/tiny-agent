## 三、正文骨架

### 第 1 节 · 一个请求到底由哪些部分组成（建立分段意识）

**要点**：多数人只知道 `messages`，实际上一次 Anthropic 请求有四处在花同一个窗口。

```
请求 = tools（工具说明书） + system（指令+记忆） + messages（历史+本轮） + maxTokens（输出预留）
         ↑ 每轮都发          ↑ 每轮都可能变      ↑ 每轮只增不减        ↑ 有硬上界
```

**要传达的判断**：`API 校验的是 (总输入 + maxTokens) ≤ 窗口`——**总量约束意味着任何一段失控都会让整体失败**。

**可贴的素材**：预算公式

```
available = Window − MaxTokens×(MaxToolRounds+1) − SafetyMargin − ToolResultReserve×MaxToolRounds
```

**这个公式值得单独讲一句**：`输出预留 = max_tokens × (最大工具轮数 + 1)`，为什么是"轮数+1"——因为每次调模型都可能产出一份完整回复，工具循环最多 5 轮，加上最终回答就是 6 次。

### 第 2 节 · 第一版：滑动窗口（算法层）

**要点 1：量纲必须是 token，不是条数**

消息长短极不均（一次工具结果 stringify 后可能几百 token），条数窗口会被单条大消息撑爆。

**要点 2：估算口径用字节数/3，不引 tokenizer**

```go
func estimateTokens(m anthropic.MessageParam) int {
    data, _ := json.Marshal(m)
    return len(data)/3 + 1
}
```

理由讲清楚：中文 UTF-8 每字 3 字节 ≈ 1 token，英文会略高估；**高估无害、低估才危险**，预算本来就留了安全余量吸收误差。

**要点 3：裁剪单位是"整轮"，不是"单条"——这里引出 `blockType`**

这是全文技术含量最集中的一段，值得展开：

- Anthropic API 规定 `tool_result` 必须放在 `role: "user"` 的消息里
- 于是 `role == "user"` 同时覆盖两种语义相反的消息：**真提问**（轮起点）和 **工具回填**（上一轮的尾巴）
- 如果按"role 是 user 就切轮"，会把 `tool_use` 和配对的 `tool_result` 拆到窗口两侧 → `tool_use_id` 配对断裂 → API 400
- 所以必须看 content block 的 `type` 字段来区分：

```go
// blockType 取 content block 的 JSON type 字段（text / tool_use / tool_result）
// 用 JSON 探测而不是类型断言，避开 SDK 各 block 具体结构的差异
func blockType(b anthropic.ContentBlockParamUnion) string { ... }

func isNewUserTurn(m anthropic.MessageParam) bool {
    if m.Role != "user" { return false }
    for _, b := range m.Content {
        if blockType(b) == "tool_result" { return false }   // ← 轮边界的唯一判据
    }
    return true
}
```

**一句话总结这一节**：`blockType` 本身不裁剪任何东西，它是"哪里能下刀"的判据来源——**它是谓语，不是主语**。

**要点 4：两条底线**

- 整轮成对裁剪（防拆配对）
- 只剩最新一轮时"宁超不切半轮"（`first < len(starts)-1` 这个循环闸）

### 第 3 节 · 第一版的接入策略（架构层，本文最有价值的段落）

**要点：位置对，但预算放错了层——这是两个独立决策，很多人混成一个。**

| 决策 | 做法 | 判断 |
|---|---|---|
| 裁剪逻辑放哪层 | 调用方（main），`agent.go` 一行不改 | ✅ 对：`MinCore` 无状态、策略在外层 |
| 预算放哪层 | 也是调用方，一个文件级常量 | ❌ 错：调用方缺信息，只能拍 |

**接入细节值得讲的三点**：

1. **裁剪是"预处理"，不是请求的一部分**——`SendMessage` 签名一个字没改，裁剪结果走已有的 `history` 参数流进去。好处：核心循环零侵入、`TrimHistory` 保持纯函数可纯单测。
2. **时序是"准入式"**——在拿到用户输入之后、本轮输入进入历史之前裁剪，所以窗口里永远不含当前提问，天然不误伤。
3. **取值"宁低勿高"**——低估只丢旧消息、高估爆窗；报错即调参信号。

**代码（`de46e14` 全部改动只有 9 行）**：

```go
const historyBudgetTokens = 90000

text := scanner.Text()
history = TrimHistory(history, historyBudgetTokens)
```

**要引用的那段注释**（它自己写了假设，这是全文的伏笔）：

```go
// 工具结果+system+本轮输入≈3k，再留安全余量 → ~90000
// 若真实跑长对话报 context 超限，把此值调小一档即可。
```

### 第 4 节 · 转折：静态预算 → 运行期变量（文章的高潮）

**要点：失效链的精确机制**

设计文档里的公式，`system` 本来是**变量项**：

```
history 预算 = W − system − 本轮 user − maxTokens×(maxRounds+1) − 工具结果预留 − 安全余量
                 ↑ 变量
```

落盘时被"代入估计值 → 打八折 → 固化成常数"：

```
const historyBudgetTokens = 90000   // system 从"每轮算"退化成"假设它很小"
```

而 `system` 里装着什么？**运行期检索出来的记忆命中**——长度完全不可控。

```
TrimHistory 保证：messages ≤ 90000        ✓（它管的那段确实守住了）
没有谁保证：      90000 + system + tools + 本轮 + maxTokens ≤ 窗口
API 校验的：      总量                      ✗
```

**关键论断（值得加粗）**：

> **两个片段各自都没错，合起来可能错——而且不报错、不告警，只在 API 返回 400 时才暴露。**
> 静态预算和运行期变量对不上，是这个 bug 的本质。

**可以再补一刀**：这两段代码（`agent.go` 拼 system、`main.go` 裁 messages）在同一请求里各管一头、通过参数相连，但**在预算上互不知情**——`TrimHistory` 不知道 `systemExtra` 多长，`fullSystem` 拼接不看任何预算。

### 第 5 节 · 第二版：显式装配（解决方案）

**核心一句**：从"拍一个常数给 history"改成"**先付别人，history 吃剩下**"。风险从"可能爆"变成"守恒"。

**要点 1：四段统一记账，按优先级付钱**

```
tools / system(稳定)  固定先付，不可裁，超了只报警
system(记忆)          按上限控量（先丢整条，再截断第一条）
user(本轮)            必保
history               吃剩余 ← 动态算出来，不再是常数
```

**要点 2：记账顺序 ≠ 排列顺序（两条独立的轴，这是最容易被写错的地方）**

- **记账按优先级**：谁先吃预算、超了先砍谁
- **排列按稳定性**：稳定内容在前、每轮变化的记忆垫底

"重要"不等于"该放前面"——检索到的记忆每轮都变，再相关也只能垫底，因为缓存是 **tools → system → messages 的连续前缀匹配**，中间夹一块会变的，后面全灭。

**要点 3：可观测性——装配报告**

```
[context] 窗口 131072 = 输出预留 12288 + 可用 112128 | 实占 xxxx (yy%)
  tools            1234 / 1234
  system(稳定)       89 / 89
  system(记忆)      512 / 1024  ✂
  history          4200 / 98016
  user(本轮)         31 / 31
  ! history 从头部裁掉 4 条消息 -> messages 前缀变化，prompt cache 需重建
```

三类告警：固定段超预算 / history 前缀失效 / 工具循环撑爆。

**要点 4：这个方案的代价（要诚实写）**

- 抽象成本：为了可观测付出一个 `Budget` + `AssembleReport` + `AssembleContext`
- 裁剪仍是破坏性的（被裁的历史永久丢失）
- 工具循环的增长"只能预留不能预知"，只能每轮复核账本、超了告警不裁剪

### 第 6 节 · 沉淀：三条工程纪律（文章的"带走物"）

**纪律一：影响全局的数字，必须单一事实来源**

踩坑实录：`maxTokens` 曾有两处事实来源——`NewMinCore` 里写死 `2048`（真正发出去的）和装配器里的 `defaultMaxTokens = 2048`（算输出预留用的）。改一处漏一处 → 输出预留凭空少算 12k，而报错时根本想不到这里。

修法：`req.Budget.MaxTokens = int(m.maxTokens)`——以"真正发出去的值"为唯一来源。

同一个病在 `historyBudgetTokens = 90000` 上已经犯过一次。

**纪律二：静态预算管不住运行期变量**

判据很简单：**只要有一个"每轮变化且长度运行期才知道"的内容被拼进请求，静态常量预算就必然失效**。

**纪律三：优先级排序按"有损程度"，不按"好不好实现"**

| 类别 | 手段 | 信息损失 |
|---|---|---|
| 无损可逆 | 外置（写文件/DB，上下文只留引用）、隔离 | 零，随时读回 |
| 可控无损 | 选择/装配（检索、排序、预算分配） | 零，只是"没放进来" |
| 有损不可逆 | 压缩（摘要、丢弃） | 有损，丢了找不回 |

原则：**先做无损的，再做有损的；做有损的必须配评估**。

→ 直接结论：**摘要压缩不该是第一步，它排最后**。"上下文满了就摘要"是被高估的技术——因为好实现所以流行，不代表对。

---

### 第 7 节 · 结语与路线图

**收束**：三次重构的共性——每一次都不是因为"技术更先进"，而是因为上一版的核心假设被新情况打破了。

| 版本 | 核心假设 | 被什么打破 |
|---|---|---|
| 一 | 上下文只有一个来源 | 记忆模块接入 |
| 二 | 来源长度可预算 | 检索结果长度运行期才知道 |
| 三 | 裁剪的破坏性可以接受 | 需要"裁出窗口但没丢信息" |

**后续路线**（写文章时作为"未完待续"）：L0 超长工具结果截断 → 外置 + 按 ID 召回 → 指令分层 → 摘要压缩 + mini eval。

**结尾可留一句**：

> 上下文工程的门槛不在算法，在于**你能不能意识到自己写下的那个常数是一个假设**。
