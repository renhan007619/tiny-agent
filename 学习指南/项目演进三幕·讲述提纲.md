# tiny-agent 项目演进 · 三幕讲述提纲

> **用途**：面试讲项目、快速回忆脉络、判断"什么时候该做下一个重构"。
> **证据来源**：commit `de46e14`（滑动窗口落盘）、`4aa0678`→`1d7d828`（装配器落盘与接线）；设计文档 `ce093b2d`（滑动窗口设计）、`0df7fd07`（装配器提案·三缺陷）、`25a15d58`（装配器定稿）。
> **生成时间**：2026-09-16（基于当日读码与 git 核查）。

## 主线一句话

**上下文管理这件事，我用三次重构走完了"散落拼接 → 单点预算 → 显式装配"的演进；每一次升级都是被"新的上下文来源出现"逼出来的，而不是提前设计的。**

面试价值：这条线证明的不是"我会写滑动窗口算法"，而是**能识别架构在哪一刻失效、并按成本递增的顺序升级**。

## 第一幕 · 只有一个来源时：把裁剪当"预处理"

**时间**：2026-09-07 设计 → 09-09 落盘（commit `de46e14`）

### 当时的约束

- `history` 每轮只增不减，长对话必然把 token 顶到窗口上限 → API 400
- 上下文的来源**只有一个**：对话历史（`history`）
- 项目纪律：`MinCore` 无状态、不持有策略（长期记忆接入时已定：`history` 和 `memory.db` 都由调用方持有）

### 做的决策

| 决策 | 做法 | 依据 |
|---|---|---|
| 接入位置 | main 的 REPL 循环内，**`agent.go` 一行不改** | "策略在外层 REPL、MinCore 无状态纯净" |
| 预算形态 | 文件级常量 `const historyBudgetTokens = 90000` | 它是配置不是状态 |
| 预算来源 | 公式推导 113k × 0.8 ≈ 90000 | **宁低勿高**：低估只丢旧消息、高估爆窗 |
| 时序 | `text` 之后、`store.Search` 之前 | 准入式：裁剪先于本轮输入，永不误伤当前提问 |
| 传参方式 | 结果走**已有的 `history` 参数**，不加 budget 参数 | 让核心循环对"裁剪"零感知 |

核心代码（`de46e14` 全部改动只有 9 行）：

```go
const historyBudgetTokens = 90000

// REPL 循环内
text := scanner.Text()
history = TrimHistory(history, historyBudgetTokens)   // ← 先裁
systemExtra := ""
if hits, serr := store.Search(text, 3); serr == nil && len(hits) > 0 {
    systemExtra = "相关记忆: \n" + strings.Join(hits, "\n")
}
```

`SendMessage` 签名一个字没改（仍是 `userMessage, history, tools, maxRounds, systemExtra`）——裁剪结果通过已有的 `history` 参数流进去。

### 代价（当时已知并接受）

1. **预算只覆盖一段**：`TrimHistory` 只管 `messages`，看不到 tools / system / 本轮输入
2. **裁剪是破坏性的**：`history = res.History` 回写，被裁的轮次永久丢失（不落盘）
3. **常量是假设值**：注释自己写着"工具结果+system+本轮输入≈3k"，待实测校正

### 什么时候该升级（可判断的信号）

- ✅ **出现第二个上下文来源，且长度在运行期才知道** → 本幕的静态预算必然失效
- ✅ 需要回答"这一轮一共给模型看了什么、各占多少 token"而答不上来
- ❌ 不需要升级的情况：来源只有 history、且用户对话轮数有限

### 面试口径

> "滑动窗口刚落地时我只有一个上下文来源，所以选了成本最低的接法：当成调用方的一次预处理，核心循环零感知。好处是 `TrimHistory` 保持纯函数、可以纯单测（后来 18 个用例全绿）；代价是预算无法跨来源协调——这个代价我当时就知道，只是还没到需要付的时候。"

## 第二幕 · 来源变多后：预算失守，需要账本

**时间**：2026-09-10（文档 `0df7fd07` 诊断现状）

### 当时的约束

- 记忆模块已接入：`store.Search(text,3)` 结果拼成 `systemExtra`，注入 system
- 上下文来源变成**两个**：`history`（有预算）+ `systemExtra`（**无预算**）
- `systemExtra` 的长度**在运行期才知道**——取决于检索命中了几条、每条多长

### 诊断：三个缺陷（出处 `0df7fd07`）

| # | 缺陷 | 原文依据 |
|---|---|---|
| ① | **记忆注入没有预算**（评"接近 bug 级"） | `TrimHistory` 只裁 messages，**管不到 systemExtra**；"工具结果+system+本轮输入≈3k"的假设一破就没人拦 |
| ② | **system 段混入可变内容、破坏 prefix cache** | `fullSystem = systemPrompt + "\n\n" + systemExtra`，缓存是 tools→system→messages 连续前缀，system 一变后面全灭 |
| ③ | **任务状态缺失** | 工具循环内无 Goal/Steps/进度，长任务没有锚 |

⚠️ **注意区分**：三缺陷是"当时整个上下文管理现状"的诊断，是装配器的立项理由，**不是对第一幕接入方式的评价**。只有①与第一幕的接入策略直接因果相关（策略把预算限定在单段、把 system 折算成静态假设），②的根因在 `agent.go` 的拼接位置，③与之无关。

### 失效链（缺陷①的精确机制）

```
设计文档的公式：history 预算 = W − system − 本轮 user − maxTokens×(maxRounds+1) − 工具结果预留 − 安全余量
                                              ↑ system 是变量项
落盘时：        代入约数 → 打八折 → 固化成常数 90000
                                              ↑ system 退化成"假设它很小"

结果：TrimHistory 保证 messages ≤ 90000   ✓
      但没人保证 90000 + system + tools + 本轮 + maxTokens ≤ 窗口
      而 API 校验的恰恰是总量                     ✗
```

**两个片段各自都没错，合起来可能错**——而且不报错、不告警，只在 API 返回 400 时才暴露。

### 做的决策

不是"立刻改代码"，而是**先立项做账本**（`0df7fd07` 提案）：

- 承认"一个部门的预算表、四个部门在花钱"的类比
- 定技术优先级原则：**无损 > 可控 > 有损**（外置=无损、选择=可控无损、压缩=有损）
- 结论：摘要压缩**排最后**（它被高估了，因为好实现所以流行）

### 代价

- 多了一层抽象：`Budget` 结构体、`AssembleReport`、`AssembleContext`
- 调用方接口变化：`SendMessage` 从 5 个位置参数改成 `SendRequest` 结构体

### 什么时候该升级

- ✅ **有任何一个"每轮变化且长度不可控"的内容被拼进请求** ← 这是最硬的信号
- ✅ 调试时出现"明明没超却被拒"或"超了才发现"的困境
- ✅ 需要向别人解释"这一轮 prompt 里装了什么"却只能翻代码猜

### 面试口径

> "预算失守不是因为裁剪写错了，而是因为我把预算设计成了一个静态常量，而 system 那段的长度是运行期才知道的。**静态预算和运行期变量对不上，且不报错**——这是我要做账本的根本原因。"

## 第三幕 · 收敛：裁剪从"预处理"变成"装配的一个环节"

**时间**：2026-09-12 定稿（`25a15d58`）→ 09-14/15 落盘接线（`4aa0678` → `1d7d828`）

### 当时的约束

- 四段内容（tools / system / 记忆 / messages）共用一个窗口，必须统一记账
- 排列顺序与记账顺序是**两条独立的轴**，不能混
- 分包不能拆（`tool_use` / `tool_result` 靠 id 配对）
- 缓存前缀要求稳定内容在前

### 做的决策

| 决策 | 做法 |
|---|---|
| 预算下沉 | main 只给 `budget := DefaultBudget()`（策略参数），**派生值在装配器里算** |
| 记账顺序 | 按优先级：tools / system(稳定) 固定先付 → 记忆控量 → 本轮输入必保 → **history 吃剩余** |
| 排列顺序 | 按稳定性：稳定在前、每轮变化的记忆垫底 |
| 裁剪位置 | `TrimHistory` 移入 `AssembleContext` 内部，按 `histBudget` 调用 |
| 可观测 | `AssembleReport` + 三类告警，`TINY_AGENT_DEBUG_CONTEXT` 控制打印 |

关键转变：

```
第一幕：main 拍一个常数 → TrimHistory              （决策在缺信息的地方）
第三幕：main 给策略参数 → 装配器派生 histBudget → TrimHistory   （决策在信息齐的地方）
```

预算公式（最终版）：

```
available  = Window − MaxTokens×(MaxToolRounds+1) − SafetyMargin − ToolResultReserve×MaxToolRounds
             = 131072 − 12288 − 4096 − 2560 = 112128
msgBudget  = available − tools − system(稳定) − system(记忆)
histBudget = msgBudget − 本轮输入
```

### 代价

- `history = res.History` 的**破坏性语义**没变（裁剪仍不可逆），只是位置变了
- 工具循环里的 messages 增长"只能预留不能预知" → 每轮复核账本，超了只告警不裁剪
- 复杂度上升：为"可观测"付出的抽象成本，在小项目里是负债

### 什么时候该升级（下一幕的信号）

- ✅ 需要"裁出窗口但没丢信息" → 路线图③ 外置 + 按 ID 召回（挂点在 `history = res.History` 那一行）
- ✅ 工具结果单条就能撑爆预留 → 路线图② L0 免费清理（截断超长工具结果，`truncateByTokens` 已备好）
- ✅ 需要"知道压缩有没有丢关键信息" → mini eval 任务集（10-20 条 + 一键回归）

### 面试口径

> "装配器不是提前设计出来的，是被'第二个来源'逼出来的。它解决的核心只有一句：**从'拍一个常数给 history'改成'先付别人、history 吃剩下'**。风险从'可能爆'变成'守恒'。"

---

## 一句话收束（三幕的共性）

每一幕的升级都不是因为"技术更先进"，而是因为**上一幕的核心假设被新情况打破了**：

| 幕 | 核心假设 | 被什么打破 |
|---|---|---|
| 一 | 上下文只有一个来源 | 记忆模块接入（第二个来源） |
| 二 | 来源长度可预算 | 检索结果长度运行期才知道 |
| 三 | 裁剪可逆性可以牺牲 | 需要"裁出窗口但没丢信息"（外置+召回） |

**讲述时把"假设—打破"这一对讲清楚，比罗列技术名词有说服力得多。**
