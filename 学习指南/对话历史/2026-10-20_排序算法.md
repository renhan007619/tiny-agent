细节准确性检查：

快排：
- 平均 O(n log n)，最坏 O(n²)（每次 pivot 都是最值，如已排序数组取首/尾元素）
- 空间：递归栈 O(log n) 期望，最坏 O(n)
- 不稳定：举例 [2a, 2b, 1] partition 交换会打乱
- 三路划分解决大量重复元素（全相等数组退化为 O(n²) 用二路划分时，虽然有的实现二路也能处理，但经典 Lomuto 在全部相等时是 O(n²)）

Lomuto：以 a[hi] 为 pivot，i 指向小于区的下一个位置，j 遍历。缺点：交换次数多，全部相等时退化。

霍尔（Hoare）双指针：从两端向中间，交换逆序对。更快。

Go 代码：

```go
// Lomuto，以最右为 pivot
func partition(a []int, lo, hi int) int {
	p := a[hi]
	i := lo
	for j := lo; j < hi; j++ {
		if a[j] < p {
			a[i], a[j] = a[j], a[i]
			i++
		}
	}
	a[i], a[hi] = a[hi], a[i]
	return i
}
```

三路：

```go
// 荷兰国旗：lt 左边 < p，gt 右边 > p，[lt,gt] 等于 p
func quick3(a []int, lo, hi int) {
	if lo >= hi { return }
	p := a[lo]
	lt, gt, i := lo, hi, lo
	for i <= gt {
		switch {
		case a[i] < p:
			a[lt], a[i] = a[i], a[lt]; lt++; i++
		case a[i] > p:
			a[i], a[gt] = a[gt], a[i]; gt--   // i 不动
		default:
			i++
		}
	}
	quick3(a, lo, lt-1)
	quick3(a, gt+1, hi)
}
```
注意 pivot 选 a[lo]，lt 从 lo 开始，i 从 lo 开始，因为 a[lo]==p 会走 default i++。正确。

归并：

```go
func mergeSort(a []int) []int {
	if len(a) <= 1 { return a }
	mid := len(a) / 2
	l := mergeSort(a[:mid])
	r := mergeSort(a[mid:])
	return merge(l, r)
}
func merge(l, r []int) []int {
	out := make([]int, 0, len(l)+len(r))
	i, j := 0, 0
	for i < len(l) && j < len(r) {
		if l[i] <= r[j] {   // <= 保证稳定
			out = append(out, l[i]); i++
		} else {
			out = append(out, r[j]); j++
		}
	}
	out = append(out, l[i:]...)
	out = append(out, r[j:]...)
	return out
}
```

稳定性关键：`<=`。

逆序对：merge 时 `r[j] < l[i]` 时，逆序对增加 len(l)-i。

堆排：
- 建堆：从最后一个非叶节点 n/2-1 开始下沉，O(n)。证明：每个节点下沉代价 = 其高度，总和 Σ h*2^(log n - h) = O(n)。
- 排序：每次把堆顶和末尾交换，堆大小减一，下沉，O(n log n)
- 不稳定

TopK 用最小堆 O(n log k)。

建堆 O(n) 的直觉解释：大部分节点在底层，下沉代价低。

排序稳定性总表：
- 稳定：插入、冒泡、归并、计数、基数、桶
- 不稳定：快排、堆排、选择、希尔

Go 的 sort.Slice 不稳定（用的是 pdqsort），sort.SliceStable 稳定（用 symmerge/插入）。

Go 1.19+ sort.Slice 用 pdqsort（pattern-defeating quicksort）：结合插入排序（小数组 <12）、快排、堆排（递归过深时，防 O(n²)）、以及针对已排序/重复元素的优化。Go 1.21 slices.Sort 泛型版也是 pdqsort。

Java 的 Arrays.sort 对基本类型用双轴快排（DualPivotQuicksort，不稳定），对对象用 TimSort（稳定，归并+插入）。

introsort = 快排 + 堆排兜底 + 插入排序小数组，C++ std::sort。

##### 一、快排

**大白话**：随便挑一个数当基准，把所有比它小的数都赶到左边，比它大的数都赶到右边；这样基准就落在最终位置上了，然后对左右两段递归做同样的事。

核心动作只有一个：`partition`。它写不对，整个快排就会出错。

```go
// Lomuto 划分：以最右元素为 pivot
func partition(a []int, lo, hi int) int {
	pivot := a[hi]
	i := lo                      // i 是"小于区"的下一个空位
	for j := lo; j < hi; j++ {
		if a[j] < pivot {
			a[i], a[j] = a[j], a[i]
			i++
		}
	}
	a[i], a[hi] = a[hi], a[i]    // pivot 归位
	return i
}

func quickSort(a []int, lo, hi int) {
	if lo >= hi {
		return
	}
	p := partition(a, lo, hi)
	quickSort(a, lo, p-1)
	quickSort(a, p+1, hi)
}
```

**递归边界**：`lo >= hi`，不是 `lo == hi`。这里写漏了，就是栈溢出。

**复杂度（必须背下来）**

| 场景 | 时间 | 空间 |
|---|---|---|
| 平均 | O(n log n) | O(log n) 递归栈 |
| 最坏 | **O(n²)** | **O(n)** 递归栈 |

最坏情况发生在**每次划分都极不均衡**时，比如数组已经有序，而你取首元素或尾元素当 pivot，每次只切掉一个元素，递归 n 层。

**两个真实存在的问题，面试最爱问**

1. **有序数组退化** → 随机取 pivot，或三数取中。
2. **大量重复元素退化**（Lomuto 碰到全相等的数组会退化成 O(n²)）→ 三路划分：

```go
// 荷兰国旗：lt 左边 < pivot，gt 右边 > pivot，[lt, gt] 全是 == pivot
func quick3(a []int, lo, hi int) {
	if lo >= hi { return }
	p := a[lo]
	lt, gt, i := lo, hi, lo
	for i <= gt {
		switch {
		case a[i] < p:
			a[lt], a[i] = a[i], a[lt]; lt++; i++
		case a[i] > p:
			a[i], a[gt] = a[gt], a[i]; gt--   // 注意 i 不动，换过来的数还没检查
		default:
			i++
		}
	}
	quick3(a, lo, lt-1)
	quick3(a, gt+1, hi)
}
```
`case a[i] > p` 时 `i` 不动，这点最容易写错，因为换来的是未检查的元素。

**稳定性：不稳定。** 跨距离交换一定会打乱相同元素的相对次序。

##### 二、归并

**大白话**：把数组对半劈开，分别排好，再把两个有序段像洗牌一样合并起来。

```go
func mergeSort(a []int) []int {
	if len(a) <= 1 {
		return a
	}
	mid := len(a) / 2
	l := mergeSort(a[:mid])
	r := mergeSort(a[mid:])
	return merge(l, r)
}

func merge(l, r []int) []int {
	out := make([]int, 0, len(l)+len(r))
	i, j := 0, 0
	for i < len(l) && j < len(r) {
		if l[i] <= r[j] {      // 必须 <= ，写 < 就不稳定
			out = append(out, l[i]); i++
		} else {
			out = append(out, r[j]); j++
		}
	}
	out = append(out, l[i:]...)
	out = append(out, r[j:]...)
	return out
}
```

**稳定性的关键就在那一个 `<=`**：相等时优先拿左边，左边本来就在前面。改成 `<` 就变不稳定的了。这个细节面试官必问。

**复杂度**：时间恒为 **O(n log n)**（没有最坏情况，这是它比快排稳的地方），空间 **O(n)**，稳定。

**归并真正的价值在于它衍生出的题**，而不是“排序”本身：

- **求逆序对**：合并时若 `r[j] < l[i]`，说明 `l[i:]` 全部大于 `r[j]`，一次就能贡献 `len(l) - i` 个逆序对。
- **链表排序（LC148）**：链表用归并不需要额外数组，只要拆开、合并指针，空间 O(1)（递归栈 O(log n)）。
- **外部排序**：数据大到内存放不下时，分块排好后做多路归并；这是大数据场景下唯一可行的排序方式。

**常见追问：空间能压到 O(1) 吗？** 数组的原地归并算法存在，但实现复杂度高、实际运行还更慢，工程上不会使用。所以正确的回答是：**数组归并的 O(n) 空间是可以避免的，但不会这么做；链表归并天然可以做到 O(1)。**

##### 三、堆排（只需记住三件事）

1. **建堆 O(n)，不是 O(n log n)**。从最后一个非叶节点 `n/2-1` 往前逐个下沉。直觉：**绝大多数节点在底层，下沉高度接近 0**，代价求和收敛到 O(n)。严格推导是 Σ 高度×该层节点数。
2. **排序阶段 O(n log n)**：反复“堆顶（最大值）与末尾交换，堆大小减一，新堆顶下沉”。
3. **原地，但不稳定**。堆排唯一的优势在于最坏情况也是 O(n log n) 且不需要额外空间；在 C++ 的 introsort 里，它是快排递归过深时的应急方案。

面试更常见的不是手写堆排，而是：

- **TopK** → 维护大小为 k 的**小顶堆**，O(n log k)，比全排序更好
- **数据流中位数** → 大顶堆 + 小顶堆

##### 四、三个 O(n²) 排序算法的取舍（会说就行，写就没必要）

| 算法 | 什么时候它有用 |
|---|---|
| 插入排序 | 小数组最快、近乎有序时 O(n)。**所有现代库排序的最后一步都靠它扫尾**（快排切到 <12 个元素就改用插入） |
| 冒泡 | 只考一个点：优化成“一轮无交换就提前退出”，以及“记录最后一次交换位置以缩小边界” |
| 选择排序 | 交换次数最少（n-1 次），但**不稳定**（注意“交换把远处相等的元素甩到后面”这个反例） |

**稳定性速查（必背）**：稳定 = 插入、冒泡、归并、计数、基数、桶；不稳定 = 快排、堆排、选择、希尔。

```go
func sortArray(nums []int) []int {
	aux := make([]int, len(nums))
	var sort func(lo, hi int) // [lo, hi)
	sort = func(lo, hi int) {
```

用三路划分最稳，天然处理重复元素。但也可以用 Hoare 双指针 + 随机 pivot。我给三路划分版，因为它同时解决了 LC912 的重复元素问题。

```go
func sortArray(nums []int) []int {
	var quick func(lo, hi int)
	quick = func(lo, hi int) {
		if lo >= hi { return }
		// 随机 pivot
		r := lo + rand.Intn(hi-lo+1)
		nums[lo], nums[r] = nums[r], nums[lo]
		p := nums[lo]
		lt, gt, i := lo, hi, lo
		for i <= gt {
			switch {
			case nums[i] < p:
				nums[lt], nums[i] = nums[i], nums[lt]; lt++; i++
			case nums[i] > p:
				nums[i], nums[gt] = nums[gt], nums[i]; gt--
			default:
				i++
			}
		}
		quick(lo, lt-1)
		quick(gt+1, hi)
	}
	quick(0, len(nums)-1)
	return nums
}
```

需要 import "math/rand"。用 rand.Intn 在新版 Go 里（1.20+）全局 Seed 已随机化，OK。

检查三路划分：初始 [lo, hi]，p = nums[lo]，lt=lo, gt=hi, i=lo。
- i=lo 时 nums[i]==p 走 default，i++。所以 lt 停在 lo，[lo, lt) 空。
- 若 nums[i] < p，交换 nums[lt], nums[i]。因为 i >= lt 总是成立吗？初始 i=lt=lo。当 i 前进后 i > lt 可能。交换后 lt++，i++。维护了 [lo, lt) < p，[lt, i) == p。对。
- 若 nums[i] > p，交换 nums[i], nums[gt]，gt--，i 不动。维护 (gt, hi] > p。对。
- 循环结束 [lt, gt] == p。递归 [lo, lt-1] 和 [gt+1, hi]。对。

复杂度：平均 O(n log n)，最坏因随机化仍理论 O(n²) 但概率极低；全相等数组因三路划分直接 O(n)。空间 O(log n) 期望。

LC912 上的坑：如果不随机化（取 nums[lo]），LC 的测试数据里有序数组会退化 → TLE（快排最坏 O(n²)，n=5e4 时 2.5e9 次操作）。这个要强调。

另一个 Go 特有坑：递归深度最坏 n 层。Go 的 goroutine 栈初始 2KB 可增长到 1GB，5e4 层递归每层几百字节，完全没问题。C++ 会爆栈。这点是"了解即可"。

```go
func sortArray(nums []int) []int {

	var siftDown func(i, size int)
	siftDown = func(i, size int) {
		for {
			l, r, max := 2*i+1, 2*i+2, i

			if r < size && nums[r] > nums[max] { max = r }
			if max == i { return }
			nums[i], nums[max] = nums[max], nums[i]
			i = max
		}

	for i := n/2 - 1; i >= 0; i-- {
		siftDown(i, n)
	}
	// 排序 O(n log n)
	for size := n - 1; size > 0; size-- {
		nums[0], nums[size] = nums[size], nums[0]
		siftDown(0, size)
	}
	return nums
}
```

##### 版本二：三路快排（原地、常数小，但必须随机化）

```go
func sortArray(nums []int) []int {
	var quick func(lo, hi int)             // 闭区间 [lo, hi]
	quick = func(lo, hi int) {
		if lo >= hi {
			return
		}
		r := lo + rand.Intn(hi-lo+1)       // 随机 pivot，防有序数据退化
		nums[lo], nums[r] = nums[r], nums[lo]

		p := nums[lo]
		lt, gt, i := lo, hi, lo
		for i <= gt {
			switch {
			case nums[i] < p:
				nums[lt], nums[i] = nums[i], nums[lt]
				lt++; i++
			case nums[i] > p:
				nums[i], nums[gt] = nums[gt], nums[i]
				gt--                       // i 不动！换过来的是没检查的数
			default:
				i++
			}
		}
		quick(lo, lt-1)                    // [lt, gt] 全是 == p，已经归位
		quick(gt+1, hi)
	}
	quick(0, len(nums)-1)
	return nums
}
```
`import "math/rand"`

**复杂度**：平均 O(n log n)，空间 O(log n) 栈；最坏理论 O(n²) 但概率可忽略。全相等数组因为三路划分直接 O(n)。

**本题中的注意点（这题最能体现这些注意点）**

1. **不随机化就大概率 TLE**。LC912 的测试集里有大量近乎有序和全相等的用例，固定 `nums[lo]` 或 `nums[hi]` 当 pivot，Lomuto 划分会退化成 O(n²)。
2. `nums[i] > p` 时**不能执行 i++**。这是三路划分唯一的思维陷阱：从右边换过来的元素还没检查过。
3. Go 的递归深度最坏 n 层，但 goroutine 栈可动态增长到 GB 级，5×10⁴ 层完全没事；同样的代码放 C++ 会爆栈。这点面试如果被问“栈溢出怎么办”，Go 和 C++ 要分开答。

##### 版本三：堆排（空间最优，代价是常数大）

```go
func sortArray(nums []int) []int {
	n := len(nums)

	var siftDown func(i, size int)         // 迭代版，无递归栈
	siftDown = func(i, size int) {
		for {
			l, r, big := 2*i+1, 2*i+2, i
			if l < size && nums[l] > nums[big] { big = l }
			if r < size && nums[r] > nums[big] { big = r }
			if big == i {
				return
			}
			nums[i], nums[big] = nums[big], nums[i]
			i = big
		}
	}

	for i := n/2 - 1; i >= 0; i-- {        // 建堆 O(n)，从最后非叶节点往前
		siftDown(i, n)
	}
	for size := n - 1; size > 0; size-- {  // 排序 O(n log n)
		nums[0], nums[size] = nums[size], nums[0]
		siftDown(0, size)
	}
	return nums
}
```

**复杂度**：O(n log n) 恒定，**额外空间 O(1)**（三个版本里唯一的时间最坏情况和空间都最优的版本），不稳定。

**本题中的注意点**：建堆起点是 `n/2 - 1`，不是 `n - 1`，叶子节点天然是堆。排序循环里 `size` 从 `n-1` 递减到 1，注意下沉传入的边界是 `size` 而不是 `n`。

##### 未优化版 A：Lomuto 划分 + 端点做 pivot（教科书标准款）

```go
func sortArray(nums []int) []int {

	quick = func(lo, hi int) {
		if lo >= hi {
			return
		}

	}

func partition(a []int, lo, hi int) int {
	pivot := a[hi]      // 直接取最右元素，没有任何挑选
	i := lo
	for j := lo; j < hi; j++ {
		if a[j] < pivot {
			a[i], a[j] = a[j], a[i]
			i++
		}
	}
	a[i], a[hi] = a[hi], a[i]   // pivot 归位
	return i
}
```

这就是绝大多数人背的第一版快排：结构清楚、正确，在**随机数据**上跑得飞快，但在 LC912 上会直接 TLE。

###### 它在 LC912 上会以两种方式超时

**方式一：数组已经有序或接近有序**

`pivot = a[hi]` 恰好是当前区间最大值，partition 后 `p == hi`，左段长度为 `hi-lo`、右段为空——**每层只切掉一个元素**。递归深度达到 n，总比较次数为 `n(n-1)/2 ≈ 1.25×10⁹`（n = 5×10⁴）。这个数据量级下，Go 跑一遍要几秒钟，而 LC 的时限只有 1–2 秒，必然 TLE。

**方式二：数组里有大量重复元素（这比方式一更隐蔽）**

当所有元素都相等时，`a[j] < pivot` 永远为 false，`i` 一直不向前移动；循环结束后，代码把 `a[lo]` 和 `a[hi]` 互换，返回 `lo`——**左段为空、右段为 `[lo+1, hi]`，同样是每层只切掉一个元素**。

这里有一个关键点，很多人会想错：

> **只加随机化，解决不了重复元素导致的退化。**

因为随机选出来的 pivot 值还是同一个（所有值都相等），partition 的结果完全一样，仍然是 O(n²)。所以“随机化”和“三路划分”分别解决的是两个不同的问题，不能互相替代。

**这版有个极容易被写错的边界**：Hoare 的返回值 `j` **不是 pivot 的最终位置**，所以递归区间是 `[lo, j]` 和 `[j+1, hi]`——左段**包含** `j`，而不是 `[lo, j-1]`。如果按照 Lomuto 的习惯写成 `j-1`，就会漏掉元素，从而产生错误答案。这是 Hoare 版在面试中丢分的第一大原因。

###### 这里有一个反直觉的对比

| 输入 | Lomuto（A 版） | Hoare（B 版） |
|---|---|---|
| 随机数据 | O(n log n) | O(n log n)，比较次数更少 |
| 已排序 | **O(n²)** | **O(n²)**（pivot 是最小值，同样每层只切掉一个元素） |
| **全部相等** | **O(n²)** | **O(n log n)** ✅ |

Hoare 划分时，两个指针只有在“左边遇到 ≥ pivot、右边遇到 ≤ pivot”时才交换，所以**全相等数组会被均匀地从中间劈开**——这正是 Hoare 版的天然优势，也是它在不少教材里被使用时不用额外处理重复元素的原因。

核心：Hoare 划分（原始 quicksort 论文的方案）相对于 Lomuto 的优势：

1. **交换次数更少**：Lomuto 每遇到一个小于 pivot 的元素就交换一次，即使它已经在正确位置（自己和自己交换，或与已在正确位置交换）。Hoare 只有在两端各找到一个"错位"元素时才交换一次。具体量化：
   - Lomuto：小于 pivot 的元素个数为 k，则交换 k 次（可能更多，如果实现是 <= 则更多）。加上最后一次 pivot 归位。期望交换 n/2 次左右。

### 🤖 助手

##### 先纠正一个提问里的隐含前提

严格说，**Hoare 不是“优化版”，它是原始版**：Hoare 划分来自 1961 年他本人的 quicksort 论文；Lomuto 划分则是 1980 年代才出现的**教学简化版**，它用可读性换性能。

所以更准确的问法是：**Lomuto 相比 Hoare，牺牲了什么？** 下面按这个思路讲。

---

##### 一、核心差异：一对一安置 与 成对交换

看两段内层循环的对比：

```go
// Lomuto：单指针 j 单向扫，每找到一个小于 pivot 的元素，就挪到 i
for j := lo; j < hi; j++ {
	if a[j] < pivot {
		a[i], a[j] = a[j], a[i]   // 每次交换只安置 1 个元素
		i++
	}
}

// Hoare：两个指针向中间夹，两端各找到一个"错位"元素才交换
for i <= hi && a[i] < pivot { i++ }
for j >= lo+1 && a[j] > pivot { j-- }
if i >= j { break }
a[i], a[j] = a[j], a[i]           // 一次交换同时安置 2 个元素
```

**这就是关键**：Lomuto 每做一次交换，只把一个元素安置到正确的一侧；Hoare 每做一次交换，**同时把右边的小元素送到左边，把左边的大元素送到右边**，一次交换就能同时完成两个元素的位置调整。

在随机数据上，这个差别会让交换次数相差约 **3 倍**（经验值；Hoare 约 n/6 次，Lomuto 约 n/2 次）。Lomuto 还有额外浪费：当 `i == j` 时，它会对元素自己和自己做交换，纯粹是空操作。

**既然 Lomuto 那么差，为什么书上都先教它？** 因为它的不变式极好理解（`[lo, i)` 全小于 pivot、`[i, j)` 全大于等于 pivot），20 行就能讲清，面试写起来也不容易错。**它是为了教学而故意牺牲性能的版本。**

---

##### 二、更大的收益：重复元素（这是初学者常忽略的点）

上一轮已经算过：**Lomuto 在全等数组上是 O(n²)**。原因是 `a[j] < pivot` 恒为 false，`i` 一动不动，最后返回 `lo`，每层只切掉一个元素。

Hoare 为什么不会这样？**因为它把“等于 pivot”也视为错位。**

- `a[i] < pivot` 时停 → 停在第一个 **≥ pivot** 的元素上
- `a[j] > pivot` 时停 → 停在第一个 **≤ pivot** 的元素上

全等数组里，两个指针**一开始就同时停下**，直接交换、各走一步、再同时停下……于是指针从两端向中间同步移动，**区间被均匀从中间劈开**，递归深度是 log n，复杂度是 O(n log n)。

关键在于**停止条件用的是严格不等号**。这是 Lomuto 和 Hoare 设计哲学的分歧：
- Lomuto 把“等于”归到**一侧**（`<` 进左，`>=` 进右）→ 相等元素全堆一边 → 划分失衡
- Hoare 把“等于”当作**可以交换的对象** → 相等元素被均匀撒到两边 → 划分平衡

这一条在 LC912 这种“测试数据里塞了大量重复值”的题上，是**生与死的差别**。

---

##### 三、还有两个小差别（知道即可，别当主要论据）

| 维度 | Lomuto | Hoare |
|---|---|---|
| 比较次数 | 每次划分约 n 次 | 约 n 次，**差别很小** |
| pivot 位置自由度 | 必须在端点（要当哨兵） | 也可端点，但通常是先存值 |
| 是否需要“pivot 归位”那步 | 需要，`a[i], a[hi] = a[hi], a[i]` | 需要，但**返回值不是 pivot 位置** |
| 递归区间 | `[lo, p-1]`、`[p+1, hi]` | `[lo, j]`、`[j+1, hi]`（**左段含 j**） |

**比较次数没有本质优势**，这一点要敢于否定。很多人以为 Hoare“更快”是因为比较更少，其实不是，差异在**数据移动量**和**划分平衡度**。

另外承认一个 Hoare 的**真实缺点**：`[lo, j]` 左段包含 `j`，意味着 pivot 归位后**还会被当作普通元素再参与一次划分**，多一次无谓比较。同时，这个“返回值不是 pivot 位置”的语义也是 Hoare 版最难写对、最容易在面试里写错、递归边界也最容易出错的地方——**收益是性能，代价是容易写错**。

---

##### 四、客观结论：它的上限在哪

Hoare 在重复元素上是“**不会失控**”，但并非“**最优**”。

- **全等数组**：Hoare 是 O(n log n)，但它会做成千上万次**毫无意义的相等元素互换**（换个位置还是同一个值）。
- **三路划分**：全等数组是 **O(n)**，一次扫描结束，等于区直接跳过不递归。

所以性能排序是：**三路划分（重复多）＞ Hoare（重复多但不如三路）＞ Lomuto（重复多直接失控）**；随机数据上则是 **Hoare ≈ 三路 ＞ Lomuto**。

顺带说一句，现代高性能实现（pdqsort、C++ 的 `std::sort`）**既不用裸 Hoare，也不用 Lomuto**，用的是**分块划分（block partition）**——把 Hoare 的“两端夹”换成“攒一批再批量交换”，进一步减少分支和写操作。Hoare 划分的历史地位是“原始正确版本 + 划分思想的源头”，不是“终极答案”。

---

##### 五、面试怎么答这题（照这个说就够）

> Hoare 划分相对 Lomuto 有两个实质优势：一是**交换次数少**，它一次交换同时安置两端两个错位元素，Lomuto 一次只安置一个，随机数据下交换量大约差三倍；二是**对重复元素稳健**，因为它的停指针条件是严格不等号，等于 pivot 的元素会被均匀分到两侧，而 Lomuto 会把相等元素全归一侧，导致全等数组退化成 O(n²)。比较次数两者差不多，不是差异点。不过 Hoare 的递归区间是 `[lo, j]` 和 `[j+1, hi]`，左段包含 j，返回值不是 pivot 最终位置，这是它最容易写错的地方；而重复元素的最优解其实不是 Hoare，是三路划分。

这五句话里，**“一次交换安置两个”和“严格不等号导致均分”是【必记】**，其余【了解即可】。

##### 例 1：全等数组 `[7,7,7,7,7,7,7,7]`（8 个 7）

看**递归层数**，这是最能说明问题的地方：

**Lomuto**（pivot 取端点 7）
```
第一层 partition：没有任何元素 < 7，返回 lo
→ 左段空，右段只剩 7 个 7
第二层：同样，右段只剩 6 个
...
```
每层只切掉 **1 个元素**，共 **7 层**。每层扫一遍 O(n)，总时间 **O(n²)**。

**Hoare**（pivot = 7，两个指针一起走）
```
i 停在 1（7 不小于 7），j 停在 7（7 不大于 7）→ 交换，i=2, j=6
i 停 2，j 停 6 → 交换，i=3, j=5
i 停 3，j 停 5 → 交换，i=4, j=4 → 交叉，返回 j=4
```
一层就直接把 8 个元素切成 **[0,4] 和 [5,7]**，即 5 个和 3 个。再往下一层递归，**总共只有 3 层**。

| | 层数 | 总时间 |
|---|---|---|
| Lomuto | 7 层（≈ n） | O(n²) |
| Hoare | 3 层（≈ log₂n） | O(n log n) |

一句话：**Hoare 把“等于 pivot”当作应该交换的情况，所以相等元素被均匀掷到两边；Lomuto 把“等于”全推给一侧，于是每次只切掉一个元素。**

---

##### 例 2：`[5,9,1,8,2]`，两者都用 5 当 pivot

**Lomuto**（pivot 在左端，`j` 单向扫）

| 步骤 | 动作 |
|---|---|
| j=1, 值 9 | 9<5？否，跳过 |
| j=2, 值 1 | 是 → 和 i=1 的 9 交换 → `[5,1,9,8,2]` ① |
| j=3, 值 8 | 否，跳过 |
| j=4, 值 2 | 是 → 和 i=2 的 9 交换 → `[5,1,2,8,9]` ② |
| 结尾 | pivot 归位，`[2,1,5,8,9]` ③ |

**3 次交换**（2 次内层 + 1 次归位）

**Hoare**（两个指针向中间夹）

| 步骤 | 动作 |
|---|---|
| i 停在 1（值是 9 ≥ 5），j 停在 4（值是 2 ≤ 5） | 交换 → `[5,2,1,8,9]` ① |
| i 走到 3（8 ≥ 5），j 走到 2（1 ≤ 5） | 交叉，停 |
| 归位 | `[1,2,5,8,9]` ② |

**2 次交换**（1 次内层 + 1 次归位）

**差在哪，看这两步就懂**

Lomuto 为了把 1 和 2 送到左边，**分别搬了两次**（1 跨过 9、2 跨过 8），每次只送过去一个小元素。

Hoare **一次交换就把 9 和 2 对调**，两个元素同时完成安置。而 1 从头到尾根本没有被搬动，因为 `i` 指针经过它时只是继续往前走，并没有触发交换。

所以那句话是成立的：**Lomuto 的交换次数约等于“小于 pivot 的元素个数”，Hoare 的交换次数约等于“真正错位的对数”。** 随机数据下前者约 n/2，后者约 n/6。

先纠正一个方向性的问题：**经典约定是 Hoare 用 `lo`、Lomuto 用 `hi`**，《算法导论》两版都这么写。你说的正好反了。不过这不是“必须”，而是由“谁需要哨兵”决定的；下面说清楚。

---

##### 先通俗讲清前面的数字

前面说的交换次数和层数，说白了就是两句话：

- **Lomuto 是一个一个搬**：扫到一个比 pivot 小的元素，才把它移到左边，一次只处理一个元素。
- **Hoare 是一对一对换**：左边找出一个“本该在右边”的，右边找出一个“本该在左边”的，一次换一对。

所以 Lomuto 的交换次数约等于“比 pivot 小的元素个数”，Hoare 约等于“真正错位的对数”。

**全等数组**最能体现差别：Lomuto 只看“是不是严格小于 pivot”，判断结果永远为否，一个元素都搬不动，每层只切掉一个元素，于是变成一条链；Hoare 把“等于”也视为错位，两个指针一碰到相等元素就交换，于是区间被对半切开。

---

##### 为什么 Hoare 必须先动 j

**用一个比喻来理解**：pivot 放在 `lo`，相当于在**左边界派了一个守卫**。

`j` 从右往左走，任务是找出“小于或等于 pivot”的元素。它一路走一路看，万一左边全是大于 pivot 的元素怎么办？没关系，它走到 `lo` 时，`a[lo]` 就是 pivot 本身，而一个数不可能“大于自己”，所以**它必然在这里停下，永远走不出这个区间**。

`i` 从左往右走，左边没有守卫保护它。因此它需要一个“天花板”，也就是**`j` 已经停下的位置**。`i` 一旦走到 `j`，循环就结束，所以它也走不出去。

顺序因此是确定的：

> **先让 j 走**，它有守卫保护，绝对安全；**再让 i 走**，它靠 j 保护，同样安全。

反过来先动 `i`：第一轮 `i` 会停在 `lo`，因为 pivot 不小于 pivot；此时 `j` 还没动，两者一交换，**就把守卫换走了**，`lo` 上不再是 pivot。之后 `j` 继续往左扫，就没有东西能保证它停下。

【了解即可】严格说，在 CLRS 这种“i 从 lo-1、j 从 hi+1”的对称写法里，两种顺序往往能得到相同结果；但“先 j 后 i”是唯一在**各种变体写法下都不用补边界 if** 的顺序，所以成了标准。考试时按“先 j”记，不会出错。

---

##### 为什么 Hoare 用 lo、Lomuto 用 hi

一句话：**Hoare 需要哨兵，Lomuto 不需要。**

| | 扫描方式 | 是否依赖哨兵 | 结论 |
|---|---|---|---|
| Hoare | `i`、`j` 从两端向中间走 | **需要**，因为 `j` 向左扫必须保证不越界 | 哨兵只能来自 `lo` 位置上的 pivot，所以**必须用 lo** |
| Lomuto | 单个 `j` 单向从左扫到右 | **不需要**，右边界写死成 `hi` | 两端都行；教材选 `hi` 只是让 `i := lo-1`、`return i+1` 写起来对称 |

所以准确的结论是：

- Hoare 用 lo 是**强制**的：如果换成 hi，`j` 从 `hi` 出发，一开始就会停在自己身上，左边没有守卫，一路扫到 `lo` 以下就会越界。
- Lomuto 用 hi 是**习惯**：如果换成 lo 完全安全，只是索引要偏移一位。

【必记】Hoare→lo，Lomuto→hi；Hoare 换到 hi 需要补边界检查，Lomuto 换到 lo 不用担心。

---

##### 【必记】为什么这里 i 的循环必须写 `<=`，不能写 `<`

```go
for i < j && nums[i] <= pivotval {   // ⚠️ 这里是 <=
    i++
}
```

因为你的 `i` 起点是 `lo`，而 `nums[lo]` **就是 pivot 本身**。pivot 不大于等于自己，如果用 `<`：

- `i` 会卡在 `lo` 不动；
- 第一轮交换就变成 `nums[lo] ↔ nums[j]`，**pivot 被换走**，整个划分逻辑立即失效。

所以“闭区间 + i 从 lo 出发”这个组合，**天然要求 `<=` 和非严格比较**。而纯 Hoare 那种“i 从 lo-1、j 从 hi+1”的虚拟边界写法，用的是严格比较。这是两种写法最根本的分岔。

---

##### 真正的风险：全等数组还是 O(n²)

`nums[i] <= pivotval` 和 `nums[j] >= pivotval` 会让全等数组中的每个元素都“满足条件”，于是：

- `j` 从右一路扫到 `lo`；
- `i` 一步都不动；
- 一层只排除 `lo` 一个元素，递归 `n` 层，**O(n²)**。

随机化救不了这个，因为随机换来的 pivot 值还是同一个。LC912 的测试集里有大量重复数据，这是你这版的唯一隐患。

**解决办法**：把这个 `partition` 换成三路划分，`quick` 的骨架几乎不用改：

```go
// 返回左右两段递归的闭区间边界
func partition3(nums []int, lo, hi int) (int, int) {
	idx := lo + rand.Intn(hi-lo+1)
	nums[lo], nums[idx] = nums[idx], nums[lo]
	p := nums[lo]
	lt, gt, i := lo, hi, lo
	for i <= gt {
		switch {
		case nums[i] < p:
			nums[lt], nums[i] = nums[i], nums[lt]
			lt++
			i++
		case nums[i] > p:
			nums[i], nums[gt] = nums[gt], nums[i]
			gt--            // i 不动，换过来的是没检查过的
		default:
			i++
		}
	}
	return lt - 1, gt + 1
}
```

调用侧：

```go
l, r := partition3(nums, lo, hi)
quick(lo, l)
quick(r, hi)
```

`lt-1` 可能小于 `lo`，`gt+1` 可能大于 `hi`，这时候子区间只剩单个元素，或者 `lo >= hi`，上一层已经 return，因此它们自然被 `lo >= hi` 拦住，不用额外判断。全等数组会在一次扫描里被 `[lt, gt]` 整段吞掉，直接结束。

两个小建议，不影响正确性：

1. `pivot := lo + rand.Intn(...)` 里 `pivot` 先当下标、后面又有 `pivotval`，读起来容易绕，建议改成 `idx`。

先纠正一个说法：**“Hoare 选 hi 就错”这个说法不成立**。真正的问题是**只换了 pivot 的位置，没有配套更换指针移动的顺序**：如果 pivot 放在 hi，同时把移动顺序也镜像成“先动 i”，那这版实现完全正确。所以真正的规则是：

> **pivot 站在哪一端，就先让朝它走过去的那个指针出发。**

| pivot 位置 | 谁朝它走 | 谁必须先进 |
|---|---|---|
| `lo` | `j`（从右往左） | **先动 j** |
| `hi` | `i`（从左往右） | **先动 i** |

因为 pivot 可以看作一堵**墙**，而墙只能挡住一个方向。

---

##### 通俗理解：pivot 是墙，墙只能单面防护

**pivot 放在 lo** → 给左边界砌了一堵墙。`j` 从右往左走，走到墙前**必定停下**（墙上的值不大于它自己），所以 `j` 绝不会扫出界。

`i` 从左往右走，前面没墙，所以让它**后走**：等 `j` 站好位置，`i` 走到 `j` 就停下。

顺序反了会怎样？拿 `[1,2,3]` 试（pivot 取 lo=0 的 1）：

| | 先动 i（❌） | 先动 j（✅） |
|---|---|---|
| 第一步 | i 从 0 出发，`1 <= 1` 成立 → **跨过墙**到 1；`2 <= 1` 不成立，停 | j 从 2 出发：`3>=1`→1，`2>=1`→0，**撞墙停** |
| 第二步 | j 从 2 减到 1，撞上 i，停 | i 根本没机会出发 |
| 归位 | `swap(nums[1], nums[0])` → `[2,1,3]` | `swap(nums[0], nums[0])`，返回 0 |
| 结果 | **2 > 1 却跑到 pivot 左边，错** | 正确 |

关键就在第一步：**先动 `i` 时，`i` 会跨过位于 `lo` 的 pivot，把自己原本受 pivot 保护的位置让出来。** 最后归位那一下，就把大于 pivot 的值搬回了 `lo`——左段被这个大于 pivot 的值破坏。

---

##### 为什么“hi + 先 j”会错

把 pivot 挪到 `hi`，顺序却还是先动 `j`。这时 **`j` 的起点就是墙本身**，`nums[hi] >= pivotval` 恒成立，`j` 第一步就跨过了墙——**墙直接消失**。

而此时 `lo` 那一端并没有可用的保护值（`nums[lo]` 是任意值），`i` 也没有可依靠的边界。两个都没有保护的指针相遇后，最后的归位操作 `swap(nums[i], nums[hi])` 就把错误的值搬进了左段。

例子 `[3,1,2]`（pivot 取 hi=2 的 2）：

```
j 从 2 出发：nums[2]=2 >= 2 → j=1；nums[1]=1 >= 2 不成立，停 j=1
i 从 0：nums[0]=3 <= 2 不成立，停 i=0
i<j → 交换 nums[0]↔nums[1] → [1,3,2]
第二轮：j 从 1 减 → nums[1]=3>=2 → j=0，撞上 i，停
归位：swap nums[0]↔nums[2] → [2,3,1]，返回 0
```

返回 0 时，右段 `[3,1]` 里 1 比 2 小却留在右边——**这时划分已经错了**。递归下去最终得到 `[2,1,3]`，根本没排好。

【必记】pivot 位置和“谁先动”是**配套关系**：`lo` 配 j、`hi` 配 i。只改一个，就错。

因为 Lomuto 属于**另一套动作**：它靠单向扫描，并不让两端向中间对撞。

- 和 p 一样 → 直接放过，`i` 前进
- 比 p 大 → 和 `gt` 位置换一下，`gt` 后退

循环结束时 `i > gt`，`[lt, gt]` 这一段**全部等于 p**，所以它们**已经在最终位置上，不需要再递归**。返回 `lt-1` 和 `gt+1`，把这一段整个跳过。

---

##### 【必记】`nums[i] > p` 时 i 为什么不能前进

因为 `swap(nums[i], nums[gt])` 是**从右侧换过来一个尚未检查的元素**。`gt` 位置上的元素还没被 `i` 检查过。你这个时候如果 `i++`，就等于**跳过一个未检查的元素**，直接产生错误答案。

对比之前讨论的“先动 j”那套：这里是“换来的没看过，所以原地再看一眼”。这是荷兰国旗标志算法唯一的易错点。

##### 复杂度（n = 数组长度）

| 场景 | 时间 | 空间 |
|---|---|---|
| 平均 | O(n log n) | O(log n) 栈 |
| **全等数组** | **O(n)** | O(1) 栈 |

##### 根本原因：`gt` 位置本身还没有被检查过

三路划分的不变式是：

```
[lo, lt) 小于 p    [lt, i) 等于 p    [i, gt] 没看过    (gt, hi] 大于 p
```

注意，最右边是 `(gt, hi]`，而 **`gt` 本身属于“没看过”这一段的右端点**。

所以 `swap(nums[i], nums[gt])` 换过来的 `nums[gt]`，是一个还没被 `i` 检查过的元素。如果 `i++`，这个元素就再也没人检查它了；它可能比 `p` 小，却会被永远留在右边。

| i | 看到 | 动作 | 数组 | lt, gt |
|---|---|---|---|---|
| 0 | `2` = p | i++ | `[2,3,1]` | 0, 2 |
| 1 | `3` > p | 换 `i` 和 `gt`，gt-- | `[2,1,3]` | 0, 1 |
| 1 | `1` < p（**重新检查**） | 换 `lt` 和 `i`，lt++, i++ | `[1,2,3]` | 1, 2 |

|---|---|---|---|---|

**原理**：那么快排的原理，是用一个pivot标杆作为标准，用指针来遍历，实现凡是小于pivot的数，和一个慢指针i（从左边开始交换一次加1）交换。最终再把pivot（在lomuto版本中通常为最右边的hi）交换到i的位置。

***
**局限**：1.对于pivot的选择，如果每一次都选到最大或者最小数，那么递归栈的长度则最坏来到O(n),而每次递归又要遍历O(n),时间复杂度来到O(n^2)。

2.对于全部都是相等元素，比如{3,3,3,3,3}这样的例子普通快排也是会出现O(n^2)

***

**进阶快排**：最普通的快排，其实是lomuto版本（单路）。那么还有几种优化

①：双路，双向快排hoare。 左指针i，右指针j，在i指针找到大于pivot的数，j指针找到小于pivot的数时，再进行交换。由于每次交换都将小数往右移的同时大数往左移，**相对单路减少了交换次数,大概是单路的次数1/3，但只是常数级别优化**

关键点：
1. 时间复杂度一样：都是每层 partition 扫 O(n)。
2. 嵌套 for 的写法，内层两个 for 合起来总共推进 i、j 不超过区间长度，所以总比较次数仍是 O(n)。不是 O(n²)。这是很多人的误区——看到嵌套就以为 O(n²)。
3. 三路的单层 for + switch，本质是把"推进哪个指针"写成三个分支。

区别（细节）：
- 两路嵌套 for：一旦内层遇到不满足条件的就停，交换后重新进入外层，两个内层 for 从当前位置继续。总步数 ≤ n。
- 三路 if/switch：每次循环迭代只推进一个指针（lt/eq/gt），总迭代 ≤ n。

真正的差异：
1. **可读性/安全性**：三路的单层循环，边界条件只在一处（`i <= gt`），不容易写错越界；两路的嵌套 for，每个内层都要写 `i < j` 保护，漏一个就越界。
2. **常数**：嵌套 for 的写法通常更快一点（同一轮交错推进，减少外层判断），但差异很小。
3. **计数**：三路每轮只处理一个元素；两路每轮可能处理两个（一交换就同时安置两个）。

用伪代码说明"两路嵌套也只是一遍扫描"：

```go
for i < j {
    for i < j && nums[j] >= p { j-- }   // j 只减不增
    for i < j && nums[i] <= p { i++ }   // i 只增不减
    swap
}
```
i 从 lo 单调增到最多 hi，j 从 hi 单调减到最少 lo，各自总共走 n 步，所以两个内层加起来 O(n)。**不是 n²。**

### 🤖 助手

**没有本质区别，两种写法每层都只扫一遍 O(n)。** 唯一要防范的误区是：看到嵌套 for 就以为会变成 O(n²)。

两路快排里的两个内层循环，`j` **只减不增**、`i` **只增不减**；外层循环反复进入内层时，它们从上次停下的位置继续走。因此两个内层合起来，`i` 最多走 n 步、`j` 最多走 n 步，**总计 O(n)**，不会重复扫描。

下面的对照表说明两者只是代码组织方式不同：

| | 两路（嵌套 for） | 三路（单层 for + 分支） |
|---|---|---|
| 每层扫描 | O(n) | O(n) |
| 指针数量 | 2 个（i, j） | 3 个（lt, eq, gt） |
| 每轮推进 | 可能一次推进两个指针 | 每次只推进一个指针 |
| 边界条件写在哪 | **每个内层循环都要写 `i < j`**，漏写一个就会越界 | **只写在一处**（`eq <= gt`） |
| 主要易错点 | 漏写边界保护 | `> p` 分支中 `i` 必须停住不动 |
| 适用场景 | 无大量重复元素 | 重复元素多 |

【必记】真正有价值的差别只有一条：**三路把全部边界判断集中到同一处，因此更难写错；两路的边界条件分散在几个内层循环里，容易漏。**

至于性能：两种写法常数差别很小，面试官不会考。而“三路比两路慢”这种说法也只是假象；三路只在全等数组上多做几十次无意义交换，但换来整个等于区不再递归，实际更快。

一句话总结：**两种写法是同一个算法的不同写法，区别只在于你要维护 2 个区还是 3 个区。**
