##### 改动 3 · REPL 循环内包住 `SendMessage` 【逐行理解】

**改前**（151-163，现状）：

```go
		askCtx, cancel := context.WithTimeout(ctx, 60*time.Second)
		res, err := llm.SendMessage(askCtx, SendRequest{
			UserMessage: text,
			...
		})

```

**改后**：`askCtx` 创建之后插 `tracer().Start`，`cancel()` 之后插 `recordErr` + `turnSpan.End()`。

四个坑，逐个说清：

**① `askCtx, turnSpan := ...` 是重新赋值 `askCtx`，不是新建变量。**
`Start` 的返回值 ctx 里塞了 span 指针，**必须赋回 `askCtx`** 再传给 `SendMessage`。写成 `_, turnSpan := ...` 就断链了——`SendMessage` 收到的 ctx 不带 span，`agent.go` 里所有 `tracer().Start(ctx, ...)` 都会各自成为**新的 root**，一次用户输入散成 N 条互不相干的 trace。这是 OTel **最高频的坑**，没有之一。

**同一作用域内 `:=` 只要有新变量就合法**（`turnSpan` 是新的），旧的 `askCtx` 是被**赋值**而非 shadow——所以能编译，也不会有"两个 askCtx"的语义错误。

**② 每轮一个 root span，而不是整个会话一条 trace。**
会话可能几十分钟、几十轮，一条 trace 长达几十个 span 铺在同一时间轴上，**读不了**。会话级关联走 `session.id` 属性——后端按属性过滤就能把 30 条 turn trace 拉成一条时间线。**trace 负责"一次任务"，属性负责"跨任务聚合"**，别让一个机制干两件事。

`attrHistoryMsgs` 记 `len(history)` 也值得点一句：这时 `history` 还是**本轮开始前**的长度（本轮 append 在 `SendMessage` 内部），所以这个数天然是"本轮输入的历史规模"，逐轮看它在涨 = 上下文在膨胀。这是后面解释"第 2 轮为什么比第 1 轮慢"的**解释变量**，不是装饰。

**③ `End` 必须在循环内，不能用 `defer`。**
`defer` 要等 `main` 返回才跑。写成 `defer turnSpan.End()` 有两个后果：

- 第 1 轮的 span 从 `Start` 一直活到进程退出，**耗时 = 你整个会话的时长**，全错；
- 循环 30 轮就攒 30 个未结束的 span 挂在内存里，导出时序也乱。

（span 的耗时是 `EndTime - StartTime` 的墙钟，跟 ctx 无关——**`cancel()` 不会替你 End span**，OTel span 不监听 `ctx.Done()`。忘了 End 就被静默丢弃，你在后端只会看到"这条 trace 少了中间一段"。）

**④ 先 `cancel()` 再 `recordErr` + `End()`，顺序有讲究。**

| 动作 | 作用域 |
|---|---|
| `cancel()` | 只影响**请求**（HTTP 客户端中断、计时器释放） |
| `span.End()` | 只影响**记录**（定格 EndTime、交给 exporter） |

先收计时器、再收 span，保证 span 的 EndTime **覆盖到请求真正返回之后**，不会被"我先 End 了再去 cancel"这种顺序切掉尾部。

还有一个设计优点值得你自己记：**这里的 `recordErr` + `End` 放在 `if err != nil` 之前，所以两条出口（继续往下 / `continue`）都已经收口了**。对比块 8 里 `chatSpan` 要 `return` 出去，没法用统一的"之后"，只能错误分支手动 `End` 再 `return`。两种写法内核是同一条纪律：**任何出口之前，span 必须 End**。

```go
	// 失败只降级、不阻断：agent 能不能跑比能不能观测重要。
	shutdown, terr := InitTelemetry(ctx)
	if terr != nil {
		fmt.Fprintln(os.Stderr, ">>> 可观测性初始化失败（本次运行无 trace）:", terr)
	} else {
		// 必须显式 Shutdown：Batch 默认 5s 落一次网，直接 return 会丢最后一批 span。
		defer func() {
			sctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
			defer cancel()
			if err := shutdown(sctx); err != nil {
				fmt.Fprintln(os.Stderr, ">>> 关闭 tracer 失败（最后一批 span 可能丢失）:", err)
			}
		}()
	}

	var history []anthropic.MessageParam
	scanner := bufio.NewScanner(os.Stdin)
```

**逐行**：
- `InitTelemetry(ctx)`：返回 `(Shutdown函数, error)`。注意它**不 panic、不退出**，把失败当普通返回值交出来。
- `if terr != nil` → 打一行 stderr。**没有 `os.Exit`**：没 trace 只是瞎，功能是完整的。
- `else` 才 `defer`：`shutdown` 在错误时是 `nil`，调 nil func 会 panic——所以必须在 else 分支里包。
- `sctx, cancel := context.WithTimeout(context.Background(), 5s)`：独立超时。`shutdown` 内部要发最后一个 HTTP batch，用无限期的 `ctx` 会让后端挂掉时**退出永远卡住**。
- `defer cancel()` + `if err := shutdown(sctx)`：显式报告关闭失败，而不是静默丢 span。

**为什么位置在这**：
1. 前面有 **3 处** `os.Exit(1)`（38 / 80 / 114 行）。`os.Exit` 绕过栈展开，**defer 不执行**。放前面 = 在最常见的失败路径（key 没配）上留下一个注册了全局 provider、永远不会 Shutdown 的进程。
2. 和 ResultStore 的“构造期失败要退出”（76-80 行）划清界线：

| | 磁盘布局错 | 没有 trace |
|---|---|---|
| 缺什么 | 功能不可用 | 功能完整，只是盲 |
| 处理 | `os.Exit(1)` | 打一行，继续 |

3. 必须有 `Shutdown`：`WithBatcher` 攒 5s/512 条才发。`main` 直接返回 = 内存里那批 span 一条发不出去，而丢的正是**用户最后一句话**那条 trace。

#### 改动 3 · REPL 循环内 root span

**改前**（151-163）
```go
		askCtx, cancel := context.WithTimeout(ctx, 60*time.Second)
		res, err := llm.SendMessage(askCtx, SendRequest{...})
		cancel()
		if err != nil { ... continue }
```

**改后**
```go
		askCtx, cancel := context.WithTimeout(ctx, 60*time.Second)

		// 每轮一个 root span：一次"任务"就是用户这一次输入。
		// 不按整会话切 trace——会话几十轮，trace 太长没法看；会话关联走 session.id。
		askCtx, turnSpan := tracer().Start(askCtx, spanTurn, trace.WithAttributes(
			attribute.String(attrSessionID, sessionID),
			attribute.Int(attrHistoryMsgs, len(history)),
		))

		res, err := llm.SendMessage(askCtx, SendRequest{ /* 内容不变 */ })

		cancel() // SendMessage 已返回，计时器立刻释放
		recordErr(turnSpan, err)
		turnSpan.End()

		if err != nil { ... continue }
```

**逐行**：
- `askCtx, turnSpan := ...`：**`askCtx` 是重新赋值，不是新变量**。`Start` 返回的 ctx 里塞了 span，必须赋回去再往下传。
- `spanTurn` / `attrSessionID` / `attrHistoryMsgs`：都在 telemetry.go 的常量表里（`spanTurn = "agent.turn"`），一处定义防止口径分裂。
- `len(history)`：此刻 history 还是**本轮开始前**的条数（append 在 SendMessage 内部）。逐轮看它涨，就是“上下文在膨胀”的证据。
- `recordErr(turnSpan, err)`：内部做两件事——`RecordError`（留详情）+ `SetStatus(Error)`（后端靠状态算错误率）。传 nil 会直接 return，所以不用先判空。
- `cancel()` 在 `End()` **之前**：cancel 只管请求，不管 span；先收计时器再收 span，保证 EndTime 覆盖到请求真正结束。
- `End()` 放在 `if err != nil` **之前**：这样成功/失败两条出口都已经收口了。

**三个必踩的坑**：
1. **ctx 不往下传 = 断链**。写成 `_, turnSpan := ...`，`SendMessage` 收不到 span，agent.go 里每个 `Start` 都变成新 root，一次输入散成 N 条无关 trace。
2. **不能 `defer turnSpan.End()`**。defer 等 `main` 返回，第 1 轮 span 会把后面所有轮次时间算进去（span 耗时 = EndTime−StartTime 的墙钟）。而且 `cancel()` **不会**替你 End——OTel span 不听 `ctx.Done()`，忘了 End 就被静默丢弃。
3. **每轮一个 root，不是整会话一条**。整会话一条 trace 几十个 span 铺在同一时间轴上，读不了。**trace 管“一次任务”，`session.id` 管“跨任务聚合”**。
