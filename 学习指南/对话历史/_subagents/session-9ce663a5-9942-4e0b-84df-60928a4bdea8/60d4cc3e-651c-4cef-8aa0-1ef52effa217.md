##### 一、把刚才那句补完：MULTI/EXEC 与 Lua

【理解】

- `MULTI ... EXEC`：命令先入队，`EXEC` 时一次性连续执行完，中间不插别的客户端命令。但它**不回滚**——第 2 条命令因类型错误失败，第 1 条已经生效了。所以它是「不被打断」，不是「要么全成功要么全失败」。
- `EVAL`（Lua 脚本）：脚本执行期间整个 Redis 不处理其他命令，脚本内多步逻辑整体原子。代价是脚本里写死循环，整个实例卡死（`lua-time-limit` 默认 5s 后其他客户端开始收 `BUSY`，但脚本本身不会自己停，只能 `SCRIPT KILL`）。

这两者的存在本身就是证据：**如果单线程天然让「多步操作」原子，就不需要 MULTI 和 Lua 了。**

---

##### 二、「Redis 单线程实现了原子性」这句话要校准三层

【必记】下面这个辨析比结论本身值钱，面试被追问时能立刻拉开层次。

**第一层：单线程保证的是「命令级不交错」，不是「业务级原子」。**

Redis 主线程的循环长得像这样（伪代码）：

```
while true:
    cmd = 从就绪的客户端里读一条命令
    execute(cmd)        ← 这一步从头跑到尾，中间不切走
```

所以一条命令一旦开始执行，就一定会跑完才轮到下一个客户端。这就是全部保证。

**第二层：`SET key v NX PX 1000` 之所以原子，根本原因是它「是一条命令」。**

`NX`、`PX` 不是三条命令，是 `SET` 这一条命令的**参数**。服务端在 `setGenericCommand()` 这**一次函数调用**里完成「检查 key 是否存在 → 不存在则写入 → 设置过期」，中间没有任何可以让别的命令插进来的点。单线程只是让「这一次函数调用不被打断」成立。

反过来验证：如果你自己拆成

```
EXISTS lock        → 0
SET lock val
PEXPIRE lock 1000
```

这三条**无论 Redis 多单线程都不原子**——三条命令之间完全可以插进别的客户端的命令，两个客户端能同时判断出 `EXISTS = 0`。这就是经典的 SETNX+EXPIRE 双命令写法出问题的根因，也是你博客「问题 2」那条 `SetNX(ctx, key, val, 0)` 之外的另一个坑：**即使你传了过期时间，只要你分两条命令发，就仍然不安全。**

**第三层：这里的「原子性」实际是隔离性，不含回滚语义。**

数据库 ACID 里的原子性 = 要么全做要么全不做。Redis 单命令的「原子」= **执行过程不可见、不可插入**，不存在「做到一半失败就撤销」。理解成「不可分割地执行」而不是「失败自动撤销」，后面学 MULTI 不回滚、Lua 报错不回滚时才不会拧巴。

> 顺便提一句：Redis 6.0 起网络读写是多线程（`io-threads`），但**命令执行仍然是单线程**。所以「单线程」这个词在 6.0 后严格说应该叫「命令执行单线程」。讲给面试官时用后者，会显得你读过版本变更。

---

##### 三、单线程为什么反而快（这是同一枚硬币的另一面）

【理解】别背「因为内存」，答到这三条才算到位：

1. **纯内存操作**，没有磁盘寻道/页缓存这层开销；
2. **无锁**——单线程串行，数据结构内部不需要加锁，省掉锁竞争和上下文切换；
3. **IO 多路复用**（epoll/kqueue），一个线程扛几万连接，不用一连接一线程。

代价同样来自同一个特性：**一条慢命令阻塞全体**。`KEYS *`、`FLUSHALL`、大 key 的 `DEL`、耗时长的 Lua，都会让所有人一起等。所以生产中禁用 `KEYS`、大 key 拆分、用 `SCAN` 代替——这些规范不是玄学，是单线程的直接推论。

---

##### 四、一句话类比收束

【理解】

Redis 像**只有一个柜员的银行窗口**：柜员一次只服务一个人，一个人办完才叫下一个。
`SET key v NX PX 1000` 是「填一张单子，把查重、开户、设有效期写在同一张单上」——柜员拿过这张单子会一口气办完，中间不会抬头接别人的单子。
而 `EXISTS` + `SET` + `PEXPIRE` 是「分三次来窗口」——三次之间，别人完全可能把同一个账户开走。

**原子性来自「一张单子」，不来自「一个柜员」。** 柜员只有一个，只是保证这张单子办的过程中不被打断；单子拆成三张，一个柜员也救不了你。

【高频·实现层追问】`SetNX` 在 go-redis 里为什么发的是 `SET ... NX` 而不是 `SETNX`？
→ `SETNX` 命令不能带过期时间，而 `SET` 自 Redis 2.6.12 起支持 `NX/XX/EX/PX/KEEPTTL`，一条命令搞定「判存+写+过期」。go-redis 统一走 `SET`。注意 `SETNX` 命令本身仍然存在，是客户端的选择变了。

【高频·实现层追问】`SetNX` 返回 `false` 时 `err` 是 nil 吗？
→ 是 nil。加锁失败是**正常业务结果**，不是错误。`cmd.Result()` 得到 `(false, nil)`。写代码时判 `ok, err := ...`，先看 `err` 再看 `ok`，别把「锁被别人占了」当异常抛。

【高频·概念辨析】单线程能不能保证「读-改-写」原子？
→ 不能，除非合并成一条命令、放进 Lua 或 `MULTI/EXEC`。这是上面第二层的直接应用。

【加分·拓展】为什么 `SET ... NX PX` 比 `SETNX + EXPIRE` 安全？
→ 后者不是原子组合，客户端在两条命令之间宕机/网络断开，会留下一个**没有 TTL 的永久锁**。这和你博客「问题 2」里 `expiration = 0` 的后果一模一样，只是成因不同：一个是参数传错，一个是分段发送。**两个坑都通向「永久死锁」这个终点。**

【了解即可】`usePrecise` 的内部实现是 `d < time.Second || d%time.Second != 0`——不是整秒就走 `PX`。你说的「锁场景基本都走 PX」是对的。`formatMs` 做整数截断，所以亚毫秒的时长会被抹成 1ms 级别，这也是为什么锁的过期时间别给太小的值。

##### 块 0：方法签名

```go
func (c cmdable) SetNX(ctx context.Context, key string, value interface{}, expiration time.Duration) *BoolCmd {
```

【逐行理解】

- `c cmdable`：`cmdable` 不是接口，是**函数类型** `type cmdable func(ctx context.Context, cmd Cmder) error`。它代表「一个能执行命令的东西」，`Client`、`Pipeline`、`Tx` 都实现了它。这就是为什么 `SetNX` 既能直接在 `client` 上调用，也能在 `pipeline` / `tx` 里调用，**同一份代码**。这是 go-redis 的设计精髓：命令方法只负责「拼命令」，不负责「怎么发」。

- `ctx context.Context`：不是摆设。它一路传到 `c(ctx, cmd)`，控制的是**这次网络调用**的超时/取消。传 `context.WithTimeout(ctx, 100ms)` 时，超时的是「发命令+等回复」这个动作，不是锁本身的 TTL。

- `key string, value interface{}`：`value` 是 `interface{}` 而不是 `string`，因为要兼容 `string`、`[]byte`、`int`、`bool`、`time.Time`、`float64` 等。go-redis 在编码时按类型分流，其它类型走 `fmt.Sprint`。顺便说一句：**传一个 struct 进来不会报错，会变成 `{12 34}` 这种字符串写进 Redis**，锁场景千万别这么传。

- `expiration time.Duration`：用 `time.Duration` 而不是 `int` 秒，所以你能传 `500*time.Millisecond`。这是它能精确到毫秒的起点。

- 返回值 `*BoolCmd`：**不是 `bool`**，这行最值得说，见块 7。

##### 块 4：分支二 —— 保留原 TTL

```go
	case KeepTTL:
		cmd = NewBoolCmd(ctx, "set", key, value, "keepttl", "nx")
```

【逐行理解】

- `KeepTTL` 是 go-redis 定义的常量：**`const KeepTTL = -1`**，注意它是 `time.Duration(-1)`，也就是 **-1 纳秒**，不是 -1 秒。这个数值很容易记错。
- 发出去的是 `SET <key> <value> KEEPTTL NX`：如果 key 已存在，覆盖 value 但**不动原来的过期时间**；不存在就正常写入（此时没有 TTL）。
- 用途：给已存在的 key 换值又不想刷新有效期。锁场景里「续期但不改 TTL」才用得上，属于冷门分支。
- **坑**：因为是 `case KeepTTL` 而不是 `case -1`，语义清楚；但如果你传了别的负数（比如 `-5 * time.Second`），会掉进 `default` 分支，最后发 `PX -5000`，被服务端以 `invalid expire time` 拒绝。**这类错误在客户端不报，延迟到服务端才暴露**，属于「了解即可」的边角。

##### 块 5：分支三 —— 有 TTL（锁的主路径）

【逐行理解】

**`usePrecise(d)` 的实现**是：

```go
func usePrecise(d time.Duration) bool {
	return d < time.Second || d%time.Second != 0
}
```

即「**不足 1 秒，或不是整秒**」就用毫秒精度。你博客里写「判断是否是整秒」是大致对的说法，精确表述是上面这行。锁的 TTL 基本都是 `800ms`、`30s`、`1500ms` 这种，前者必然走 PX，后者若给 `30*time.Second` 则走 EX——**同样是 30 秒，`30*time.Second` 发 `EX 30`，`30000*time.Millisecond` 也发 `EX 30`**，因为 Duration 是时间长度不是单位，两者相等。

**`formatMs` / `formatSec`** 做的事：`Duration` → 整数字符串。`formatMs` 是 `int64(d / time.Millisecond)`，**整数截断**。所以 `1500*time.Microsecond`（1.5ms）会被抹成 `1`，发 `PX 1`。TTL 给太小的值要小心，别指望亚毫秒精度。

**参数顺序不敏感**：`SET key v PX 30000 NX` 和 `SET key v NX PX 30000` 完全等价，Redis 自己解析选项。这里把 `nx` 放最后只是代码风格。

**这里是真正原子的一步**：`NX`（判存）和 `PX`（设过期）都是 `SET` 这一条命令的参数，服务端在 `setGenericCommand()` 一次调用里走完，中间插不进任何别的客户端的命令。**所以它不会出现「写进去了但过期没设上」的中间态**——这正是它相对于 `SETNX` + `EXPIRE` 两条命令的核心优势。

##### 块 6：真正把命令发出去

```go
	_ = c(ctx, cmd)
```

【逐行理解】

前面所有 `NewBoolCmd(...)` 都**只是构造**：把 `cmd`、`key`、`value`、`"px"`、`"30000"`、`"nx"` 塞进一个 `[]interface{}` 参数数组，再把 `cmd` 对象自己挂上。**一个字节都没发。**

`c(ctx, cmd)` 才真正干活，链路是：

```
c(ctx, cmd)
  → hooks 前置（监控/日志/耗时统计）
  → 从连接池取连接
  → 序列化成 RESP 协议写进 socket
  → 阻塞读回复（+OK / $-1 / -ERR）
  → 把结果写回 cmd.val / cmd.err
  → hooks 后置
```

**`_ =` 丢弃的是这次调用的返回值**，因为 `c(ctx, cmd)` 返回的 error 和已经存进 `cmd.err` 的是同一个东西，**没有丢失任何信息**——调用方后面 `cmd.Result()` 照样拿得到。这是 go-redis 全库的统一惯例，不是偷懒。

⚠️ 一个常见误解：**v9 的 `c()` 是同步阻塞的，命令在这一行就已经执行完、回复也已经读完。** `*BoolCmd` 不是「异步 future」，只是「一个已经装好结果的盒子」。

##### 块 7：为什么返回 `*BoolCmd` 而不是 `bool`

```go
	return cmd
}
```

【逐行理解】

返回盒子而不是值，是为了**统一 API 和延迟取错**：

```go
ok, err := client.SetNX(ctx, "lock", "uuid-1", 30*time.Second).Result()
```

`Result()` 做的事就是把 `cmd.val, cmd.err` 一起吐出来。好处是所有命令（`Get` 返回 `*StringCmd`、`HGet` 返回 `*StringCmd`、`SetNX` 返回 `*BoolCmd`）的调用姿势完全一致，也方便在 pipeline 里先攒一堆命令、最后统一收结果。

**关键行为**（面试高频）：

- 加锁成功 → `(true, nil)`
- 加锁失败（key 已存在，Redis 回 `nil`） → **`(false, nil)`**
- 网络错误 / 超时 / 语法错 → `(false, 非 nil error)`

`BoolCmd.readReply` 会把 `nil` 回复翻成 `false`，**不当作 error**。所以判断逻辑必须是：

```go
ok, err := client.SetNX(...).Result()
if err != nil { /* 真故障，可能是网络问题，锁状态未知 */ }
if !ok { /* 正常竞争失败，别人拿着锁 */ }
```

**把「锁被别人占着」当异常处理，是新手最常见的错。** 两者的语义完全不同：`!ok` 是预期内的，`err != nil` 是预期外的——**而且 `err != nil` 时你根本不知道 key 到底写没写进去**，这才是分布式锁真正难的地方（所以生产上要配 `GET` 校验 value 来兜底）。

##### 分档考点

【高频·实现层追问】为什么返回 `*BoolCmd` 而不是 `bool`？
→ 统一 API + 延迟取错，`Result()` 一次拿到 `(val, err)`。

【高频·实现层追问】`SetNX` 返回 `false` 时 `err` 是 nil 吗？
→ 是 nil。加锁失败是正常业务结果。

【高频·实现层追问】`err != nil` 时能确定锁没加上吗？
→ **不能**。可能是写进去了但回复丢了。这正是分布式锁的经典难题，要靠 value 唯一标识 + `GET` 校验 + 超时兜底。

【高频·概念】为什么发 `SET` 不发 `SETNX`？
→ `SETNX` 不能带过期时间，`SET` 支持 `NX/EX/PX/KEEPTTL`，一条命令完成三合一。

【加分·拓展】`SET ... NX PX` 和 `SETNX` + `EXPIRE` 的本质差别？
→ 前者一条命令原子；后者两条命令之间若客户端崩溃，留下**无 TTL 的永久锁**。**注意：这跟你博客「问题 2」的 `expiration = 0` 是两个不同成因，同一个终点。**

【了解即可】`KeepTTL = -1`（纳秒）、`formatMs` 整数截断、负数过期时间延迟到服务端报错、参数顺序不敏感。
