##### 一、快排

**大白话**：随便挑一个数当基准，把所有比它小的数都赶到左边，比它大的数都赶到右边；这样基准就落在最终位置上了，然后对左右两段递归做同样的事。

核心动作只有一个：`partition`。它写不对，整个快排就会出错。

```go
// Lomuto 划分：以最右元素为 pivot
func partition(a []int, lo, hi int) int {
	pivot := a[hi]
	i := lo                      // i 是"小于区"的下一个空位
	for j := lo; j < hi; j++ {
		if a[j] < pivot {
			a[i], a[j] = a[j], a[i]
			i++
		}
	}
	a[i], a[hi] = a[hi], a[i]    // pivot 归位
	return i
}

func quickSort(a []int, lo, hi int) {
	if lo >= hi {
		return
	}
	p := partition(a, lo, hi)
	quickSort(a, lo, p-1)
	quickSort(a, p+1, hi)
}
```

**递归边界**：`lo >= hi`，不是 `lo == hi`。这里写漏了，就是栈溢出。

**复杂度（必须背下来）**

| 场景 | 时间 | 空间 |
|---|---|---|
| 平均 | O(n log n) | O(log n) 递归栈 |
| 最坏 | **O(n²)** | **O(n)** 递归栈 |

最坏情况发生在**每次划分都极不均衡**时，比如数组已经有序，而你取首元素或尾元素当 pivot，每次只切掉一个元素，递归 n 层。

**两个真实存在的问题，面试最爱问**

1. **有序数组退化** → 随机取 pivot，或三数取中。
2. **大量重复元素退化**（Lomuto 碰到全相等的数组会退化成 O(n²)）→ 三路划分：

```go
// 荷兰国旗：lt 左边 < pivot，gt 右边 > pivot，[lt, gt] 全是 == pivot
func quick3(a []int, lo, hi int) {
	if lo >= hi { return }
	p := a[lo]
	lt, gt, i := lo, hi, lo
	for i <= gt {
		switch {
		case a[i] < p:
			a[lt], a[i] = a[i], a[lt]; lt++; i++
		case a[i] > p:
			a[i], a[gt] = a[gt], a[i]; gt--   // 注意 i 不动，换过来的数还没检查
		default:
			i++
		}
	}
	quick3(a, lo, lt-1)
	quick3(a, gt+1, hi)
}
```
`case a[i] > p` 时 `i` 不动，这点最容易写错，因为换来的是未检查的元素。

**稳定性：不稳定。** 跨距离交换一定会打乱相同元素的相对次序。

##### 二、归并

**大白话**：把数组对半劈开，分别排好，再把两个有序段像洗牌一样合并起来。

```go
func mergeSort(a []int) []int {
	if len(a) <= 1 {
		return a
	}
	mid := len(a) / 2
	l := mergeSort(a[:mid])
	r := mergeSort(a[mid:])
	return merge(l, r)
}

func merge(l, r []int) []int {
	out := make([]int, 0, len(l)+len(r))
	i, j := 0, 0
	for i < len(l) && j < len(r) {
		if l[i] <= r[j] {      // 必须 <= ，写 < 就不稳定
			out = append(out, l[i]); i++
		} else {
			out = append(out, r[j]); j++
		}
	}
	out = append(out, l[i:]...)
	out = append(out, r[j:]...)
	return out
}
```

**稳定性的关键就在那一个 `<=`**：相等时优先拿左边，左边本来就在前面。改成 `<` 就变不稳定的了。这个细节面试官必问。

**复杂度**：时间恒为 **O(n log n)**（没有最坏情况，这是它比快排稳的地方），空间 **O(n)**，稳定。

**归并真正的价值在于它衍生出的题**，而不是“排序”本身：

- **求逆序对**：合并时若 `r[j] < l[i]`，说明 `l[i:]` 全部大于 `r[j]`，一次就能贡献 `len(l) - i` 个逆序对。
- **链表排序（LC148）**：链表用归并不需要额外数组，只要拆开、合并指针，空间 O(1)（递归栈 O(log n)）。
- **外部排序**：数据大到内存放不下时，分块排好后做多路归并；这是大数据场景下唯一可行的排序方式。

**常见追问：空间能压到 O(1) 吗？** 数组的原地归并算法存在，但实现复杂度高、实际运行还更慢，工程上不会使用。所以正确的回答是：**数组归并的 O(n) 空间是可以避免的，但不会这么做；链表归并天然可以做到 O(1)。**

##### 三、堆排（只需记住三件事）

1. **建堆 O(n)，不是 O(n log n)**。从最后一个非叶节点 `n/2-1` 往前逐个下沉。直觉：**绝大多数节点在底层，下沉高度接近 0**，代价求和收敛到 O(n)。严格推导是 Σ 高度×该层节点数。
2. **排序阶段 O(n log n)**：反复“堆顶（最大值）与末尾交换，堆大小减一，新堆顶下沉”。
3. **原地，但不稳定**。堆排唯一的优势在于最坏情况也是 O(n log n) 且不需要额外空间；在 C++ 的 introsort 里，它是快排递归过深时的应急方案。

面试更常见的不是手写堆排，而是：

- **TopK** → 维护大小为 k 的**小顶堆**，O(n log k)，比全排序更好
- **数据流中位数** → 大顶堆 + 小顶堆

##### 四、三个 O(n²) 排序算法的取舍（会说就行，写就没必要）

| 算法 | 什么时候它有用 |
|---|---|
| 插入排序 | 小数组最快、近乎有序时 O(n)。**所有现代库排序的最后一步都靠它扫尾**（快排切到 <12 个元素就改用插入） |
| 冒泡 | 只考一个点：优化成“一轮无交换就提前退出”，以及“记录最后一次交换位置以缩小边界” |
| 选择排序 | 交换次数最少（n-1 次），但**不稳定**（注意“交换把远处相等的元素甩到后面”这个反例） |

**稳定性速查（必背）**：稳定 = 插入、冒泡、归并、计数、基数、桶；不稳定 = 快排、堆排、选择、希尔。

##### LC912 排序数组设定的意义

```
输入 nums，把数组升序排列，返回。
```

##### 版本一：归并（面试首选，最稳妥即可通过）

```go
func sortArray(nums []int) []int {
	aux := make([]int, len(nums))          // 只分配一次，别在递归里 make
	var sort func(lo, hi int)              // 区间 [lo, hi)
	sort = func(lo, hi int) {
		if hi-lo <= 1 {
			return
		}
		mid := lo + (hi-lo)/2
		sort(lo, mid)
		sort(mid, hi)

		i, j, k := lo, mid, lo
		for i < mid && j < hi {
			if nums[i] <= nums[j] {        // <= 才稳定
				aux[k] = nums[i]; i++
			} else {
				aux[k] = nums[j]; j++
			}
			k++
		}
		for i < mid { aux[k] = nums[i]; i++; k++ }
		for j < hi  { aux[k] = nums[j]; j++; k++ }
		copy(nums[lo:hi], aux[lo:hi])      // 写回原数组，下一层才看得到
	}
	sort(0, len(nums))
	return nums
}
```

**复杂度**：时间恒为 O(n log n)（**没有最坏情况**），空间 O(n)，稳定。

**本题中的注意点**

- `aux` 必须开在递归外。如果写成 `aux := make([]int, hi-lo)` 放在 merge 里，5×10⁴ 数据会产生约 8×10⁵ 次分配，虽然能过但会被面试官追问。
- 最后那个 `copy` 不能省。省了的话，`nums` 永远是原样，只排了 `aux`，这是手写归并最常见的错误。
- 区间用**左闭右开** `[lo, hi)`，不要和快排的闭区间混用，写一个就固定一种，否则边界必错。

##### 版本二：三路快排（原地、常数小，但必须随机化）

```go
func sortArray(nums []int) []int {
	var quick func(lo, hi int)             // 闭区间 [lo, hi]
	quick = func(lo, hi int) {
		if lo >= hi {
			return
		}
		r := lo + rand.Intn(hi-lo+1)       // 随机 pivot，防有序数据退化
		nums[lo], nums[r] = nums[r], nums[lo]

		p := nums[lo]
		lt, gt, i := lo, hi, lo
		for i <= gt {
			switch {
			case nums[i] < p:
				nums[lt], nums[i] = nums[i], nums[lt]
				lt++; i++
			case nums[i] > p:
				nums[i], nums[gt] = nums[gt], nums[i]
				gt--                       // i 不动！换过来的是没检查的数
			default:
				i++
			}
		}
		quick(lo, lt-1)                    // [lt, gt] 全是 == p，已经归位
		quick(gt+1, hi)
	}
	quick(0, len(nums)-1)
	return nums
}
```
`import "math/rand"`

**复杂度**：平均 O(n log n)，空间 O(log n) 栈；最坏理论 O(n²) 但概率可忽略。全相等数组因为三路划分直接 O(n)。

**本题中的注意点（这题最能体现这些注意点）**

1. **不随机化就大概率 TLE**。LC912 的测试集里有大量近乎有序和全相等的用例，固定 `nums[lo]` 或 `nums[hi]` 当 pivot，Lomuto 划分会退化成 O(n²)。
2. `nums[i] > p` 时**不能执行 i++**。这是三路划分唯一的思维陷阱：从右边换过来的元素还没检查过。
3. Go 的递归深度最坏 n 层，但 goroutine 栈可动态增长到 GB 级，5×10⁴ 层完全没事；同样的代码放 C++ 会爆栈。这点面试如果被问“栈溢出怎么办”，Go 和 C++ 要分开答。

##### 版本三：堆排（空间最优，代价是常数大）

```go
func sortArray(nums []int) []int {
	n := len(nums)

	var siftDown func(i, size int)         // 迭代版，无递归栈
	siftDown = func(i, size int) {
		for {
			l, r, big := 2*i+1, 2*i+2, i
			if l < size && nums[l] > nums[big] { big = l }
			if r < size && nums[r] > nums[big] { big = r }
			if big == i {
				return
			}
			nums[i], nums[big] = nums[big], nums[i]
			i = big
		}
	}

	for i := n/2 - 1; i >= 0; i-- {        // 建堆 O(n)，从最后非叶节点往前
		siftDown(i, n)
	}
	for size := n - 1; size > 0; size-- {  // 排序 O(n log n)
		nums[0], nums[size] = nums[size], nums[0]
		siftDown(0, size)
	}
	return nums
}
```

**复杂度**：O(n log n) 恒定，**额外空间 O(1)**（三个版本里唯一的时间最坏情况和空间都最优的版本），不稳定。

**本题中的注意点**：建堆起点是 `n/2 - 1`，不是 `n - 1`，叶子节点天然是堆。排序循环里 `size` 从 `n-1` 递减到 1，注意下沉传入的边界是 `size` 而不是 `n`。

```go
func sortArray(nums []int) []int {
	const offset = 50000
	cnt := make([]int, 100001)
	for _, v := range nums {
		cnt[v+offset]++
	}
	k := 0
	for v, c := range cnt {

		}

}
```

##### 未优化版 A：Lomuto 划分 + 端点做 pivot（教科书标准款）

```go
func sortArray(nums []int) []int {
	var quick func(lo, hi int) // 闭区间 [lo, hi]
	quick = func(lo, hi int) {
		if lo >= hi {
			return
		}
		p := partition(nums, lo, hi)
		quick(lo, p-1)
		quick(p+1, hi)
	}
	quick(0, len(nums)-1)
	return nums
}

func partition(a []int, lo, hi int) int {
	pivot := a[hi]      // 直接取最右元素，没有任何挑选
	i := lo
	for j := lo; j < hi; j++ {
		if a[j] < pivot {
			a[i], a[j] = a[j], a[i]
			i++
		}
	}
	a[i], a[hi] = a[hi], a[i]   // pivot 归位
	return i
}
```

这就是绝大多数人背的第一版快排：结构清楚、正确，在**随机数据**上跑得飞快，但在 LC912 上会直接 TLE。

###### 它在 LC912 上会以两种方式超时

**方式一：数组已经有序或接近有序**

`pivot = a[hi]` 恰好是当前区间最大值，partition 后 `p == hi`，左段长度为 `hi-lo`、右段为空——**每层只切掉一个元素**。递归深度达到 n，总比较次数为 `n(n-1)/2 ≈ 1.25×10⁹`（n = 5×10⁴）。这个数据量级下，Go 跑一遍要几秒钟，而 LC 的时限只有 1–2 秒，必然 TLE。

**方式二：数组里有大量重复元素（这比方式一更隐蔽）**

当所有元素都相等时，`a[j] < pivot` 永远为 false，`i` 一直不向前移动；循环结束后，代码把 `a[lo]` 和 `a[hi]` 互换，返回 `lo`——**左段为空、右段为 `[lo+1, hi]`，同样是每层只切掉一个元素**。

这里有一个关键点，很多人会想错：

> **只加随机化，解决不了重复元素导致的退化。**

因为随机选出来的 pivot 值还是同一个（所有值都相等），partition 的结果完全一样，仍然是 O(n²)。所以“随机化”和“三路划分”分别解决的是两个不同的问题，不能互相替代。

```go
		}
```

**这版有个极容易被写错的边界**：Hoare 的返回值 `j` **不是 pivot 的最终位置**，所以递归区间是 `[lo, j]` 和 `[j+1, hi]`——左段**包含** `j`，而不是 `[lo, j-1]`。如果按照 Lomuto 的习惯写成 `j-1`，就会漏掉元素，从而产生错误答案。这是 Hoare 版在面试中丢分的第一大原因。

###### 这里有一个反直觉的对比

| 输入 | Lomuto（A 版） | Hoare（B 版） |
|---|---|---|
| 随机数据 | O(n log n) | O(n log n)，比较次数更少 |
| 已排序 | **O(n²)** | **O(n²)**（pivot 是最小值，同样每层只切掉一个元素） |
| **全部相等** | **O(n²)** | **O(n log n)** ✅ |

Hoare 划分时，两个指针只有在“左边遇到 ≥ pivot、右边遇到 ≤ pivot”时才交换，所以**全相等数组会被均匀地从中间劈开**——这正是 Hoare 版的天然优势，也是它在不少教材里被使用时不用额外处理重复元素的原因。

##### 先纠正一个提问里的隐含前提

严格说，**Hoare 不是“优化版”，它是原始版**：Hoare 划分来自 1961 年他本人的 quicksort 论文；Lomuto 划分则是 1980 年代才出现的**教学简化版**，它用可读性换性能。

所以更准确的问法是：**Lomuto 相比 Hoare，牺牲了什么？** 下面按这个思路讲。

---

##### 一、核心差异：一对一安置 与 成对交换

看两段内层循环的对比：

```go
// Lomuto：单指针 j 单向扫，每找到一个小于 pivot 的元素，就挪到 i
for j := lo; j < hi; j++ {
	if a[j] < pivot {
		a[i], a[j] = a[j], a[i]   // 每次交换只安置 1 个元素
		i++
	}
}

// Hoare：两个指针向中间夹，两端各找到一个"错位"元素才交换
for i <= hi && a[i] < pivot { i++ }
for j >= lo+1 && a[j] > pivot { j-- }
if i >= j { break }
a[i], a[j] = a[j], a[i]           // 一次交换同时安置 2 个元素
```

**这就是关键**：Lomuto 每做一次交换，只把一个元素安置到正确的一侧；Hoare 每做一次交换，**同时把右边的小元素送到左边，把左边的大元素送到右边**，一次交换就能同时完成两个元素的位置调整。

在随机数据上，这个差别会让交换次数相差约 **3 倍**（经验值；Hoare 约 n/6 次，Lomuto 约 n/2 次）。Lomuto 还有额外浪费：当 `i == j` 时，它会对元素自己和自己做交换，纯粹是空操作。

**既然 Lomuto 那么差，为什么书上都先教它？** 因为它的不变式极好理解（`[lo, i)` 全小于 pivot、`[i, j)` 全大于等于 pivot），20 行就能讲清，面试写起来也不容易错。**它是为了教学而故意牺牲性能的版本。**

---

##### 二、更大的收益：重复元素（这是初学者常忽略的点）

上一轮已经算过：**Lomuto 在全等数组上是 O(n²)**。原因是 `a[j] < pivot` 恒为 false，`i` 一动不动，最后返回 `lo`，每层只切掉一个元素。

Hoare 为什么不会这样？**因为它把“等于 pivot”也视为错位。**

- `a[i] < pivot` 时停 → 停在第一个 **≥ pivot** 的元素上
- `a[j] > pivot` 时停 → 停在第一个 **≤ pivot** 的元素上

全等数组里，两个指针**一开始就同时停下**，直接交换、各走一步、再同时停下……于是指针从两端向中间同步移动，**区间被均匀从中间劈开**，递归深度是 log n，复杂度是 O(n log n)。

关键在于**停止条件用的是严格不等号**。这是 Lomuto 和 Hoare 设计哲学的分歧：
- Lomuto 把“等于”归到**一侧**（`<` 进左，`>=` 进右）→ 相等元素全堆一边 → 划分失衡
- Hoare 把“等于”当作**可以交换的对象** → 相等元素被均匀撒到两边 → 划分平衡

这一条在 LC912 这种“测试数据里塞了大量重复值”的题上，是**生与死的差别**。

---

##### 三、还有两个小差别（知道即可，别当主要论据）

| 维度 | Lomuto | Hoare |
|---|---|---|
| 比较次数 | 每次划分约 n 次 | 约 n 次，**差别很小** |
| pivot 位置自由度 | 必须在端点（要当哨兵） | 也可端点，但通常是先存值 |
| 是否需要“pivot 归位”那步 | 需要，`a[i], a[hi] = a[hi], a[i]` | 需要，但**返回值不是 pivot 位置** |
| 递归区间 | `[lo, p-1]`、`[p+1, hi]` | `[lo, j]`、`[j+1, hi]`（**左段含 j**） |

**比较次数没有本质优势**，这一点要敢于否定。很多人以为 Hoare“更快”是因为比较更少，其实不是，差异在**数据移动量**和**划分平衡度**。

另外承认一个 Hoare 的**真实缺点**：`[lo, j]` 左段包含 `j`，意味着 pivot 归位后**还会被当作普通元素再参与一次划分**，多一次无谓比较。同时，这个“返回值不是 pivot 位置”的语义也是 Hoare 版最难写对、最容易在面试里写错、递归边界也最容易出错的地方——**收益是性能，代价是容易写错**。

##### 四、客观结论：它的上限在哪

Hoare 在重复元素上是“**不会失控**”，但并非“**最优**”。

- **全等数组**：Hoare 是 O(n log n)，但它会做成千上万次**毫无意义的相等元素互换**（换个位置还是同一个值）。
- **三路划分**：全等数组是 **O(n)**，一次扫描结束，等于区直接跳过不递归。

所以性能排序是：**三路划分（重复多）＞ Hoare（重复多但不如三路）＞ Lomuto（重复多直接失控）**；随机数据上则是 **Hoare ≈ 三路 ＞ Lomuto**。

顺带说一句，现代高性能实现（pdqsort、C++ 的 `std::sort`）**既不用裸 Hoare，也不用 Lomuto**，用的是**分块划分（block partition）**——把 Hoare 的“两端夹”换成“攒一批再批量交换”，进一步减少分支和写操作。Hoare 划分的历史地位是“原始正确版本 + 划分思想的源头”，不是“终极答案”。

##### 先通俗讲清前面的数字

前面说的交换次数和层数，说白了就是两句话：

- **Lomuto 是一个一个搬**：扫到一个比 pivot 小的元素，才把它移到左边，一次只处理一个元素。
- **Hoare 是一对一对换**：左边找出一个“本该在右边”的，右边找出一个“本该在左边”的，一次换一对。

所以 Lomuto 的交换次数约等于“比 pivot 小的元素个数”，Hoare 约等于“真正错位的对数”。

**全等数组**最能体现差别：Lomuto 只看“是不是严格小于 pivot”，判断结果永远为否，一个元素都搬不动，每层只切掉一个元素，于是变成一条链；Hoare 把“等于”也视为错位，两个指针一碰到相等元素就交换，于是区间被对半切开。

---

##### 为什么 Hoare 必须先动 j

**用一个比喻来理解**：pivot 放在 `lo`，相当于在**左边界派了一个守卫**。

`j` 从右往左走，任务是找出“小于或等于 pivot”的元素。它一路走一路看，万一左边全是大于 pivot 的元素怎么办？没关系，它走到 `lo` 时，`a[lo]` 就是 pivot 本身，而一个数不可能“大于自己”，所以**它必然在这里停下，永远走不出这个区间**。

`i` 从左往右走，左边没有守卫保护它。因此它需要一个“天花板”，也就是**`j` 已经停下的位置**。`i` 一旦走到 `j`，循环就结束，所以它也走不出去。

顺序因此是确定的：

> **先让 j 走**，它有守卫保护，绝对安全；**再让 i 走**，它靠 j 保护，同样安全。

反过来先动 `i`：第一轮 `i` 会停在 `lo`，因为 pivot 不小于 pivot；此时 `j` 还没动，两者一交换，**就把守卫换走了**，`lo` 上不再是 pivot。之后 `j` 继续往左扫，就没有东西能保证它停下。

【了解即可】严格说，在 CLRS 这种“i 从 lo-1、j 从 hi+1”的对称写法里，两种顺序往往能得到相同结果；但“先 j 后 i”是唯一在**各种变体写法下都不用补边界 if** 的顺序，所以成了标准。考试时按“先 j”记，不会出错。

##### 为什么 Hoare 用 lo、Lomuto 用 hi

一句话：**Hoare 需要哨兵，Lomuto 不需要。**

| | 扫描方式 | 是否依赖哨兵 | 结论 |
|---|---|---|---|
| Hoare | `i`、`j` 从两端向中间走 | **需要**，因为 `j` 向左扫必须保证不越界 | 哨兵只能来自 `lo` 位置上的 pivot，所以**必须用 lo** |
| Lomuto | 单个 `j` 单向从左扫到右 | **不需要**，右边界写死成 `hi` | 两端都行；教材选 `hi` 只是让 `i := lo-1`、`return i+1` 写起来对称 |

所以准确的结论是：

- Hoare 用 lo 是**强制**的：如果换成 hi，`j` 从 `hi` 出发，一开始就会停在自己身上，左边没有守卫，一路扫到 `lo` 以下就会越界。
- Lomuto 用 hi 是**习惯**：如果换成 lo 完全安全，只是索引要偏移一位。

【必记】Hoare→lo，Lomuto→hi；Hoare 换到 hi 需要补边界检查，Lomuto 换到 lo 不用担心。

##### 实操：先看一个最小例子，再自己走一遍

**示范**（[3,1,2]，pivot=3，走 CLRS 版）：

| 轮次 | 动作 | 数组 |
|---|---|---|
| 1 | j 从 3 减到 2，`a[2]=2 > 3` 为否，停 | `[3,1,2]` |
| | i 从 -1 增到 0，`a[0]=3 < 3` 为否，停 | |
| | i(0) < j(2)，交换 `a[0]`↔`a[2]` | `[2,1,3]` |
| 2 | j 减到 1，`a[1]=1 > 3` 为否，停 | |
| | i 增到 1，`a[1]=1 < 3` 为是 → i 增到 2，`a[2]=3 < 3` 为否，停 | |
| | i(2) ≥ j(1)，退出，**返回 j=1** | |
| 结果 | 左段 `[0,1]`= `[2,1]`，右段 `[2,2]`= `[3]` | 划分正确 |

**轮到你**：对数组 `[5, 1, 9, 2, 8]`，pivot = 5（lo=0，hi=4），按同样的格式走一遍，并记下：

1. 每一轮 `j` 停在哪、`i` 停在哪
2. 交换了哪两个下标
3. 退出时 `return j` 的值是多少

- `j` 从 `hi+1 = 5` 开始，**第一次要先 `j--` 变成 4 才比较**，而不是从 4 直接比较。
- `i` 从 `lo-1 = -1` 开始，第一次也是先 `i++` 变成 0。
