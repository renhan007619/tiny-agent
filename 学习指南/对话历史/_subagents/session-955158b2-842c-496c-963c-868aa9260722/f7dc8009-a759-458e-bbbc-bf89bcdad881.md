##### 未优化版 A：Lomuto 划分 + 端点做 pivot（教科书标准款）

```go
func sortArray(nums []int) []int {
	var quick func(lo, hi int) // 闭区间 [lo, hi]
	quick = func(lo, hi int) {
		if lo >= hi {
			return
		}
		p := partition(nums, lo, hi)
		quick(lo, p-1)
		quick(p+1, hi)
	}
	quick(0, len(nums)-1)
	return nums
}

func partition(a []int, lo, hi int) int {
	pivot := a[hi]      // 直接取最右元素，没有任何挑选
	i := lo
	for j := lo; j < hi; j++ {
		if a[j] < pivot {
			a[i], a[j] = a[j], a[i]
			i++
		}
	}
	a[i], a[hi] = a[hi], a[i]   // pivot 归位
	return i
}
```

这就是绝大多数人背的第一版快排：结构清楚、正确，在**随机数据**上跑得飞快，但在 LC912 上会直接 TLE。

###### 它在 LC912 上会以两种方式超时

**方式一：数组已经有序或接近有序**

`pivot = a[hi]` 恰好是当前区间最大值，partition 后 `p == hi`，左段长度为 `hi-lo`、右段为空——**每层只切掉一个元素**。递归深度达到 n，总比较次数为 `n(n-1)/2 ≈ 1.25×10⁹`（n = 5×10⁴）。这个数据量级下，Go 跑一遍要几秒钟，而 LC 的时限只有 1–2 秒，必然 TLE。

**方式二：数组里有大量重复元素（这比方式一更隐蔽）**

当所有元素都相等时，`a[j] < pivot` 永远为 false，`i` 一直不向前移动；循环结束后，代码把 `a[lo]` 和 `a[hi]` 互换，返回 `lo`——**左段为空、右段为 `[lo+1, hi]`，同样是每层只切掉一个元素**。

这里有一个关键点，很多人会想错：

> **只加随机化，解决不了重复元素导致的退化。**

因为随机选出来的 pivot 值还是同一个（所有值都相等），partition 的结果完全一样，仍然是 O(n²)。所以“随机化”和“三路划分”分别解决的是两个不同的问题，不能互相替代。

##### 未优化版 B：Hoare 双指针 + 首元素做 pivot（原始论文版）

```go
func sortArray(nums []int) []int {
	var quick func(lo, hi int)
	quick = func(lo, hi int) {
		if lo >= hi {
			return
		}
		p := partition(nums, lo, hi)
		quick(lo, p)
		quick(p+1, hi)      // 注意：Hoare 返回的 p 不是 pivot 最终位置
	}
	quick(0, len(nums)-1)
	return nums
}

func partition(a []int, lo, hi int) int {
	pivot := a[lo]
	i, j := lo+1, hi
	for {
		for i <= hi && a[i] < pivot {
			i++
		}
		for j >= lo+1 && a[j] > pivot {
			j--
		}
		if i >= j {
			break
		}
		a[i], a[j] = a[j], a[i]
		i++
		j--
	}
	a[lo], a[j] = a[j], a[lo]
	return j
}
```

**这版有个极容易被写错的边界**：Hoare 的返回值 `j` **不是 pivot 的最终位置**，所以递归区间是 `[lo, j]` 和 `[j+1, hi]`——左段**包含** `j`，而不是 `[lo, j-1]`。如果按照 Lomuto 的习惯写成 `j-1`，就会漏掉元素，从而产生错误答案。这是 Hoare 版在面试中丢分的第一大原因。

###### 这里有一个反直觉的对比

| 输入 | Lomuto（A 版） | Hoare（B 版） |
|---|---|---|
| 随机数据 | O(n log n) | O(n log n)，比较次数更少 |
| 已排序 | **O(n²)** | **O(n²)**（pivot 是最小值，同样每层只切掉一个元素） |
| **全部相等** | **O(n²)** | **O(n log n)** ✅ |

Hoare 划分时，两个指针只有在“左边遇到 ≥ pivot、右边遇到 ≤ pivot”时才交换，所以**全相等数组会被均匀地从中间劈开**——这正是 Hoare 版的天然优势，也是它在不少教材里被使用时不用额外处理重复元素的原因。

所以在 LC912 上，两个未优化版本都会在“有序数据”上失败，但原因不完全相同：A 版因为有序和重复元素**两种原因**失败，B 版只因为有序**一种原因**失败。这个区别说清楚，面试官基本能确认你确实研究过。

##### 先纠正一个提问里的隐含前提

严格说，**Hoare 不是“优化版”，它是原始版**：Hoare 划分来自 1961 年他本人的 quicksort 论文；Lomuto 划分则是 1980 年代才出现的**教学简化版**，它用可读性换性能。

所以更准确的问法是：**Lomuto 相比 Hoare，牺牲了什么？** 下面按这个思路讲。

---

##### 一、核心差异：一对一安置 与 成对交换

看两段内层循环的对比：

```go
// Lomuto：单指针 j 单向扫，每找到一个小于 pivot 的元素，就挪到 i
for j := lo; j < hi; j++ {
	if a[j] < pivot {
		a[i], a[j] = a[j], a[i]   // 每次交换只安置 1 个元素
		i++
	}
}

// Hoare：两个指针向中间夹，两端各找到一个"错位"元素才交换
for i <= hi && a[i] < pivot { i++ }
for j >= lo+1 && a[j] > pivot { j-- }
if i >= j { break }
a[i], a[j] = a[j], a[i]           // 一次交换同时安置 2 个元素
```

**这就是关键**：Lomuto 每做一次交换，只把一个元素安置到正确的一侧；Hoare 每做一次交换，**同时把右边的小元素送到左边，把左边的大元素送到右边**，一次交换就能同时完成两个元素的位置调整。

在随机数据上，这个差别会让交换次数相差约 **3 倍**（经验值；Hoare 约 n/6 次，Lomuto 约 n/2 次）。Lomuto 还有额外浪费：当 `i == j` 时，它会对元素自己和自己做交换，纯粹是空操作。

**既然 Lomuto 那么差，为什么书上都先教它？** 因为它的不变式极好理解（`[lo, i)` 全小于 pivot、`[i, j)` 全大于等于 pivot），20 行就能讲清，面试写起来也不容易错。**它是为了教学而故意牺牲性能的版本。**

---

##### 二、更大的收益：重复元素（这是初学者常忽略的点）

上一轮已经算过：**Lomuto 在全等数组上是 O(n²)**。原因是 `a[j] < pivot` 恒为 false，`i` 一动不动，最后返回 `lo`，每层只切掉一个元素。

Hoare 为什么不会这样？**因为它把“等于 pivot”也视为错位。**

- `a[i] < pivot` 时停 → 停在第一个 **≥ pivot** 的元素上
- `a[j] > pivot` 时停 → 停在第一个 **≤ pivot** 的元素上

全等数组里，两个指针**一开始就同时停下**，直接交换、各走一步、再同时停下……于是指针从两端向中间同步移动，**区间被均匀从中间劈开**，递归深度是 log n，复杂度是 O(n log n)。

关键在于**停止条件用的是严格不等号**。这是 Lomuto 和 Hoare 设计哲学的分歧：
- Lomuto 把“等于”归到**一侧**（`<` 进左，`>=` 进右）→ 相等元素全堆一边 → 划分失衡
- Hoare 把“等于”当作**可以交换的对象** → 相等元素被均匀撒到两边 → 划分平衡

这一条在 LC912 这种“测试数据里塞了大量重复值”的题上，是**生与死的差别**。

---

##### 三、还有两个小差别（知道即可，别当主要论据）

| 维度 | Lomuto | Hoare |
|---|---|---|
| 比较次数 | 每次划分约 n 次 | 约 n 次，**差别很小** |
| pivot 位置自由度 | 必须在端点（要当哨兵） | 也可端点，但通常是先存值 |
| 是否需要“pivot 归位”那步 | 需要，`a[i], a[hi] = a[hi], a[i]` | 需要，但**返回值不是 pivot 位置** |
| 递归区间 | `[lo, p-1]`、`[p+1, hi]` | `[lo, j]`、`[j+1, hi]`（**左段含 j**） |

**比较次数没有本质优势**，这一点要敢于否定。很多人以为 Hoare“更快”是因为比较更少，其实不是，差异在**数据移动量**和**划分平衡度**。

另外承认一个 Hoare 的**真实缺点**：`[lo, j]` 左段包含 `j`，意味着 pivot 归位后**还会被当作普通元素再参与一次划分**，多一次无谓比较。同时，这个“返回值不是 pivot 位置”的语义也是 Hoare 版最难写对、最容易在面试里写错、递归边界也最容易出错的地方——**收益是性能，代价是容易写错**。

---

##### 四、客观结论：它的上限在哪

Hoare 在重复元素上是“**不会失控**”，但并非“**最优**”。

- **全等数组**：Hoare 是 O(n log n)，但它会做成千上万次**毫无意义的相等元素互换**（换个位置还是同一个值）。
- **三路划分**：全等数组是 **O(n)**，一次扫描结束，等于区直接跳过不递归。

所以性能排序是：**三路划分（重复多）＞ Hoare（重复多但不如三路）＞ Lomuto（重复多直接失控）**；随机数据上则是 **Hoare ≈ 三路 ＞ Lomuto**。

顺带说一句，现代高性能实现（pdqsort、C++ 的 `std::sort`）**既不用裸 Hoare，也不用 Lomuto**，用的是**分块划分（block partition）**——把 Hoare 的“两端夹”换成“攒一批再批量交换”，进一步减少分支和写操作。Hoare 划分的历史地位是“原始正确版本 + 划分思想的源头”，不是“终极答案”。

##### 五、面试怎么答这题（照这个说就够）

> Hoare 划分相对 Lomuto 有两个实质优势：一是**交换次数少**，它一次交换同时安置两端两个错位元素，Lomuto 一次只安置一个，随机数据下交换量大约差三倍；二是**对重复元素稳健**，因为它的停指针条件是严格不等号，等于 pivot 的元素会被均匀分到两侧，而 Lomuto 会把相等元素全归一侧，导致全等数组退化成 O(n²)。比较次数两者差不多，不是差异点。不过 Hoare 的递归区间是 `[lo, j]` 和 `[j+1, hi]`，左段包含 j，返回值不是 pivot 最终位置，这是它最容易写错的地方；而重复元素的最优解其实不是 Hoare，是三路划分。

##### 例 1：全等数组 `[7,7,7,7,7,7,7,7]`（8 个 7）

看**递归层数**，这是最能说明问题的地方：

**Lomuto**（pivot 取端点 7）
```
第一层 partition：没有任何元素 < 7，返回 lo
→ 左段空，右段只剩 7 个 7
第二层：同样，右段只剩 6 个
...
```
每层只切掉 **1 个元素**，共 **7 层**。每层扫一遍 O(n)，总时间 **O(n²)**。

**Hoare**（pivot = 7，两个指针一起走）
```
i 停在 1（7 不小于 7），j 停在 7（7 不大于 7）→ 交换，i=2, j=6
i 停 2，j 停 6 → 交换，i=3, j=5
i 停 3，j 停 5 → 交换，i=4, j=4 → 交叉，返回 j=4
```
一层就直接把 8 个元素切成 **[0,4] 和 [5,7]**，即 5 个和 3 个。再往下一层递归，**总共只有 3 层**。

| | 层数 | 总时间 |
|---|---|---|
| Lomuto | 7 层（≈ n） | O(n²) |
| Hoare | 3 层（≈ log₂n） | O(n log n) |

一句话：**Hoare 把“等于 pivot”当作应该交换的情况，所以相等元素被均匀掷到两边；Lomuto 把“等于”全推给一侧，于是每次只切掉一个元素。**

##### 先通俗讲清前面的数字

前面说的交换次数和层数，说白了就是两句话：

- **Lomuto 是一个一个搬**：扫到一个比 pivot 小的元素，才把它移到左边，一次只处理一个元素。
- **Hoare 是一对一对换**：左边找出一个“本该在右边”的，右边找出一个“本该在左边”的，一次换一对。

所以 Lomuto 的交换次数约等于“比 pivot 小的元素个数”，Hoare 约等于“真正错位的对数”。

**全等数组**最能体现差别：Lomuto 只看“是不是严格小于 pivot”，判断结果永远为否，一个元素都搬不动，每层只切掉一个元素，于是变成一条链；Hoare 把“等于”也视为错位，两个指针一碰到相等元素就交换，于是区间被对半切开。

##### 为什么 Hoare 必须先动 j

**用一个比喻来理解**：pivot 放在 `lo`，相当于在**左边界派了一个守卫**。

`j` 从右往左走，任务是找出“小于或等于 pivot”的元素。它一路走一路看，万一左边全是大于 pivot 的元素怎么办？没关系，它走到 `lo` 时，`a[lo]` 就是 pivot 本身，而一个数不可能“大于自己”，所以**它必然在这里停下，永远走不出这个区间**。

`i` 从左往右走，左边没有守卫保护它。因此它需要一个“天花板”，也就是**`j` 已经停下的位置**。`i` 一旦走到 `j`，循环就结束，所以它也走不出去。

顺序因此是确定的：

> **先让 j 走**，它有守卫保护，绝对安全；**再让 i 走**，它靠 j 保护，同样安全。

反过来先动 `i`：第一轮 `i` 会停在 `lo`，因为 pivot 不小于 pivot；此时 `j` 还没动，两者一交换，**就把守卫换走了**，`lo` 上不再是 pivot。之后 `j` 继续往左扫，就没有东西能保证它停下。

【了解即可】严格说，在 CLRS 这种“i 从 lo-1、j 从 hi+1”的对称写法里，两种顺序往往能得到相同结果；但“先 j 后 i”是唯一在**各种变体写法下都不用补边界 if** 的顺序，所以成了标准。考试时按“先 j”记，不会出错。

---

##### 为什么 Hoare 用 lo、Lomuto 用 hi

一句话：**Hoare 需要哨兵，Lomuto 不需要。**

| | 扫描方式 | 是否依赖哨兵 | 结论 |
|---|---|---|---|
| Hoare | `i`、`j` 从两端向中间走 | **需要**，因为 `j` 向左扫必须保证不越界 | 哨兵只能来自 `lo` 位置上的 pivot，所以**必须用 lo** |
| Lomuto | 单个 `j` 单向从左扫到右 | **不需要**，右边界写死成 `hi` | 两端都行；教材选 `hi` 只是让 `i := lo-1`、`return i+1` 写起来对称 |

所以准确的结论是：

- Hoare 用 lo 是**强制**的：如果换成 hi，`j` 从 `hi` 出发，一开始就会停在自己身上，左边没有守卫，一路扫到 `lo` 以下就会越界。
- Lomuto 用 hi 是**习惯**：如果换成 lo 完全安全，只是索引要偏移一位。

【必记】Hoare→lo，Lomuto→hi；Hoare 换到 hi 需要补边界检查，Lomuto 换到 lo 不用担心。

}

##### 通俗理解：pivot 是墙，墙只能单面防护

**pivot 放在 lo** → 给左边界砌了一堵墙。`j` 从右往左走，走到墙前**必定停下**（墙上的值不大于它自己），所以 `j` 绝不会扫出界。

`i` 从左往右走，前面没墙，所以让它**后走**：等 `j` 站好位置，`i` 走到 `j` 就停下。

顺序反了会怎样？拿 `[1,2,3]` 试（pivot 取 lo=0 的 1）：

| | 先动 i（❌） | 先动 j（✅） |
|---|---|---|
| 第一步 | i 从 0 出发，`1 <= 1` 成立 → **跨过墙**到 1；`2 <= 1` 不成立，停 | j 从 2 出发：`3>=1`→1，`2>=1`→0，**撞墙停** |
| 第二步 | j 从 2 减到 1，撞上 i，停 | i 根本没机会出发 |
| 归位 | `swap(nums[1], nums[0])` → `[2,1,3]` | `swap(nums[0], nums[0])`，返回 0 |
| 结果 | **2 > 1 却跑到 pivot 左边，错** | 正确 |

|---|---|---|
| `[lo, lt)` | 比 p 小的人 | `lt` |
| `[lt, i)` | 和 p 一样高的人 | `i` |
| `[i, gt]` | **还没看的人** | `i` 正在检查 |
| `(gt, hi]` | 比 p 大的人 | `gt` |

循环做的事就是：**`i` 检查自己面前这个人，把他分到左边、中间、右边三组。**

- 比 p 小 → 和 `lt` 位置换一下，`lt` 前进，`i` 前进
- 和 p 一样 → 直接放过，`i` 前进
- 比 p 大 → 和 `gt` 位置换一下，`gt` 后退

循环结束时 `i > gt`，`[lt, gt]` 这一段**全部等于 p**，所以它们**已经在最终位置上，不需要再递归**。返回 `lt-1` 和 `gt+1`，把这一段整个跳过。

---

##### 【必记】`nums[i] > p` 时 i 为什么不能前进

因为 `swap(nums[i], nums[gt])` 是**从右侧换过来一个尚未检查的元素**。`gt` 位置上的元素还没被 `i` 检查过。你这个时候如果 `i++`，就等于**跳过一个未检查的元素**，直接产生错误答案。

对比之前讨论的“先动 j”那套：这里是“换来的没看过，所以原地再看一眼”。这是荷兰国旗标志算法唯一的易错点。

##### 复杂度（n = 数组长度）

| 场景 | 时间 | 空间 |
|---|---|---|
| 平均 | O(n log n) | O(log n) 栈 |
| **全等数组** | **O(n)** | O(1) 栈 |

全等数组为什么是 O(n)：所有元素都走 `default`，`i` 一路扫到 `hi+1`，`[lt, gt]` 一下覆盖整个区间，左右两段都为空，**递归直接终止**。一次扫描就结束。

##### 三种划分横向对比

| 划分方式 | 随机数据 | 全等数组 | 交换次数 | 特点 |
|---|---|---|---|---|
| 二路（你原来的两端夹） | O(n log n) | **O(n²)** | 中 | 简单、闭区间干净 |

##### 根本原因：`gt` 位置本身还没有被检查过

三路划分的不变式是：

```
[lo, lt) 小于 p    [lt, i) 等于 p    [i, gt] 没看过    (gt, hi] 大于 p
```

注意，最右边是 `(gt, hi]`，而 **`gt` 本身属于“没看过”这一段的右端点**。

所以 `swap(nums[i], nums[gt])` 换过来的 `nums[gt]`，是一个还没被 `i` 检查过的元素。如果 `i++`，这个元素就再也没人检查它了；它可能比 `p` 小，却会被永远留在右边。

##### 反例：[2, 3, 1]，p = 2

**正确写法（i 不动）**

| i | 看到 | 动作 | 数组 | lt, gt |
|---|---|---|---|---|
| 0 | `2` = p | i++ | `[2,3,1]` | 0, 2 |
| 1 | `3` > p | 换 `i` 和 `gt`，gt-- | `[2,1,3]` | 0, 1 |
| 1 | `1` < p（**重新检查**） | 换 `lt` 和 `i`，lt++, i++ | `[1,2,3]` | 1, 2 |
| 2 | i > gt，结束 | 返回 `(0, 2)` | | |

等于区 `[1,1]` = `[2]` 是干净的，结果正确。

**错误写法（i++）**

| i | 看到 | 动作 | 数组 | lt, gt |
|---|---|---|---|---|
| 0 | `2` = p | i++ | `[2,3,1]` | 0, 2 |
| 1 | `3` > p | 换 `i` 和 `gt`，gt--，**i++** | `[2,1,3]` | 0, 1 |
| 2 | i > gt，结束 | 返回 `(1, 2)` | | |

等于区 `[1,1]` 里放的是 `1`，但它明明 `< p`，所以**小于区混进了等于值、等于区混进了小于值**，划分直接失效。

##### 那什么时候 i 才不用管？

只有一种情况：**`gt == i`**，也就是右边已经没有“没看过”的元素了。这时 `swap` 是自交换，`nums[i]` 还是原来的 `> p`，`gt--` 之后 `i > gt` 循环自然结束，等价于“不动”。

所以统一写“`> p` 时 `i` 不动”，逻辑最简单，不需要特判。

---

【必记】三路划分的 `i` 只有两个出口：`< p` 时 `i++`，`== p` 时 `i++`；`> p` 时 **`i` 原地不动，只让 `gt--`**。判断标准就一句：**“换进来的是谁？没检查过就原地再看一眼。”**
