##### 结论

这个问题本身是个伪二选一。**OTel 里没有哪一段值得你自研，而“自研”真正有内容的部分，OTel 也帮不了你**。正确做法是分层：管道用 OTel，语义自己设计。另外，我不同意“作为下一个模块”这个提法——理由在后面。

##### 为什么

OTel 分为三段，逐段来看：

| 段 | 内容 | 自研价值 |
|---|---|---|
| 数据模型 | trace/span/metric/log + 属性、context 传播 | 0（自研 = 造轮子，面试扣分） |
| SDK/导出 | Go SDK、采样、OTLP、Collector、Jaeger | 0（同上） |
| **语义** | 一个 agent 的 span 如何切分、属性叫什么、哪些指标值得计算 | **全部价值都在这里** |

第三段恰好是生态尚未统一的领域。OTel 官方的 GenAI semconv（`gen_ai.*`）到 2025 年仍是 development 状态，agent 这一层（`invoke_agent` / `execute_tool` / 多轮对话怎么归属于 trace）更是各家在摸索：[AI Agent Observability – Evolving Standards](https://opentelemetry.io/blog/2025/ai-agent-observability/)、[gen_ai 属性注册表](https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/)。所以“自研”的定位应当是：**按 gen_ai 的命名约定，扩展一组 agent 专用属性**——换后端时不用改一行业务代码，这就是面试话术里最值钱的一句，也远强于“我自己做了个日志系统”。

##### 质疑你的两个前提

**1. 可观测性不是模块，是横切关注点。**

一旦将它做成独立的 `obs.go` 包，它就只能看到模块边界，也就是 `SendMessage` 的入参和返回值。而你项目里最值得观测的东西全都发生在内部：

- 工具循环第几轮开始消耗 token
- 装配器裁剪了哪一段、裁了多少
- 哪次工具结果被外置了、句柄是什么

这些要么在 `agent.go` 的循环内部，要么在 `AssembleReport` 中。因此，可观测性必须**从内部埋点、由外部上报**，不能等业务层运行完再回头补。

**2. 你已有的可观测性雏形已经很像样了，别推倒重来。**

`AssembleReport`（`context_assembler.go:126`）、`>>> [1] 调用模型 4.2s` 这类 stderr 打点、warning 三分类——这已经是“结构化观测数据”，只是序列化成了人类可读文本、目标是 stderr。这个模块要做的是**给这些数据加一条机器可读的通道**，并非新建一块东西。

顺带一个实证：`schema.go:110` 的 `Tool.execute(input)` 不带 `ctx`。接 OTel 时第一个会卡住的地方就是这里——工具内部的 IO 没法挂到父 span 下，也没法被取消。**这就是“可观测性不能是独立模块”的证据**：它要求 context 已经贯穿全链路，而你的项目还没有做到。

├─ context.assemble          attrs: window/available/msg_budget + 每段 used|budget|trimmed

##### 三个必须现在就定的决策（也是最容易被面试问的）

1. **prompt / 工具结果全文绝不进 span attribute**。高基数、撑爆后端、隐私，三宗罪。正确做法是把句柄写进 trace，全文留在 `resultstore`——**你已经有 resultstore 了，这是天然契合，是这套设计里最漂亮的一环**。
2. **采样**：agent 长尾失败多，默认头部采样会丢掉失败样本。用 `ParentBased(TraceIDRatio)` 作兜底，并让错误强制采样，或者在 Collector 侧做尾采样。
3. **trace 边界**：一轮用户输入 = 一个 trace。一旦跨轮切分，会话关联就断了；会话级信息用 baggage / `session.id` 属性带。

##### 面试分层
