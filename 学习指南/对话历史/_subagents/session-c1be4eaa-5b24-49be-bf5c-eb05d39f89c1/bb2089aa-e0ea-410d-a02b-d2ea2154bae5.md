#### 归并排序：一句话本质

**把数组分成两半，各自排好，再把两个有序数组合并成一个。** 核心其实就一件事：`merge`（合并两个有序数组，线性时间）。分只是手段，合并才是灵魂。

类比：两队人各自按身高排好，你站到队首，每次比两边队首谁矮就让谁先出列——最后必然拼成一队有序的。

---

##### 一、做什么（三步）

```
mergeSort(a):
  1. 分：mid = len/2，切成 a[:mid] 和 a[mid:]
  2. 治：递归排序左右两半（长度 ≤1 时天然有序，直接返回）
  3. 并：merge(left, right) 双指针合并
```

递归树：根节点要求把 n 个元素排序，拆成两个 n/2 的子问题，一直拆到单元素；然后自底向上逐层合并。**“分”不做事，“并”才做事**——这是很多人第一遍学时容易走偏的地方。

---

##### 二、为什么对、为什么快

`merge` 的正确性靠**双指针不变式**：`i`、`j` 分别指向左右两个数组的队首，每次取较小的那个放入结果，被取走的那个指针前移。因为左右内部已有序，所以任何时刻**较小的候选一定在 i 或 j 上**，不会漏。

速度快靠递归树的形状：树高 `log₂n`，每一层的合并总共扫描 n 个元素，所以是 `n × log n`。

---

##### 三、关键实现（Go，展示用，不落盘）

```go
func mergeSort(a []int) []int {
	if len(a) <= 1 {          // 递归出口：0 或 1 个元素天然有序
		return a
	}
	mid := len(a) / 2
	left := mergeSort(a[:mid])
	right := mergeSort(a[mid:])
	return merge(left, right)
}

func merge(l, r []int) []int {
	tmp := make([]int, 0, len(l)+len(r)) // 预分配，避免反复扩容
	i, j := 0, 0
	for i < len(l) && j < len(r) {
		if l[i] <= r[j] {  // 关键：<= 取左边，才能保证稳定
			tmp = append(tmp, l[i])
			i++
		} else {
			tmp = append(tmp, r[j])
			j++
		}
	}
	tmp = append(tmp, l[i:]...) // 谁先走完，另一个剩下的整段追加
	tmp = append(tmp, r[j:]...)
	return tmp
}
```

【逐行理解】`l[i] <= r[j]` 那一行是面试高频追问点：遇到相等时先取左边的，左边元素原本就在前面，这个选择**就是稳定性的全部来源**；改成 `<` 就不稳定了。

【理解】这里每层 `merge` 都新建 `tmp`，写法干净但总分配量是 `O(n log n)`。工程写法是开一个全局 `buf` 数组、用下标 `[l, mid)` `[mid, r)` 原地回填，把峰值压到 `O(n)`；刷题时两种写法都可接受。

---

##### 四、复杂度（n = 数组长度）

| 指标 | 值 | 说明 |
|---|---|---|
| 时间 | `O(n log n)` | 最好、最坏、平均**全一样**，不依赖输入分布（快排的最坏情况是概率风险，归并没有这种风险） |
| 空间 | `O(n)` | 辅助数组；递归栈 `O(log n)` 更小可忽略 |
| 稳定 | 是 | 相等元素相对次序不变 |

推导式：`T(n) = 2T(n/2) + O(n)`，按主定理就是 `O(n log n)`。

---

##### 五、和其他排序的取舍（别只会背表格）

- **插入/冒泡**：`O(n²)`，但小数组（`n ≲ 20`）常数极小，比递归归并快——所以工业级实现（TimSort、Go 的 stable sort）都是「小块用插入排序，大块再归并」。
- **快排**：原地、常数小、缓存友好，工程里更常用；代价是最坏 `O(n²)` + 不稳定，且对已排序输入敏感。
- **堆排**：原地 `O(1)` 空间、最坏也 `O(n log n)`，但访问跳跃、缓存不友好，实测常数大。
- **归并独有价值**：① 稳定；② 顺序访问，天然适合**链表**（链表归并可以做到 `O(1)` 空间，快排做不到）；③ 适合**外排序**（数据大于内存，分块排好再 k 路归并）。

一句话：**要稳定、要链表、要外排 → 归并；要通用快、能接受不稳定 → 快排。**

##### 六、面试会问到什么（按真实度分档）

**【高频变形原题】** 归并的面试价值几乎全在“合并时顺手统计”：
- **数组中的逆序对**（剑指 51 / LC 493 翻转对）：`merge` 里当 `l[i] > r[j]` 时，左数组 `l[i..mid]` **全部**大于 `r[j]`，一次贡献 `mid - i + 1` 个逆序对，`O(n log n)` 秒杀 `O(n²)` 暴力。这是归并最高频的变形，几乎必考。
- **排序链表**（LC 148）：链表归并，快慢指针找中点 + 归并，空间 `O(1)` 或 `O(log n)`。
- **合并 K 个有序链表/数组**（LC 23）：两两分治归并，比每次找最小更简洁。
- **计算右侧小于当前元素的个数**（LC 315）：逆序对 + 记录下标。
- **区间和的个数**（LC 327）：归并统计 + 前缀和。

**【实现层追问】**
- 稳定性怎么来的？→ 上面 `<=` 的取舍。
- 为什么不用原地归并？→ 有 rotate / 手摇算法能做到，但常数大、实现难，面试写出来容易翻车，简单说明“知道有这回事”即可。
- 迭代版（自底向上）会写吗？→ `width = 1, 2, 4...` 两两合并，省掉递归栈，链表场景更常用。
- 递归深度多少、会不会栈溢出？→ `O(log n)`，n 上亿也才 27 层，不是问题。

**【加分拓展】**
- 外部排序：内存装不下时，切块排好写磁盘，再做 **k 路归并**（用堆或败者树选最小），这是大数据“排序”的真实入口。
- Go 冷知识：你平时写的 `sort.Slice` 底层是 **pdqsort**（不稳定快排族），真正稳定的 `sort.SliceStable` 才用插入排序 + `symMerge` 原地归并；Java 的 `Arrays.sort(Object[])` 是 TimSort（归并 + 插入的混合）。
- 稳定性的工程意义：多键排序可以“先按次要键排、再按主要键稳定排”两次搞定，不用写比较函数里的一堆 if。

##### 一、先看整体结构（分解树 + 合并树）

```

  [5,2,8,1]                [9,3,7,4]

[5,2]   [8,1]            [9,3]   [7,4]
 / \     / \              / \     / \
[5][2] [8][1]          [9][3] [7][4]
```

```
并（自底向上，真正干活）
[5][2] [8][1] [9][3] [7][4]
   ↓      ↓      ↓      ↓        ← 第 1 轮：长度 1 → 2
[2,5] [1,8] [3,9] [4,7]
     ↓          ↓               ← 第 2 轮：长度 2 → 4
  [1,2,5,8]  [3,4,7,9]
         ↓                      ← 第 3 轮：长度 4 → 8
  [1,2,3,4,5,7,8,9]
```

**分只做一件事：把问题拆小；并才是排序真正发生的地方。** 总共合并 3 轮（等于 `log₂8`），每轮都扫描全部 8 个元素，所以是 `8 × 3` 次比较量级 —— 这就是 `O(n log n)` 的直观来源。

##### 二、“第一次排序后”到底什么样

**最底层第一次合并 `[5]` 和 `[2]`：**

```
左数组 [5]，右数组 [2]
i=0 指向 5，j=0 指向 2
比 5 和 2 → 2 更小 → 先取 2
左数组已空 → 5 剩下，整体追加

结果：[2, 5]
```

此时**整个数组**的样子是：

```
[2, 5, 8, 1, 9, 3, 7, 4]
 └──┬──┘
  这一段有序了（长度 2），其余还是原样
```

这一点很重要：**归并排序并不是每一轮后“整个数组出现一段有序前缀”**，它只保证“若干个长度为 `w` 的有序段”被凑出来，段和段之间毫无关系。上例中 `[2,5]` 排好了，但 `8` 还可能比 `2` 小（本例恰好不是）。

##### 四、把一次 merge 拆到每一步（最关键的一步）

取第 2 轮里 `[2,5]` 和 `[1,8]` 合并，这是唯一需要动脑的环节：

```
左 [2, 5]        右 [1, 8]       结果 tmp = []
i↑                j↑

比 l[i]=2 和 r[j]=1 → 1 更小 → 取 1，j++      tmp = [1]
比 l[i]=2 和 r[j]=8 → 2 更小 → 取 2，i++      tmp = [1, 2]
比 l[i]=5 和 r[j]=8 → 5 更小 → 取 5，i++      tmp = [1, 2, 5]
i 越界 → 右数组剩下的 [8] 整段追加            tmp = [1, 2, 5, 8]
```

两个观察：
1. **每次只做一次比较，就确定一个元素的最终位置**，所以合并是线性的；
2. 最后“一段走空，另一段整段追加”——这一步很多人忘了写，导致结果少元素。

顺带，`l[i] <= r[j]` 里的 `=` 就是稳定性的来源：相等时优先取左边，左边原本就在前。

##### 五、容易搞混的一点：递归版不是“按轮”执行

上面为了讲清楚，是按“层”从上往下说的（这是**自底向上迭代版**的顺序）。但递归版是**深度优先**，真实执行顺序是：

```
先钻进最左边：[5] [2]  → 合并得 [2,5]
再处理 [8] [1]         → 合并得 [1,8]
再合并 [2,5] 和 [1,8]   → [1,2,5,8]   ← 左半彻底排好才轮到右半
再钻进右半：[9] [3]     → [3,9]
再处理 [7] [4]         → [4,7]
再合并 [3,9] 和 [4,7]   → [3,4,7,9]
最后合并两个大段        → 全部有序
```

**数学上每轮合并的有序段长度翻倍，这个结论在两个版本里都成立**，只是“什么时候轮到哪一段”不同。面试时如果你被问“迭代版怎么写”，写的就是第五节这个“按层”的顺序（`width = 1, 2, 4...` 两两合并）。

##### 一、优化空间：渐进封死，常数还有

**渐进上没有空间了。** 归并是**比较排序**，比较排序的决策树下界是 `Ω(n log n)`，归并已经达到下界，所以不存在"更快的时间复杂度"。想把 `n log n` 打下来只有一条路：**不做比较**（计数/基数/桶排序，`O(n)`），代价是对值域或分布有前提。这是理论上限。

**但工程常数上的优化还有一堆，而且每条都真实影响性能：**

| 优化 | 做法 | 效果 |
|---|---|---|
| 小数组切插入排序 | `len < 16~32` 直接插入排序 | 递归到底层时开销占比最大，收益明显（TimSort/Java/Go 都这么干） |
| 复用辅助数组 | 全局开一个 `buf`，用下标区间回填，不在每层 `make` | 把分配从 `O(n log n)` 降到 `O(n)`，省掉 GC 压力 |
| 合并前判有序 | `a[mid-1] <= a[mid]` 就跳过这次 merge | 对**近乎有序**数据从 `O(n log n)` 掉到接近 `O(n)` |
| 检测有序 run | 找自然升/降序列，反向的翻转再接 | TimSort 的核心，真实数据常有局部有序 |
| 自底向上迭代 | `width = 1,2,4...` 两两合并 | 省递归开销，链表场景更自然 |
| 多路归并 | 一次合并 k 段 | 外排序减少磁盘 I/O；但比较次数变多，是**换 I/O 换 CPU** |
| 并行归并 | 左右子树分给不同核 | 归并天然可并行，这是快排比不了的 |
| 原地归并 | rotate / 对称归并 | 空间降到 `O(1)`，但常数大、实现难，通用排序基本不用 |

**所以"几乎没有优化"这个感觉的来源是**：这些优化都是**常数级**的，不会改变复杂度，面试也不爱问。它们只在工程实现（TimSort、外排、并行库）里重要。

---

##### 二、复杂度：逐条校准

**时间 `O(n log n)` —— 对，而且是"最坏也成立"。** 这一点比快排强：快排的 `O(n log n)` 是**平均**，最坏是 `O(n²)`（极端 pivot 选择 + 已排序输入）。归并不挑输入，`T(n) = 2T(n/2) + O(n)` 恒成立。

**空间，这里要精确一点：**

- 常见写法（辅助数组）→ **`O(n)` 辅助空间** + `O(log n)` 递归栈，取大者 `O(n)`。
- 教材写"快排 `O(1)` 空间"是**忽略了递归栈**的简化说法。快排真实空间是 `O(log n)` 栈（最坏 `O(n)`，尾递归优化后可保 `O(log n)`）。
- 所以你的"空间大一点"要改成：**差的是一个量级，`n` vs `log n`，不是"一点"**。n = 100 万时，归并要 8MB 辅助数组，快排要几十层栈。

**"归并时间更稳定" —— 对，但这个稳定性的实际价值有限。** 快排最坏 `O(n²)` 是**理论风险**，工程上用三数取中、随机化、introsort（快排 + 堆排兜底，`std::sort` 和 Go 的 pdqsort 都是这个思路）就把最坏情况压住了。而快排的**常数更小、缓存更友好**（原地、顺序访问邻近内存），实测通常比归并快。归并要额外开 `n` 大小的数组、来回拷贝，大数组上有明显的内存带宽代价。

**一句话：归并不是"更稳所以更好"，而是"用空间和常数换了最坏保证 + 稳定性"。**

---

##### 三、归并真正的不可替代性

选型时别只比复杂度，归并赢在四个场景：

1. **要稳定**：多键排序（先排次键，再稳定排主键）。
2. **链表排序**：链表上归并可以做到 `O(1)` 额外空间（只改指针），快排做不到。
3. **外部排序**：数据大于内存，分块排好落盘，再 k 路归并——这是大数据排序的真正入口。
4. **可并行 / 可分布**：两半独立，MapReduce 的 merge 阶段本质就是归并。

另外归并还有一个隐藏价值：**它是"合并时顺手统计"的载体**（逆序对、翻转对、右侧小于当前元素个数），这类题只能靠归并的 merge 过程在 `O(n log n)` 里做出来。

**【高频变形原题】**
- 逆序对 / 翻转对 / 右侧小于当前元素个数 / 区间和个数 —— 归并统计四件套，最高频。

**【实现层追问】**
- "归并能优化吗？" → 标准答法：**渐进已到比较排序下界 `Ω(n log n)`，不能再优；常数上有小数组插入排序、复用 buf、跳过已有序段、自底向上迭代**（上面那张表挑 3 条说即可）。

#### 先拆“不如”的含义

“归并一般不如快排”这句话只在**一个维度**上成立：**同样规模的实际运行速度**。比较稳定性和最坏情况保证时，归并反而更强。因此，“不如”是有条件的，不能理解成“归并更差”。

---

##### 一、比实际速度时快排胜出的原因

以下四条按重要性排序：

**1. 快排是原地排序，归并要额外搬运一遍数据（主因）**
快排的分区全程**原地交换**，只在一块内存里挪位置。归并每完成一次 merge，都要把数据**写进临时数组，再拷回原数组**。数据总移动量因此大幅上升，内存带宽和 cache 实际是主要瓶颈，并不在 CPU 的比较操作上。数组一大，这点会直接体现出来。

**2. 访存模式：快排顺序扫描，归并来回跳**
快排分区就是从前往后扫一遍，CPU 的**预取器**工作得很顺（顺序访问、命中 cache line）。归并合并时要在左段、右段、临时数组之间交替读写，三个位置的地址相距很远，cache line 和 TLB 的命中率都差。这也是“分块归并 / cache-oblivious 归并”存在的原因。

**3. 常数差距：内层循环紧凑度**
快排内层只有“比较、交换、指针移动”，非常紧凑；归并的内层要做边界检查、两个索引、往另一个数组写。虽然复杂度相同，但每条指令的开销更多。

**4. 额外内存分配**
如果不复用 `buf`，每层都 `make` 会产生 `O(n log n)` 的分配和 GC 压力（前面的“复用辅助数组”优化就是针对这一点）。

类比：快排像在一张桌子上翻牌，边看边把大数甩到右边，全程不用离桌；归并像把两摞牌**搬到另一张桌子**拼好，再搬回来，拼得整齐，但搬运次数多。

---

##### 二、快排的高速度也有代价

快排并非没有缺点，它的优势是用确定代价换来的：
- **不稳定**：相等元素相对次序会乱。
- **最坏 `O(n²)`**：pivot 选得差就退化（工程上用三数取中、随机化、**introsort** 兜底：递归过深转堆排，`std::sort` 和 Go 的 pdqsort 都是这么做的）。
- **对已排序输入敏感**（没有随机化或三数取中时）。

**工程界的真实取舍最能说明问题**：Java 对**基本类型**用快排（dual-pivot quicksort），对**对象**用 TimSort（归并系）——原因很直白：基本类型不需要稳定性，要速度；对象需要稳定性，牺牲速度换正确语义。

---

##### 三、归并在哪些场景反而占优

1. **数据近乎有序**。TimSort 检测自然有序段 + 跳过已有序段，近乎有序时接近 `O(n)`；快排即使有三数取中，优势也没这么直接。
2. **链表**。链表上归并可以只改指针、`O(1)` 额外空间；快排依赖随机访问，链表上效率很差。
3. **外排序**。数据放不进内存时，只能“分块排序 + 多路归并”，这是唯一可行的方案。
4. **需要稳定**。多键排序（先排次键、再稳定排主键）是标准做法。
5. **需要并行或分布**。左右两半完全独立，可以切开并行处理；分区类快排要处理共享数组，切分麻烦。MapReduce 的 merge 阶段本质就是归并。

---

##### 四、选型速查表

| 场景 | 选择 | 核心理由 |
|---|---|---|
| 通用数组、不要求稳定 | 快排 / introsort / pdqsort | 常数小、原地、缓存友好 |
| 要求稳定 | TimSort / 归并 | 用空间和常数换稳定性 |
| 链表排序 | **归并**（几乎唯一） | 改指针即可，`O(1)` 额外空间 |
| 数据 > 内存（外排） | **多路归并** | 顺序 I/O，可 k 路合并 |
| 内存极受限 / 嵌入式 | 堆排（`O(1)` 空间、最坏 `n log n`）或原地归并 | 空间优先 |
| 近乎有序的数据 | TimSort / 插入排序 | 接近 `O(n)` |
| 整数且值域小 | 计数 / 基数排序 | 不做比较，`O(n)` |
| 需要并行 / 分布式 | **归并** | 天然可切分 |

##### 五、面试会问什么（按真实度分档）

**【高频变形原题】**
- 排序链表（LC 148）→ **只能归并**，这题本身就是“什么时候必须用归并”的答案。
- 逆序对 / 翻转对 → 只能靠归并的 merge 过程统计。

**【实现层追问】**
- “快排为什么比归并快？”→ 标准答法：**原地 + 顺序访存 + 常数小**；归并额外 `n` 空间、两遍拷贝、访存跳跃更多。复杂度相同，故是常数和硬件相关的差异，不是算法优劣。
- “快排最坏 `O(n²)` 怎么办？”→ 随机化 pivot / 三数取中 / **introsort**（递归过深切堆排）。
- “稳定排序有什么用？”→ 多键排序可以“先次键、再主键稳定排”，不必写复杂比较函数。
- “归并空间能降到 `O(1)` 吗？”→ 能，原地归并（对称归并 / rotate），但常数大，通用排序不采用。

**【加分拓展】**
- 标准库现状：C++ `std::sort` = introsort，`std::stable_sort` = 归并；Java 基本类型 = 快排、对象 = TimSort；Go `sort.Slice` = **pdqsort（不稳定）**，`sort.SliceStable` = 插入排序 + `symMerge`（**原地归并**，栈 `O(log n)`，没有 `O(n)` 辅助数组）。
- 外排序的 k 路归并：k 越大磁盘趟数越少，但每步取最小要从 `O(k)` 用堆 / 败者树降到 `O(log k)`。
- 现代 CPU 上“cache 不友好”比“比较次数多”更致命——这是复杂度相同但速度差一截的底层原因。

---

##### 一句话总结

> **快排胜在常数和内存：原地、顺序访存、紧凑内层循环；归并胜在语义和能力：稳定、最坏有保证、链表可做、可外排、可并行。** 所以工程里“默认用快排族，需要稳定性时才换归并族”——Java 和 Go 的标准库就是按这个规则分流的。
