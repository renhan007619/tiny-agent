##### 你说的“源码”是哪一种

这三种源码的价值差得很远：

| 源码 | 讲什么 | 值不值 |
|---|---|---|
| **锁库源码**（redsync） | Redlock 算法、tries/retryDelay 重试、Lua 比对删除 | 【最值】几十个文件、核心逻辑短，是“锁”这件事本身的源码 |
| **客户端库源码**（redigo / go-redis） | 命令编解码、连接池、协议解析 | 【不值】对理解分布式锁零增益 |
| **Redis 服务端源码** | SET NX 在单线程模型下怎么原子 | 【性价比低】有价值但成本极高，大二不必 |

所以关键结论是：**看门狗、红锁这些的实现都在“锁库”里，不在客户端库里。** 你的视频如果是讲 redsync 或类似锁库的源码，那 redigo 出现在代码里只是它的传输层，你完全可以把它当噪音略过——这种情形下你的判断成立，区别不大。

**唯一真正的损失**：如果视频是作者自己手写的一套锁，然后把 redigo 的 `pool.Get()` / `defer Close()` / `reply.(string)` 混在锁逻辑里讲，你容易把“手动连接管理”当成“分布式锁的必要组成部分”记下来。这个损失很小，心里有根弦就免疫了——**任何和连接获取、类型断言相关的代码行，都属于客户端库，不属于锁**。

##### 但“不手写”这件事，我得直说代价

**纯看原理 + 看源码，应对面试是够的**，而且有个隐藏优势：你可以说“redsync 用重试循环而不是 pub/sub 唤醒，这点跟 Redisson 不同”——这种回答比“我写过”更有区分度。

代价在别的地方：**分布式锁的 bug 全是时序型的，看代码时你不会觉得它有问题。** 前面那四个坑——解锁不比对 value、看门狗 goroutine 泄漏、续期失败被吞、惊群——在视频里看起来都是“正常代码”。你看着觉得对，是因为**这段代码在你的阅读经验里没有对应的失败记忆**。真正让你形成“这行有问题”的警觉的，是自己踩一次或者故意写错一次，而不是多读一遍。

##### 最小成本的补法（如果你愿意花一小时）

不是去学库，是做一次**验证理解**：一个 `main.go`，40 行以内——Redis 里一个 key、`SetNX` 加锁、Lua 比对删除、一个后台 goroutine 续期、`Unlock` 时停掉 goroutine。跑通它，你就同时拿到了：

- “看门狗原来就是个 ticker”的实感
- 续期和 Unlock 之间的竞态是什么感觉
- goroutine 泄漏怎么发现（`runtime.NumGoroutine()` 前后打印一下就看见了）

这 40 行不是为了进项目（你的 tiny-agent 用不上锁），是为了**别让面试官一追问“你实现过吗”就露底**。

package main

import (
	"fmt"

	"github.com/gomodule/redigo/redis"
)

// dial wraps DialDefaultServer() with a more suitable function name for examples.
func dial() (redis.Conn, error) {
	return redis.DialDefaultServer()
}

func main() {
	c, err := dial()
	if err != nil {
		fmt.Println(err)
		return
	}
	defer c.Close()

	if \_, err = c.Do("SET", "foo", 1); err != nil {
		fmt.Println(err)
		return
	}
	exists, err := redis.Bool(c.Do("EXISTS", "foo"))
	if err != nil {
		fmt.Println(err)
		return
	}

	fmt.Printf("%#v\\n", exists)
}

**`reply.(int64)` 为什么错**：redigo 的 `Do` 返回的是**按 RESP 协议类型映射后的原始值**——simple string → `string`，integer → `int64`，bulk string → `[]byte`，nil → `nil`。而 `SET ... NX` 成功返回的是 `+OK`（simple string），拿到的是 `string("OK")`，**不是 `int64(1)`**；失败返回 nil。

