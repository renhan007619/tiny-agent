单机锁的机制回顾：
- 单机锁依赖的是进程内/单机内核的共享内存：`sync.Mutex` 靠 CPU 原子指令（CAS/XCHG）+ 操作系统 futex 挂起；`sync.RWMutex`、条件变量同理。
- 它的成立前提：**所有竞争者共享同一块可被原子读写的内存**，且**同一时刻只有一个执行单元在跑临界区**的判定是本地可靠的。
- 单机锁解决的问题：多线程/多协程并发访问同一份内存数据。

分布式锁：
- 竞争者是不同进程、可能不同机器，没有共享内存。只能靠**外部的一个第三方服务**（Redis/etcd/ZooKeeper/DB）来做仲裁。
- 本质变化：从"共享内存 + 原子指令"变成"网络请求 + 远程状态存储"。

核心区别，我觉得可以归纳成几条：

1. **判定依据变了**：本地内存/CPU 原子指令 → 远程存储的原子操作（Redis SET NX、etcd 的 CAS/lease、ZK 的临时顺序节点）。锁的"真相"存在别人的机器上。
2. **不再是"持有即有效"**：单机锁持有着只要不释放就永远持有（除非进程崩了，但那整台机也没了，锁的语义自然失效）。分布式锁持有者可能**还活着但已经失去锁**——网络分区、GC 停顿、Redis 主从切换、租约过期。这是最本质的难点：**锁的有效性不再由持有者自己保证，而由一个会过期的租约保证**。
3. **失败模式从"二元"变成"三分"**：单机锁只有"拿到/没拿到"（加死锁/活锁）。分布式锁还有第三种状态——**不确定**：请求超时了，锁到底加上了没有？我到底还持不持有？网络超时本质是"结果未知"，这在本地锁里不存在。
4. **正确性边界变了**：单机锁的正确性靠语言/OS 保证，你写 `m.Lock()` 就是对的。分布式锁没有任何现成保证，正确性要你自己论证（fencing token、幂等、租约续期）。

难点展开（这是用户问的重点）：

**难点1：互斥的判定要跨网络，原子性靠谁**
- 单机：CPU 提供 CAS，硬件保证。
- 分布式：得找一个**单一权威**。Redis 单实例 SET NX PX 是原子的（Redis 单线程模型保证），但单点。Redlock 想靠多数派，但 Martin Kleppmann 的著名反驳：Redlock 不能防"进程暂停 + 租约过期"这类问题，因为缺乏 fencing token。这是面试高频的争论点。
- ZK/etcd 基于共识（ZAB/Raft），保证线性一致，可靠但性能低、运维重。
- **这里要强调**：锁的正确性不能只靠"加锁成功"这个返回值，必须有 fencing token（单调递增）让被保护资源自己能拒绝过期持有者的写。

**难点2：租约过期 vs 进程暂停（"我以为我还持有锁"）**
- 单机锁没有这个问题：进程 stop-the-world 期间，别的线程也拿不到锁（虽然可能死锁）。
- 分布式：客户端 GC 停顿 / 虚拟机挂起 / 网络延迟，租约过期了，锁被别人拿走，但**持有者毫不知情**，恢复后继续写 —— 双写，互斥被破。
- 对策：watchdog 自动续期（Redisson 的看门狗）、fencing token、把临界区做成幂等。

**难点3：不确定的失败（超时歧义）**
- 加锁请求超时：可能没执行、可能执行了但响应丢了。重试可能重复加锁（如果锁可重入/或实现有 bug）。
- 解锁请求超时：锁没释放 → 死锁（单机锁的死锁在进程内，重启即恢复；分布式锁的死锁可能拖垮整个集群）。
- 这是分布式系统共性问题：**超时不等于失败**。所以解锁要"判身份"（value 存唯一 token，用 Lua 脚本 CAS 删除，避免删掉别人的锁——这个坑必讲）。

**难点4：释放锁的误删**
- `DEL key` 会删掉别人的锁（我超时后其实锁已被别人拿到）。必须 Lua 比较 value 再删。
- 更狠的：即使比对了，Lua 执行前的一瞬间锁也可能过期被别人拿走 —— 所以严谨的删除仍不完备，需要 fencing token 兜底。

**难点5：时钟、续期、原子性**
- 租约依赖本地时钟（Redis TTL 用的是服务器时钟，还好；但 Redlock 依赖各节点本地时钟，对时钟漂移敏感）。
- 看门狗续期本身需要额外连接和线程，续期失败怎么办。

**难点6：可用性 vs 正确性的取舍**
- 单机锁几乎不用考虑可用性（进程在，锁就在；进程没了，锁也无所谓）。
- 分布式锁要选：Redis 主从异步复制 → 主挂了从没同步到这个 key → 两个人同时拿到锁（**互斥被破坏**）。要强一致就只能用 etcd/ZK 或 Redis 多副本 WAIT。这就是 CP vs AP 的取舍。

**难点7：可重入、公平性、阻塞等待**
- 单机锁天然支持阻塞排队、公平/非公平、可重入（记录持有线程）。
- 分布式锁：阻塞要靠轮询或 pub/sub 通知（watch），公平性很难做（ZK 顺序节点能天然做到公平排队，这是它相对 Redis 的优势）。
- 可重入：单机靠线程 ID，分布式要靠"客户端 ID + 请求 ID"，且要考虑同一客户端多线程的情况，需要本地再套一层。

**难点8：性能数量级**
- 单机加锁 ~20ns（无竞争 CAS），有竞争进内核 ~µs。
- 分布式加锁 ~0.1-1ms（同机房 Redis 一个 RTT）甚至更高。差 3-5 个数量级。
- 所以分布式锁绝不能放在热路径上；粒度要粗（否则网络 RTT 把吞吐打死）。这反过来影响架构设计。

**难点9：可观测与排障**
- 锁泄漏、锁竞争严重、谁持有锁——单机可以用 pprof/goroutine dump。分布式要靠监控、trace。

### 🤖 助手

**一句话结论**：单机锁的正确性靠的是“共享内存 + CPU 原子指令”这套本地硬件保证；分布式锁把这套保证换成了“跨网络 + 远程仲裁”，于是原本只需要解决**一个原子性问题**，变成了**四个问题一起解决**：原子性、租约与时钟、网络不确定性、一致性与可用性之间的取舍。

---

##### 一、先看清单机锁为什么成立

把 `sync.Mutex` 拆开，它能工作靠三个隐含前提：

1. **存在一块所有竞争者都能原子读写的内存** —— CAS/XCHG 由 CPU 保证，这是硬件的保证。
2. **“谁持有锁”只有一个权威副本，读到的就是真相** —— 没有网络，没有副本，没有延迟。
3. **持有即有效，直到我主动释放** —— 没有“到期”这个概念，持有多久只取决于临界区多长。

内核 futex、自旋锁、读写锁，只是把“无竞争时留在用户态、有竞争时进内核挂起”做得更省，前提都一样。

##### 二、分布式锁把这些前提逐个打碎了

| 维度 | 单机锁 | 分布式锁 |
|---|---|---|
| 判定依据 | 本地内存 + CPU CAS | 远程存储的原子命令（Redis `SET NX PX`、etcd CAS+lease、ZK 临时顺序节点） |
| 竞争者 | 同进程的线程/协程 | 不同进程、不同机器，彼此看不见 |
| 持有语义 | 持有即有效，直到主动释放 | **租约**，会过期；存在“进程还活着但锁已丢了”的僵尸持有 |
| 失败模式 | 二元：拿到 / 没拿到 | **三元**：拿到 / 没拿到 / **不知道** |
| 成本量级 | 无竞争 ~20ns，有竞争 ~µs | 同机房一个 RTT ~0.1–1ms，差 3~4 个数量级 |
| 正确性由谁保证 | 语言运行时 + OS，你用就对了 | **没有任何保证，得你自己论证** |
| 死锁影响面 | 进程内，重启即恢复 | 集群级，可能拖垮一整条业务线 |

##### 三、难点：按“会让你写错且很难查出来”的顺序排

**1. 租约 vs 进程暂停（最本质的难点）【必记】**
单机锁下，进程被 GC 停顿或虚拟机挂起几分钟，别的线程同样拿不到锁，只是大家卡住，互斥没有被破坏。分布式锁下，客户端卡住 → 租约到期 → 锁被别人拿走 → 客户端醒来后**毫不知情**继续写临界区。**互斥被直接破坏，而且双方都以为自己持锁**。

这就是 Kleppmann 那篇《How to do distributed locking》批判 Redlock 的核心：只要锁是一个自带过期时间的租约，就防不住“客户端暂停”这件事，因为锁服务没有能力判断持有者是死了还是只是变慢了。

**2. 删错别人的锁【必记，最常见的实际 bug】**
`SET NX` 成功后客户端超时了，锁其实加上了；等它重试失败、或者业务兜底逻辑去 `DEL`，可能把已经属于别人的锁删掉。必须用 Lua 做 value 比对再删（value 存每次请求唯一的 token）。但注意：即使这样也不是完备的——Lua 执行前的一瞬间锁到期被抢，仍然会删错。所以最终还是得靠 fencing token 兜底。

**3. 超时的歧义性【必记】**
加锁请求超时 = 没执行 or 执行了但响应丢了。这是分布式系统的通病：**超时不等于失败**。所以加锁必须带幂等语义（token 相同视为同一次），解锁必须能安全重试。单机锁里根本没有这个状态。

**4. 主从切换丢锁（可用性 vs 互斥只能选一个）【面试高频】**
Redis 主从是异步复制：主节点写成功、返回给客户端“锁归你”、然后主挂了，从节点还没同步到这个 key → 提升为主 → 另一个人也拿到了锁。要强互斥就得上 etcd/ZK（Raft/ZAB 共识），或者退化成单点。这是 CP 与 AP 的经典取舍，没有免费方案。

**5. 续期 / 看门狗【实现层追问】**
既然有租约，就得有人续。Redisson 的 watchdog 是后台线程定时把 TTL 续回去。难点在于：续期线程挂了怎么办？续期请求超时但实际成功了怎么办？业务执行时间不可控时，TTL 设多长？

**6. 重入、公平、阻塞等待【加分拓展】**
- 单机锁天然可重入（记录持有线程 ID）、天然阻塞排队、天然公平/非公平可选。
- 分布式锁：重入得靠“客户端 ID + 请求 ID”，且同客户端多线程还要本地再套一层；阻塞得靠轮询或 watch 通知；公平性 Redis 上基本做不到，ZK 的顺序临时节点是唯一能天然公平排队的实现——这是 ZK 相对 Redis 的真实优势，不是“ZK 更重”那么简单。

**7. 粒度和性能倒逼架构【必记】**
单机锁放热路径上几乎无感；分布式锁每个 RTT 都在毫秒级。这意味着**分布式锁的临界区必须粗、数量必须少**，否则网络开销会把吞吐打死。很多“加了锁就变慢”的事故，根因是把分布式锁用出了单机锁的粒度。

##### 四、一个我建议你别顺着主流说法接受的观点

**分布式锁大部分时候是分布式系统设计缺陷的补丁，能不用就别用。** 真正需要“跨机器互斥”的场景远比大家想象的少，常见替代方案：

- 数据库唯一约束 / 乐观锁（version 字段 CAS）—— 把互斥下沉给已经做了事务和一致性的存储
- 按业务键把请求路由到单分区/单实例，把分布式问题降维成单机问题
- 状态机 + 幂等 —— 让“重复执行”无害，比“阻止并发”便宜得多

func (m *Mutex) Lock(ctx context.Context) error {

    backoff := 5 * time.Millisecond

        if err != nil { return err }

}

### 🤖 助手

**先澄清一点**：`go-redis` 官方**没有**分布式锁实现，它是纯客户端。带看门狗的 `Redisson` 是 Java 的。Go 生态里对应的是 `go-redsync/redsync`（Redlock 实现）和 `bsm/redislock`。下面我讲的轮询式实现，就是这两个库的核心思路。

##### 一、思路

用 Redis 的一个 key 当锁位，`SET key token NX PX ttl` **一条命令**完成“不存在才设置 + 设过期”，抢不到就 sleep 重试，解锁用 Lua 比对 token 再删。

本质是：**把“锁状态”寄存在 Redis 的单线程里，用命令级原子性替代 CPU 指令级原子性。**

为什么只能轮询：Redis 没有“等某个 key 变化”的客户端阻塞原语（`BLPOP` 只能等 list 元素），所以客户端唯一能做的是**反复问**。这是它相对 etcd 的天然劣势：等待靠自旋，有网络开销和平均半个重试间隔的延迟。

##### 二、源码

###### 块 1 结构体 + TryLock【逐行理解】

```go
type Mutex struct {
	cli     *redis.Client
	key     string        // 锁位置
	token   string        // 唯一身份，解锁时比对
	ttl     time.Duration // 租约时长
}

func NewMutex(cli *redis.Client, key string, ttl time.Duration) *Mutex {
	b := make([]byte, 16)
	rand.Read(b) // crypto/rand
	return &Mutex{cli: cli, key: key, token: hex.EncodeToString(b), ttl: ttl}
}

func (m *Mutex) TryLock(ctx context.Context) (bool, error) {
	ok, err := m.cli.SetNX(ctx, m.key, m.token, m.ttl).Result()
	return ok, err
}
```

关键：`token` 必须**每次加锁请求唯一**，不能用进程 ID 或机器名——否则同一客户端并发两次加锁，解锁时会误删自己另一次持有的锁。

**一个必须知道的陷阱**：go-redis v9 的 `SetNX` 在 `ttl != 0` 时走 `SET k v PX n NX` 一条命令（安全）；但 `ttl == 0` 时退化成 `SETNX`，**没有过期时间，等于埋死锁**。所以这个 ttl 参数永远不能传 0，或者干脆用 `SetArgs{Mode:"NX", TTL:ttl}` 显式写。

###### 块 2 轮询加锁【逐行理解】

```go
func (m *Mutex) Lock(ctx context.Context, acquireTimeout time.Duration) error {
	deadline := time.Now().Add(acquireTimeout)
	backoff := 5 * time.Millisecond

	for {
		ok, err := m.TryLock(ctx)
		if err != nil {
			return err
		}
		if ok {
			return nil
		}
		if time.Now().After(deadline) {
			return ErrLockTimeout
		}
		select {
		case <-ctx.Done():
			return ctx.Err()
		case <-time.After(backoff + jitter(backoff)):
		}
		if backoff < 200*time.Millisecond {
			backoff *= 2
		}
	}
}
```

三个设计点：

1. **指数退避**：固定 10ms 轮询在锁竞争激烈时会产生大量无效请求（QPS 放大 = N × 1/间隔），退避能把压力降下来。
2. **jitter 抖动**：不加随机会让所有竞争者**同时**醒来抢锁（惊群），加 `[0, backoff)` 随机量错开。
3. **超时 vs ctx**：`acquireTimeout` 是业务级预算，`ctx` 是链路级取消，两个都要检查，否则上游断开后这个 goroutine 还在傻抢。

###### 块 3 解锁【逐行理解】

```go
var unlockScript = redis.NewScript(`
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
`)

func (m *Mutex) Unlock(ctx context.Context) (bool, error) {
	n, err := unlockScript.Run(ctx, m.cli, []string{m.key}, m.token).Int()
	if err != nil {
		return false, err
	}
	return n == 1, nil // false = 锁已过期或已不属于我，当成异常信号上报
}
```

**为什么必须 Lua，而不是先 GET 再 DEL？**
因为 `GET` 和 `DEL` 是两次网络往返，中间窗口足够让锁过期 + 被 B 抢走，然后你 DEL 掉的是 B 的锁。Lua 在 Redis 服务端**原子执行**（单线程跑完整个脚本不切换），这个窗口被彻底消除。

**返回值 `0` 是有信息量的**：说明你解锁时已经不是持有者了（锁过期了）。这是可观测性入口——生产环境应该打点告警，而不是当成正常流程忽略。很多“锁好像没生效”的事故，日志里都躺着一堆被忽略的 `0`。

###### 块 4 看门狗续期【理解】

```go
func (m *Mutex) startWatchdog(ctx context.Context, stop <-chan struct{}) {
	ticker := time.NewTicker(m.ttl / 3)
	defer ticker.Stop()
	for {
		select {
		case <-ticker.C:
			// 续期同样必须比对 token！
			m.renewScript.Run(ctx, m.cli, []string{m.key}, m.token, m.ttl.Milliseconds())
		case <-stop:
			return
		}
	}
}
```

续期脚本和删除脚本结构一样，只是把 `DEL` 换成 `PEXPIRE`。**续期也必须比对 token**——否则你给已经属于别人的锁续了命，帮竞争对手延长持有时间。

`ttl/3` 的用意：在到期前留两次重试机会，避免单次网络抖动就丢锁。

###### 块 5 使用【略读】

```go
m := NewMutex(rdb, "lock:order:123", 10*time.Second)
if err := m.Lock(ctx, 3*time.Second); err != nil {
	return err // 抢锁超时，走降级或快速失败
}
defer m.Unlock(context.WithoutCancel(ctx)) // 注意：别用已取消的 ctx 去解锁
```

`context.WithoutCancel` 是 Go 1.21+ 的细节：业务 ctx 取消后 `defer` 里的 Unlock 如果用原 ctx 会直接失败，锁只能等 TTL 自然过期。

##### 三、这版实现解决了什么、没解决什么

对照前面那 6 个问题：

| 问题 | 这块代码 |
|---|---|
| 复合操作原子性 | ✅ `SET NX PX` 一条命令 + Lua |
| 死锁 | ✅ TTL 兜底 |
| 误删别人的锁 | ✅ token 比对 |
| 业务超时锁到期 | ⚠️ 有看门狗，但续期线程挂了就退化 |
| **僵尸持有（进程暂停但锁已过期）** | ❌ **完全没解决**，必须靠 fencing token |
| **主从异步复制丢锁** | ❌ 单节点 Redis 无解，要么 Redlock 要么 etcd |

**必记的一条**：这份代码的正确性上限就是“**容忍极小概率的互斥失效**”。它适合做幂等去重、任务防重复调度这类场景；但凡涉及金额、库存扣减的严格互斥，光有这把锁不够，必须把 fencing token 落到数据库层（`UPDATE ... WHERE fence < ?`），让存储自己拒绝过期持有者的写。
