##### 一、地图：单机锁的保证是怎么被逐个换掉的

| 单机锁靠什么成立 | 分布式锁换成了 | 由此冒出的新概念 |
|---|---|---|
| CPU 原子指令（硬件保证） | Redis 单线程执行模型 | **“一条命令”是硬约束** |
| 内存共享，读就是真相 | 网络上的一次请求 | 超时歧义、需要自证身份 |
| 没有“到期”，持有即有效 | **租约 TTL** | 续约/看门狗 |
| 只有一份数据 | 主从异步复制 | 主从切换丢锁、Redlock |
| 阻塞靠 OS 的信号量 | 轮询 / watch 通知 | 惊群、Redis QPS |

**这张表就是全篇的骨架**，下面每条都是它的展开。

##### 二、六条前置知识（单机锁里根本没有）

**1. Redis 的原子性来自“单线程”**【必记】
单机锁的原子性来自 CPU 的 CAS 指令。Redis 的原子性是**架构层面**的：只有一条命令在执行，不会被打断。这给你的是**命令级**原子性，不是事务级。理解这一点，后面所有“为什么必须用一条命令 / 为什么必须 Lua”才有根。

**2. “两步之间存在窗口”是分布式锁的头号敌人**【必记，全篇最重要】
- `SETNX k v` 成功 → 客户端崩溃 → `EXPIRE` 没执行 → **锁永不过期，永久死锁**。所以必须 `SET k v EX 30 NX` 一条命令。
- 解锁同理：`GET` 判断身份 + `DEL` 两条命令，中间锁可能过期被别人抢走 → **必须 Lua**。

这跟你学的 CAS 是同一个思想，只是“原子”的提供者从 CPU 换成了 Redis 的单线程。博客只写了“2.6.12 之后 setnx 被弃置”，**没讲为什么**——这就是你感到“有前置知识不知道”的第一个来源。

**3. 过期时间 = 租约，这是单机锁不存在的概念**【必记】
引入 TTL 是为了防死锁（博客 2.3）。代价：**持有者可能在毫不知情的情况下失去锁**。看门狗就是补这个洞的，博客说“不属于本文范畴”。

**4. value 必须是身份 token**【必记】
单机锁里 `mu.Unlock()` 由语言保证只有持有者能调；分布式下解锁就是“往共享存储发一条命令”，**任何人都能发**，所以必须自证身份。这就是博客 1.2 说的“对称性”。

**5. 主从复制是异步的**【面试高频】
博客 2.4 整段是纯分布式系统前置：master 加锁成功、还没同步到 slave 就宕机 → slave 提升为主 → 锁的“凭证”凭空消失 → 独占性破裂。Redlock 就是打这个补丁。

**6. 轮询浪费的东西变了**【理解即可】
单机自旋锁浪费 CPU；分布式轮询浪费的是**网络 IO**。这才是博客 1.4“天平倾向 watch”的真实含义。

##### 三、对着博客代码，按 5 步重建

###### Step 1 加锁：`SET key token EX 30 NX`

博客 `SetNEX` **有两处必须改**：

```go
reply, err := conn.Do("SET", key, value, "EX", expireSeconds, "NX")
if err != nil {
    return -1, nil        // ← 错误被吞了，应该是 return -1, err
}
r, _ := reply.(int64)     // ← 致命：类型断言错
return r, nil
```

**`reply.(int64)` 为什么错**：redigo 的 `Do` 返回的是**按 RESP 协议类型映射后的原始值**——simple string → `string`，integer → `int64`，bulk string → `[]byte`，nil → `nil`。而 `SET ... NX` 成功返回的是 `+OK`（simple string），拿到的是 `string("OK")`，**不是 `int64(1)`**；失败返回 nil。

所以两种情况断言都失败，因为 `r, _ :=` 吞掉了 ok，`r` 恒为 0，上层 `reply != 1` 恒成立——**按这段代码，加锁永远不会成功**。

正确判断（任选）：

```go
// 方式一：认协议类型
ok := reply != nil                      // NX 失败返回 nil
// 方式二：用 redigo 的转换助手
s, err := redis.String(reply, err)
ok := err == nil && s == "OK"
```

这是第 7 条前置知识：**客户端 SDK 的返回值不等于命令语义，等于协议类型**。单机锁里你没有这一层，所以这块不会有直觉。

###### Step 2 身份：`pid_goroutineID` 会撞

```go
token: utils.GetProcessAndGoroutineIDStr()  // "1_18" 这种
```

两个问题：

1. **容器里 PID 常常都是 1**，再加上 goroutine ID 是数字、不同实例很容易撞。**token 撞了 = 能删掉别人的锁，对称性直接破**。
2. goroutine ID 是靠 `runtime.Stack` 解析栈文本“偷”出来的，是社区公认的 hack，Go 官方从不承诺它存在。

正确做法：进程启动时生成一个 UUID 作为实例 ID，再配一个 `atomic` 自增序号，拼成 token。

###### Step 3 解锁：Lua（**博客没贴这段，但这是最核心的一段**）

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

为什么必须脚本：`GET` 和 `DEL` 之间的窗口。注意它**仍不完备**（脚本执行前一刻锁过期被抢，照样删错），真正的兜底是 fencing token——这块前面聊过，不重复。

###### Step 4 等锁：`blockingLock` 的 50ms 固定轮询

逻辑本身对，但有两个问题：

- **固定间隔、无退避、无抖动**。N 个等待者 = 每秒 `N × 20` 次 Redis 请求，且同时醒来 → 惊群。生产上要指数退避 + 随机 jitter。
- 小瑕疵：`for range ticker.C` 意味着**先等 50ms 才第一次尝试**（外层已试过一次，勉强不算浪费）；循环外的 `return nil` 是**死代码**，ticker 永不关闭，永远到不了。

###### Step 5 租约到期：看门狗（博客明确没讲）

一句话补齐：后台 goroutine 每 `TTL/3` 续期一次；**续期前必须 Lua 校验身份**（不然会给别人的锁续命）；`Unlock` 时要停掉 goroutine（否则泄漏）；续期失败要主动放弃临界区，不能装作没发生。

#### 模块 0：go-redis v9 的三条认知基线

这三条和 redigo、和你写单机锁时的直觉都不一样，先立住：

**1. ctx 贯穿一切**。所有方法第一个参数都是 `context.Context`——「等待锁」这件事必须可取消、可超时。这不是语法糖，是**业务请求已经超时了、你这个协程不该继续抢锁**的能力。

**2. 连接池是隐式的**。`SetNX` 内部自己取连接、用完还回去，你完全不碰连接。这消掉了 redigo 那一整层噪音。

**3. 命令返回的是「命令对象 + `.Result()`」，`redis.Nil` 不是错误**。

```go
ok, err := m.rdb.SetNX(ctx, key, token, ttl).Result()
// 第一次用会困惑：
//   失败 ≠ err != nil
//   失败 = (ok == false, err == nil)
v, err := m.rdb.Get(ctx, key).Result()
if errors.Is(err, redis.Nil) {
    // 这是「key 不存在」，是正常业务分支，不是异常
}
```

这一点**极其重要**：分布式锁里「没抢到锁」是最常见的正常结果，如果你按 `err != nil` 判失败，逻辑会全错。这正是上一篇 redigo 代码翻车的地方（用 `reply.(int64)` 判 `1`）。

#### 模块 1：加锁 —— 原子性 + 身份

**做什么**：一条命令同时完成「不存在才写入」+「设置租约」，并把持有者身份写进 value。

**为什么**：
- 为什么必须一条命令：`SETNX` 成功后客户端崩、`EXPIRE` 没发 → **锁永不过期，永久死锁**。
- 为什么 value 要放身份：解锁是“向共享存储发命令”，谁都能发，必须自证。

```go
func (m *Mutex) TryLock(ctx context.Context) (bool, error) {
    return m.rdb.SetNX(ctx, m.key, m.token, m.ttl).Result()
}
```

`SetNX(ctx, key, value, expiration)` 底层发的就是 `SET key value PX <ms> NX`。

**坑（go-redis 特有）**：`expiration` 传 **0 就是不设过期**，锁变成永久的。所以构造锁时必须校验 `ttl > 0`，别让上游传个 0 把系统搞死。

**token 怎么生成**【必记】：

```go
// 错误示范：pid + goroutineID
// 容器里 pid 常常都是 1，两台机器上 1_18 会撞，
// 撞了就能删掉别人的锁
// 正确：实例级 UUID + 递增序号
type Mutex struct {
    instanceID string // 进程启动时 uuid.NewString()
    seq        atomic.Uint64
}
token := fmt.Sprintf("%s:%d", m.instanceID, m.seq.Add(1))
```

#### 模块 2：解锁 —— 对称性

**做什么**：只有 value 还是我的 token 时，才删除。

**为什么**：`Get` 判断 + `Del` 两条命令之间有窗口——判断完之后锁可能过期被别人抢走，你的 `Del` 就删了别人的锁。用 Lua 让这两步在 Redis 单线程里原子执行。

```go
var releaseScript = redis.NewScript(`
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
end
return 0
`)

func (m *Mutex) Unlock(ctx context.Context) error {
    n, err := releaseScript.Run(ctx, m.rdb, []string{m.key}, m.token).Int64()
    if err != nil {
        return err
    }
    if n == 0 {
        return ErrLockNotHeld // 锁已不属于我（过期了）
    }
    return nil
}
```

**为什么用 `redis.NewScript` 而不是直接 `Eval`**【实现层追问】：`NewScript` 会走 `EVALSHA`（只发 40 字节的 SHA1），并在遇到 `NOSCRIPT`（脚本缓存被清）时**自动回退到 `EVAL` 并重新缓存**。直接用 `Eval` 每次都要把整个脚本文本传过去。

**这里必须重复一次（因为太容易忘）**：Lua 比对删除**仍不完备**——脚本执行前一刻锁过期被抢，照样删错。它是“降低概率”，不是“保证正确”。保证正确要靠模块 6。

#### 模块 3：续期 —— 租约的代价

**做什么**：后台 goroutine 每 `ttl/3` 执行一次「校验身份 + 延长 TTL」。

**为什么**：业务耗时不可预知，TTL 是个保守猜测。续期把“猜”变成“动态保证”。同时**续期也必须用 Lua**——否则你会给别人的锁续命。

```go
var extendScript = redis.NewScript(`
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("PEXPIRE", KEYS[1], ARGV[2])
end
return 0
`)

func (m *Mutex) Extend(ctx context.Context) (bool, error) {
    n, err := extendScript.Run(ctx, m.rdb, []string{m.key},
        m.token, m.ttl.Milliseconds()).Int64()
    return n == 1, err
}

func (m *Mutex) startWatchdog() {
    m.stopCh = make(chan struct{})
    go func() {
        ticker := time.NewTicker(m.ttl / 3)
        defer ticker.Stop()
        for {
            select {
            case <-m.stopCh:
                return
            case <-ticker.C:
                ctx, cancel := context.WithTimeout(context.Background(), m.ttl/6)
                ok, err := m.Extend(ctx)
                cancel()
                if err != nil || !ok {
                    m.lost.Store(true) // ← 关键：让业务知道锁没了
                    return
                }
            }
        }
    }()
}
```

**三个坑**【必记】：

1. **续期失败必须让业务感知**。`m.lost.Store(true)` 之后，业务代码在长循环里要定期检查 `m.lost.Load()`，发现了就放弃临界区。很多实现只是 `log.Error` 一下继续跑，等于在“已经没有锁的情况下改数据”。
2. **`Unlock` 必须停掉 goroutine**：`close(m.stopCh)`，否则 goroutine 和 ticker 泄漏。
3. **续期周期 = ttl/3**（Redisson 的约定），留出两次重试余量；不要用 ttl/2，网络抖动一次就断档。

还有一个**反直觉的代价**：看门狗让锁“几乎不会过期”，于是——持有者活着但卡死在业务里，锁会被无限续期，别人永远拿不到。你把“误删别人的锁”换成了“活锁”。所以看门狗的 TTL 要配监控（续期次数异常告警）。

#### 模块 4：等锁 —— 重试策略

**做什么**：拿不到锁时，退避 + 抖动地重试，直到 ctx 结束。

**为什么不能固定 50ms**：N 个等待者 = 每秒 `20N` 次 Redis 请求，而且大家**同时**醒来抢，形成惊群。指数退避把频率降下来，jitter 把“同时”打散。

```go
func (m *Mutex) Lock(ctx context.Context) error {
    backoff := 10 * time.Millisecond
    for {
        ok, err := m.TryLock(ctx)
        if err != nil {
            return err // 网络/脚本错误，不重试
        }
        if ok {
            return nil
        }

        // 全抖动：sleep ∈ [backoff/2, backoff)
        sleep := backoff/2 + time.Duration(rand.Int63n(int64(backoff/2)))
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-time.After(sleep):
        }
        if backoff < 500*time.Millisecond {
            backoff *= 2
        }
    }
}
```

**为什么坚持轮询、不用 pub/sub 唤醒**（前面聊过，这里定性）：pub/sub 是 fire-and-forget，订阅者断连窗口内消息直接丢，**正确性还得靠超时兜底**；Go 生态的事实标准（redsync）就是纯重试循环。所以在够用之前，别上回调。

**如果要加通知**：`m.rdb.Subscribe(ctx, channel)` 拿 `*PubSub`，`pubsub.Channel()` 拿 channel；记住**唤醒后必须回到循环重新 `TryLock`**，不能直接进临界区。

---

#### 模块 5：可重入 —— 先别做

**单机锁天然可重入**（`sync.Mutex` 记录持有者）；分布式锁**默认不可重入**，因为“持有者”是个跨进程的 token。

**最简方案（推荐）**：本地计数，只解决“同一个协程内重复加锁”：

```go
func (m *Mutex) Lock(ctx context.Context) error {
    m.mu.Lock()
    if m.count > 0 { // 我已经持有
        m.count++
        m.mu.Unlock()
        return nil
    }
    m.mu.Unlock()

    if err := m.lockWithRetry(ctx); err != nil {
        return err
    }
    m.mu.Lock(); m.count = 1; m.mu.Unlock()
    return nil
}
```

**跨进程可重入**要用 Hash（field = 实例UUID:协程ID，value = 重入次数），加锁/解锁全得写 Lua，复杂度翻倍。

**判断标准**：你的调用链会不会在持锁状态下再去抢同一把锁？如果答案是“会，而且是不同模块之间”，那就不是重入问题，是**锁粒度设计错了**——先想清楚再决定要不要做可重入。

---

#### 模块 6：fencing token —— 正确性兜底

**做什么**：锁服务发一个单调递增编号，被保护资源自己拒绝“过期持有者”的写。

**为什么**：模块 1~3 的所有努力，都建立在“持有者能及时发现自己失去锁”上。但 GC 停顿、虚拟机挂起、网络分区都会让这个假设失效。**锁会过期，编号不会。**

```go
// 取锁时同时拿一个单调递增的栅栏号
func (m *Mutex) acquireWithFence(ctx context.Context) (int64, bool, error) {
    seq, err := m.rdb.Incr(ctx, m.key+":fence").Result()
    if err != nil {
        return 0, false, err
    }
    ok, err := m.TryLock(ctx)
    return seq, ok, err
}
```

资源侧（比如 MySQL）改成条件更新：

```sql
UPDATE account SET balance = balance - 100, fence = ?
WHERE id = ? AND fence < ?   -- 比见过的最大编号还小，就是过期持有者
```

**【加分拓展】** 这一模块比前面所有模块加起来都值钱——面试时能说清“锁负责发号，资源负责验号”，比会写 Lua 高一个层级。

---

#### 模块 7：边界 —— 主从切换

**为什么丢**：master 上 `SET NX` 成功 → 返回客户端“你持有” → 还没异步复制到 slave → master 宕机 → slave 提升 → 锁的凭证消失 → 两个人同时持有。

**怎么选**（没有免费方案）：

| 你要的 | 用什么 |
|---|---|
| 效率型（避免重复劳动、防缓存击穿） | 单实例 Redis 就够，接受极小概率重复 |
| 正确性型（钱、库存、状态机） | etcd/ZK，或 **fencing token** 让资源侧兜底 |

Redlock 在这个谱系里位置尴尬，前面聊过，不展开。

#### 第 0 节：三条元背景

单机锁能用，是因为你默信了三个前提。分布式锁把这三个**全部抽掉**了，后面的所有问题都是这三条的派生。

##### 前提一：我们共享一块内存

单机：`sync.Mutex` 的 `state` 字段和你要保护的数据在同一块内存里。`Lock()` 返回的那一瞬间，你**已经在临界区里了**，中间零间隙。

分布式：竞争者可能在另一台机器上，你们之间唯一的通道是网络。判定「我持有锁」必须去问第三方（Redis）。**从"问到了"到"我真的在里面"，隔着一个网络往返。**

##### 前提二：调用必达，失败清清楚楚

单机：`mu.Lock()` 要么阻塞等待，要么成功拿到。**没有第三种结果。**

分布式：请求发出去，超时了。它可能是没到、可能是到了但响应丢了。于是你进入一个单机锁里**根本不存在的状态**：**不知道**。

##### 前提三：我现在不动，别人也不动

单机：进程被 GC 停顿，所有线程一起停，锁状态冻结，谁也进不来。

分布式：我这台机器停顿，另一台机器上的竞争者照常跑，TTL 照常流逝。**我醒来时锁可能已经不是我的了，而且没人通知我。**

---

**所以每一个单机锁的机制，都要换一个新的担保人：**

| 单机锁靠谁担保 | 分布式换成谁 | 缺了什么 |
|---|---|---|
| CPU 的 CAS 指令 | Redis 的单线程 + 一条命令 | — |
| 操作系统的地址空间 | 一个远程 KV 存储 | — |
| 进程调度器 | 一个会**超时**的租约 | — |
| 内存屏障（可见性） | **没有对应物** | ⚠️ 缺口 |

最后一行空着，记住它：**分布式锁不提供任何内存可见性保证**。这就是为什么单机锁里不存在的「双写」问题，在分布式里是头号杀手。

#### 第 1 节：加锁 —— 原子性的担保人换人了

##### 做什么

让「检查锁不存在」和「写入我的标识」变成不可分割的一步。

##### 单机锁里这一步靠什么

```go
// sync.Mutex 的加锁核心就一行
atomic.CompareAndSwapInt32(&m.state, 0, mutexLocked)
```

CPU 保证：要么改成功、要么没改，中间别的核心插不进来。**原子性来自硬件。**

##### 分布式下新的担保人是「一条命令」

Redis 是单线程处理的，所以**一条命令执行期间不会被打断**。这就是分布式锁里原子的新来源：**不是硬件，是架构**。

这个认知一旦立住，下面所有"为什么必须这样写"都变成自然推论。

##### 于是第一个问题：为什么必须是一条命令？

如果图省事分两步：

```
① SETNX lock:order abc123     → 返回 1，我拿到锁了
② EXPIRE lock:order 30        → 还没来得及发送
   ↳ 进程被 kill / 网络断 / 机器重启

结果：lock:order 永久存在，永不过期
     → 所有竞争者永远拿不到锁 → 死锁
```

这不是理论风险，是早期 Redis 锁实现普遍踩过的坑。Redis 2.6.12 于是给 SET 加了参数，一条命令同时完成三件事：

```
SET lock:order abc123 PX 30000 NX
     └─ key      └─ 身份   └─ 租约   └─ 不存在才写
```

##### 代码：最小版（模块 1）

```go
type Mutex struct {
    rdb   *redis.Client
    key   string
    token string
    ttl   time.Duration
}

// TryLock 只尝试一次。
// ok=false 且 err=nil 表示「锁被别人占着」——这是正常结果，不是错误。
func (m *Mutex) TryLock(ctx context.Context) (bool, error) {
    if m.ttl <= 0 {
        return false, errors.New("ttl must be > 0")
    }
    return m.rdb.SetNX(ctx, m.key, m.token, m.ttl).Result()
}
```

`SetNX(ctx, key, value, expiration)` 底层发的就是 `SET key value PX <ms> NX`。

##### 三个坑

**坑 1：`expiration` 传 0 = 永不过期**【必记】
go-redis 的 `SetNX` 在 expiration 为 0 时，发的是**不带过期时间**的 `SET NX`。你刚学会的防死锁机制被自己关掉了。所以 `ttl` 必须校验，而且最好在构造函数里校验，不让这行代码有机会被调用。

**坑 2：“没抢到”不是 error**【必记】
`SetNX` 返回 `(false, nil)`。分布式锁里“锁被占着”是最常见的**正常分支**，如果你按 `if err != nil` 判失败，整个逻辑会错到离谱——上一篇博客里 `reply.(int64)` 那个 bug 就是同一类错误的加强版（连成功都判成了失败）。

**坑 3：token 不能省，也不能乱生成**【必记】
- ✗ `os.Getpid()`：容器里一堆实例的 PID 都是 1
- ✗ goroutine ID：跨机器会撞，而且 Go 从不承诺它存在
- ✓ `实例UUID + 递增序号`，全局唯一、可比较

```go
// 进程启动时生成一次
var instanceID = uuid.NewString()
var seq atomic.Uint64

token := fmt.Sprintf("%s:%d", instanceID, seq.Add(1))
```

##### 这一节结束时的状态

你现在有一个**能加、不能解**的锁。加锁靠一条命令解决，很干净。

**下一节你会看到同一个病换了个地方**：解锁看着是"删个 key"，但它其实是「先判断是不是我的，再删」——又是两步，又有窗口。而且这个窗口比加锁那个更隐蔽，因为它不会被时钟触发，只在并发下偶发。

#### 第 0 层：起点

单机锁能用，靠三个默信：**共享内存**、**调用必达**、**我不动别人也不动**。分布式锁把这三条全抽掉，于是你要换三个担保人：

| 单机锁靠谁 | 分布式换成谁 |
|---|---|
| CPU 的 CAS 指令 | Redis 单线程 + 一条命令 |
| 操作系统的地址空间 | 远程 KV 存储 |
| 进程调度器 | **一个会超时的租约** |

注意最后一行——**“租约”是单机锁里完全不存在的概念**。后面 80% 的麻烦都从它长出来。

#### 第一层：让锁“能用”（不打架）

这一层要解决的问题只有一个：**两个客户端不能同时进临界区。**

按顺序你会依次学到四件事，每件都是被前一个问题逼出来的：

**① 加锁必须是一条命令**
因为你一旦分两条（`SETNX` 成功后 `EXPIRE`），中间进程被 kill 就变成永久死锁。所以用 `SET key token PX 30000 NX`，把“不存在才写 + 设租约”焊成一步。

**② value 必须是持有者身份**
因为解锁是“向共享存储发一条命令”，谁都能发。单机锁里 `Unlock()` 由语言保证只有持有者能调，分布式下没有这个保证。

**③ 解锁必须用 Lua**
“先 GET 判断是不是我的、再 DEL”又是两步，又有窗口——跟 ① 是同一个病，只是更隐蔽（不会被时钟触发，只在并发下偶发）。

**④ 拿不到锁要有等待策略**
轮询 + 退避 + 抖动。这里的关键是：单机自旋锁浪费 CPU，分布式轮询浪费的是**网络请求**，所以固定间隔会变成惊群。

到这里你有一个**能工作的锁**。但它有三个层次的缺陷，按“数据有多重要”逐层暴露。

---

#### 第二层：让锁“不死锁，也不早死” → 逼出「TTL」

**问题**：持锁者宕机，永远不解锁。
**方案**：给锁设过期时间（TTL）。

**新问题**：TTL 定多长？
- 定短了：业务还没跑完锁就自动释放 → 别人进来 → **双写**
- 定长了：真宕机时别人要干等很久 → 可用性崩

这就是**看门狗被逼出来的确切位置**。推理很简单：

> 既然一次定不准，那就别定死——**先给一个短租约，谁还在干活谁就自己续。**

##### → 引出「看门狗（watchdog）」

它的完整逻辑包含四件事，缺一不可：

1. 后台 ticker，每 `TTL/3` 续期一次（留两次重试余量）
2. **续期前必须校验身份**——否则你会给别人的锁续命
3. `Unlock` 时必须停掉 ticker，否则 goroutine 泄漏
4. **续期失败必须让业务感知**，否则业务会在“已经没有锁”的状态下继续改数据

##### 看门狗自己带来了三个新问题

- **活锁**：持有者活着但卡死在业务里 → 锁被无限续期 → 别人永远拿不到。你把“误删别人的锁”换成了“别人饿死”。
- **泄漏**：忘停 ticker，进程里 goroutine 越积越多。
- **最关键的那个**：看门狗救不了**进程整体暂停**。

---

#### 第三层：GC 停顿 —— 分布式锁的死穴 → 逼出「fencing token」

这是整条链上最深刻的一步，请你慢慢看：

```
① A 拿到锁，TTL = 30s
② A 触发长时间 GC / 虚拟机挂起 / 网络分区
③ 30s 后锁自动过期，B 拿到锁，开始干活
④ A 醒来 —— 它完全不知道自己已经不是持有者了
⑤ A 继续写数据 → 双写 → 数据坏了
```

**为什么看门狗救不了？** 因为看门狗是 A 进程里的 goroutine，A 被整体停顿时，它一起停了。**你不可能用一个和持有者同生共死的机制，去保护持有者暂停的情况。**

于是你得到一个无法回避的结论：

> **只要锁有“到期”这个概念，就不可能防止僵尸持有者。**

##### → 引出「fencing token（栅栏令牌）」

思路转变：既然锁服务没法判断你是“死了”还是“只是慢了”，那就**别让锁服务承担正确性**，让被保护的数据自己守。

- 取锁时同时领一个**单调递增编号**（1, 2, 3...）
- 写数据时把编号带上
- 存储层（MySQL、文件）记住见过的最大编号，**拒绝更小的编号**

```
A 持锁（编号 33）→ 暂停 → B 持锁（编号 34）→ B 写，存储层记录 34
A 醒来，带 33 去写 → 存储层：33 < 34，拒绝 ✅
```

**记住这句话：锁会过期，编号不会。** 【必记，最高分点】

到这里，“正确性”有答案了。但还有**第三个维度**没碰：锁服务本身也会挂。

---

#### 第四层：锁服务挂了 → 逼出「红锁」

**问题**：Redis 单实例挂了，锁服务整体不可用。
**方案**：主从复制 + 哨兵自动切换。

**新问题**：主从是**异步**复制的。

```
① A 在 master 上 SET NX 成功，master 回「锁归你」
② kv 还没同步到 slave
③ master 宕机
④ slave 提升为新 master —— 它根本不知道这把锁存在
⑤ B 加锁成功 → 两个人都持有 → 独占性破灭
```

注意这一步和第三层的区别，**这是两个不同的问题**：
- 第三层：**持有者**不知道自己失去了锁
- 第四层：**锁服务自己**把锁弄丢了

##### 红锁的想法

既然一个 master 会说谎，那就上 **N 个互相独立的 master，多数派说了算**。

算法（N 通常 = 5）：
1. 客户端生成一个**随机 token**，依次向 5 个节点发 `SET NX PX`
2. 单节点超时**远小于**锁有效期（TTL 10s，单节点超时可能只有 50ms）
3. 同时满足两条才算成功：**≥ 3 个节点成功**，且**总耗时 < TTL**
4. 失败就向所有节点发释放

##### 红锁的问题 → 引出那场著名的争论

Martin Kleppmann 的批判，三条：

**批判一：它依赖时钟。**
“总耗时 < TTL”这个判断，靠的是各节点的本地时钟。可时钟会漂移，进程暂停后客户端以为只过了 1 秒、实际过了 10 秒。**判断本身建立在不可信的假设上。**

**批判二：它完全挡不住第三层那个问题。**
A 拿到 3 个节点的锁，然后 GC 停顿 30 秒。锁全过期，B 拿到，A 醒来继续写。**红锁在这个场景下一无所获**——你把副本从一个加到五个，防的仍然是“节点故障”，不是“客户端暂停”。

**批判三（最狠的一条）：它把两类锁混为一谈。**
- **效率型锁**：只为避免重复劳动，偶尔失效无所谓 → **单点 Redis 就够，根本不需要红锁**
- **正确性型锁**：保护钱、库存 → **红锁不够，需要 fencing token**

结论：**效率型用不上它，正确性型它不管用。**

antirez 的回应是“fencing 是存储层的职责、时钟漂移是可控的”。社区的共识基本站在 Kleppmann 这边：**Redlock 在正确性场景不推荐使用**。

---

#### 终点：一张完整的「问题 → 机制」对照表

| 你发现的问题 | 被逼出来的机制 |
|---|---|
| 加锁是两步，中间有窗口 | `SET NX PX` 一条命令 |
| 解锁是两步，中间有窗口 | Lua 比对删除 |
| 解锁可能删了别人的锁 | value 存 token |
| 抢不到锁怎么办 | 轮询 + 退避 + jitter |
| 持锁者宕机 → 死锁 | **TTL 租约** |
| 业务超 TTL → 锁提前释放 | **看门狗** |
| 续期给别人的锁续命 | 续期前 Lua 校验身份 |
| ticker 不停 → goroutine 泄漏 | `close(stopCh)` |
| 续期失败但业务不知道 | `lost` 标志 + 业务检查 |
| 持有者卡死 → 活锁 | 续期次数监控 |
| **GC 停顿 → 僵尸持有者** | **fencing token** |
| 单实例挂了 | 主从 + 哨兵 |
| 主从异步复制 → 丢锁 | **红锁** |
| 红锁依赖时钟、挡不住暂停 | **绕回 fencing token** |

**最后两行是整条链的眼**：你为了解决可用性上了红锁，结果红锁把你送回第三层的那个洞——而那个洞的唯一出口是 fencing token。

#### 一句话总结整个理论

| 层次 | 要解决的问题 | 手段 |
|---|---|---|
| 能用 | 不打架 | 一条命令 + Lua + token |
| 不出事 | 不卡死 | TTL + 看门狗 |
| 不出错 | 不双写 | **fencing token** |

**红锁是在第二层（可用性）方向上的工程加码，它不在第三层。** 这就是所有混淆的根源——很多人以为“副本越多越安全”，但多副本提高的是**可用性**，反而因为时钟和网络假设引入了新的正确性风险。
