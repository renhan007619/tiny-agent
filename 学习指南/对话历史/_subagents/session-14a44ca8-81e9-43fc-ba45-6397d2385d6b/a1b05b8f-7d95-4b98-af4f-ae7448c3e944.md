搜到了实证材料，你的判断**方向对，但“一般都会”这个词要打个折**。真实情况是分层的，而且分层比“大厂/小厂”更细。

##### 先看支持你判断的证据

**最有说服力的一条**：牛客 4 月的一份面经汇总里，有一场腾讯大模型相关岗的**二面**，20 道题里 13 道是纯 Java 后端底层——Spring IOC/AOP、JDK 与 CGLIB 动态代理、三级缓存解决循环依赖、`volatile`、JMM 工作内存与主存、JVM GC 怎么查、epoll 的 LT/ET、TIME_WAIT/CLOSE_WAIT，真正的 Agent 题目只有 6 道（上下文工程与记忆管理、上下文超限处理等）。也就是说**同一个岗位，一面问 agent、二面换成后端背景的 leader，直接变成后端八股专场**。见 [大模型、Agent面经总结](https://www.nowcoder.com/discuss/878600528970735616)。

**第二条**：一份腾讯「AI 应用开发**后端**实习生」面经，技术栈标的是「Agent、RAG、**后端开发**、DFS、设计模式」，实际考题是「agent 失败/中断如何处理、重试安全吗」「跨境汇款场景下 agent 超时/失败怎么保证资金安全」「RAG 知识库更新怎么不停服」——这些是分布式系统的题，只是换了层 agent 的皮。

**第三条**：阿里云那篇 [AI Agent 全栈开发 65 题](https://developer.aliyun.com/article/1739618) 里，记忆系统的“标准答案”基本就是后端答案：`session_id` 为 key 存 Redis、TTL 30 分钟、长任务每步异步落库、给 session 加**单调递增版本号做乐观锁，避免并发请求覆盖状态**；工具调用章节明确说“重点考察并发、容错”。社区甚至已经有 `ai-agent-interview-240` 这种把「300 道 Agent 真题 + **Java/Python/Go 八股 + 后端面试八股**」打包在一起的仓库了——这种产品存在本身就说明需求是普遍的。

##### 但也有明确的反例

一场 [腾讯 WXG 大模型应用开发岗](https://www.nowcoder.com/discuss/769357001628397568) 面经，全程是：为什么用多智能体、RAG 怎么分片、知识库大小与接口速度、RAG 评估怎么做，加一道 ACM 格式链表题。**零后端八股**。评论区贴的岗位要求也写着：掌握 Python 和 Java 够用，重点是 function call、MCP、LLM 基础、RAG——没提分布式、高并发、中间件。百度的“AI 大模型产品实习生”更干脆，全是产品题。

##### 所以准确的结论

**不是“agent 岗都考后端”，而是 agent 岗落在一个光谱上，看三件事：**

1. **岗位名字里有没有“后端/平台/基础设施”**：有，就按后端标准考；纯“应用开发”，重心在 LLM/RAG/Agent 本身，后端只要“能写”。
2. **面试官背景**：这是最不可控的变量。二面、三面大概率是后端出身的 leader，他们没法深聊 RAG 评估，就问并发、状态一致性、超时重试——**你没得选**。
3. **你自己简历写了什么**：这条对你尤其关键。你 Go 熟、用 Go 写 agent 项目，面试官会天然把你归到“后端候选人”那一档，用后端标准要求你。如果你用 Python 写 agent 应用，反而更容易被问到 LLM 侧。**语言选择会改变提问方向**，这是双刃剑。

##### 给你的落地清单（Go 版本，别照背 Java 那套）

| 必练（agent 项目里真能落地） | 不必深挖 |
|---|---|
| goroutine / GMP / channel / context 取消 | Spring 全家桶、JVM、epoll 八股（那是 Java 岗的） |
| 超时、重试退避、幂等键 | Redlock 争议的深水区 |
| 限流与配额（令牌桶 + Lua） | K8s 调度、Service Mesh |
| 状态外置 + 乐观锁 version check | 复杂分布式事务 |
| 可观测：trace/metrics/日志关联 | |
| Redis 基本用法 + 过期/淘汰语义 | |

注意第 3 行那个「二面 13/20 考后端」是 **Java** 岗。你面试 Go 岗，考的是 Go runtime、GMP 调度、channel 实现、GC、pprof——别照着 JVM/epoll 背，方向会错。

##### 一个提醒

**别把“agent 岗也考后端”理解成“转行做后端”。** 纯后端你打不过科班后端选手；你的差异化是“懂 agent + 能把 agent 当服务运营”。正确做法不是去补一门后端课，而是**拿 tiny-agent 当载体，把并发、超时、幂等、限流、状态外置这些真做一遍**——这样简历上是一条线，不是两张皮。

#### Comparing go-redis vs redigo

| Feature | [go-redisopen in new window](https://github.com/redis/go-redis) | [redigoopen in new window](https://github.com/gomodule/redigo) |
| --- | --- | --- |
| GitHub stars | 15k+ | 9k+ |
| Type-safe | ✔️  | ❌   |
| Connection pooling | Automatic | Manual |
| Custom commands | ✔️  | ✔️  |
| [High-level PubSub API](/guide/go-redis-pubsub.html) | ✔️  | ❌   |
| [Redis Sentinel client](/guide/go-redis-sentinel.html) | ✔️  | Using a plugin |
| [Redis Cluster client](/guide/go-redis-cluster.html) | ✔️  | Using a plugin |
| [Redis Ring](/guide/ring.html) | ✔️  | ❌   |
| [OpenTelemetry instrumentation](/guide/go-redis-monitoring.html) | ✔️  | ❌   |

The main difference between 2 projects is that go-redis provides type-safe API for each Redis command but redigo uses print-like API:

```
// go-redis
timeout := time.Second
_, err := rdb.Set(ctx, "key", "value", timeout).Result()


// redigo
_, err := conn.Do("SET", "key", "value", "EX", 1)
```

That said, go-redis also supports print-like API if you need it:

```
// go-redis print-like API
ok, err := rdb.Do(ctx, "SET" "key", "value", "EX", 1).Bool()
```

Also, go-redis automatically uses connection pooling but redigo requires explicit connection management:

```
// go-redis implicitly uses connection pooling
_, err := rdb.Set(...).Result()

// redigo requires explicit connection management
conn := pool.Get()
_, err := conn.Do(...)
conn.Close()
```

But if you need to manage connections manually, go-redis allows you to do that as well:

```
// go-redis manual connection management
conn := rdb.Conn(ctx)
_, err := conn.Set(...).Result()
conn.Close()
```

**可以学，但要把三层分开：协议层和算法层值得学，redigo 那一层的 API 别花时间记。**

##### 先把三层拆开

| 层 | 具体内容 | 和 redigo 有关吗 | 学不学 |
|---|---|---|---|
| **L1 协议层** | `SET key val NX PX 30000` 的原子语义、Lua 脚本比对 value 再删除、`PEXPIRE` 续期 | 无关，任何客户端都是同一条 Redis 命令 | 【必记】 |
| **L2 算法层** | 看门狗怎么续期、轮询重试的间隔与抖动、可重入计数、fencing token | 无关，属于上层锁库 | 【必记】 |
| **L3 客户端封装层** | `pool.Get()` / `defer conn.Close()` / `reply.(int64)` 类型断言 / 手动连接池 | **redigo 特有** | 跳过，15 分钟翻译一下即可 |

关键结论：**看门狗和主动轮询根本不是 redigo 或 go-redis 提供的**，它们是上层锁库（go-redsync、Redisson）实现的。视频讲这些，你学到的 100% 可迁移。真正会白学的是 L3 —— 判断标准很简单：**看视频里有多少篇幅在跟 `conn.Do(...)` 的变参和类型断言纠缠**。超过一两成，那段快进。

##### redigo 现在的客观位置

go-redis 官方文档有一张[对比表](https://redis.uptrace.dev/guide/go-redis-vs-redigo.html)：类型安全（go-redis ✅ / redigo ❌）、连接池（自动 / 手动）、Cluster、Sentinel、Ring、OpenTelemetry instrumentation（都有 / 都没有或要插件）、stars（15k+ / 9k+）。社区里已经有人在迁出 redigo（例：[confd 的迁移 issue](https://github.com/abtreece/confd/issues/371)）。

其中对你这个场景**最致命的一条是 context**：redigo 的 `Do` 没有 `context.Context`。而分布式锁最需要的能力恰恰是「加锁等待可取消、可设超时」——服务端请求已经超时了，你这个 goroutine 还在阻塞轮询抢锁。go-redis 全链路带 ctx。所以：

- **学**：随便哪个库都行
- **自己项目里用**：必须 go-redis v9

##### 视频里要警惕的四个典型错误实现

这类老教程最容易在这些地方写错，你照着抄就会埋坑：

1. **解锁直接 `DEL`，不比对 value** —— 会删掉别人的锁。必须 Lua 比对。这条上一轮讲过，是老教程翻车第一名。
2. **看门狗 goroutine 泄漏** —— `Unlock()` 后没有 close 掉 stop channel，ticker 还在跑；或者续期时**不检查锁还是不是自己持有的**（value 已经变了还傻续）。这两个是看门狗最常见的 bug。
3. **续期失败被吞掉** —— Redis 报错或超时，代码 `_ =` 忽略，业务继续在临界区里跑，其实锁早没了。续期失败必须主动放弃临界区或终止业务。
4. **重试用固定 `time.Sleep` 无抖动** —— 几百个客户端同时醒来抢锁，形成惊群。要加随机抖动（jitter）+ 指数退避。

##### 更省时间的路径（建议按这个顺序）

1. **先自己用 go-redis 裸写一版**：`SetNX` + Lua 删除 + 后台续期 goroutine，30 行以内。写完之后，任何视频里的代码你都能一眼看穿它在讲哪一层。
2. **再看 `go-redsync` 源码** —— 这个库恰好同时支持 go-redis 和 redigo 两个后端（adapter 分开实现），**锁的核心逻辑完全一致**。这本身就证明了机制与客户端库解耦。视频如果是讲 redsync 源码，那含金量很高，值得看完。
3. 最后对照 Java 的 Redisson 看一层：它的看门狗是「TTL 的 1/3 周期续期」，跟 Go 那套能对上。

##### 附：redigo → go-redis 速查（够你翻译视频代码）

| 操作 | redigo | go-redis v9 |
|---|---|---|
| 取连接 | `conn := pool.Get(); defer conn.Close()` | 不用管，自动池 |
| 加锁 | `conn.Do("SET", k, v, "NX", "PX", ms)` → `reply.(string)` | `rdb.SetNX(ctx, k, v, ttl)` → `(bool, error)` |
| 比对删除 | `script.Do(conn, k, v)` | `redis.NewScript(lua).Run(ctx, rdb, []string{k}, v)` |
| 续期 | `conn.Do("PEXPIRE", k, ms)` | `rdb.PExpire(ctx, k, ms)` |

**一句话**：这个视频用来理解机制和源码没问题，反而因为 redigo 的 `Do` 更「裸」，你能更清楚地看到发出去的到底是哪条 Redis 命令——这其实是优点。但**别把它的连接管理和封装习惯带进自己的项目**，落到 tiny-agent 里一律 go-redis v9 + context。
