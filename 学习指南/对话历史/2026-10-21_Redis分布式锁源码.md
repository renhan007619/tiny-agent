#### 分布式锁

底层场景转换：

*   单机锁：进程和线程之间**共享内存**，锁是内存中一个变量，进程之间共同操作锁。

*   分布式锁：多个物理节点，机器之间，并不共享锁，共同操作锁无法实现。所以利用第三方组件，例如redis或mysql存储锁数据，**跨网络操作锁来实现**。

##### 问题引出：

**1.加锁/解锁原子性丧失**

单机锁：可以利用cpu进行原子性加锁解锁，处理并发安全问题。

分布式锁：加锁需要网络请求，延迟高，不能实现原子性操作。并发危险

***

**2.客户端宕机导致死锁**

单机锁：进程崩溃后**自动释放内存**，锁自动消失，不会出现永久死锁。

分布式锁：某个拥有**锁的组件如果宕机**，没来的及释放锁，锁无法被释放，导致死锁

***

**3.业务时间超时，锁被误删。（归属权）**

单机锁：对于锁的归属权明确，没有超时机制，一直拥有直到主动释放

分布式锁：锁有过期时间（死锁兜底机制，且时间本身是人为预测的不准），如果锁过期业务仍未结束，且此时A组件崩溃重启，中途因为锁过期B拿到锁，**A启动后以为自己持有锁释放，于是把B的锁释放了**。

***

**4.主从机制。异步执行导致锁数据丢失。（弱一致性问题）**

单机锁：无锁单独节点

分布式锁：由如redis这个样的组件管理锁，在主从机制异步场景下，**如果主机持有锁后马上宕机，从节点晋升锁丢失。**

#### 技术选型（主动轮询型）

针对一把分布式锁，redis：将一个kv对插入到存储介质中（需要确保key不是提前存在的），加锁成功。

解锁时，用对应的key值找到数据然后删除掉即可。

如果在插入的时候对应的key值已经存在了，那么则陷入主动轮询机制，重试加锁直到key值被其他组件删除，并由自身完成数据插入。

由于是并发场景，所以【检查key没有存在->尝试插入kv对】需要是**原子化操作**，不可分割。

**除了redis，mysql也可以作为这个存储介质**

利用mysql的**唯一键**（类似redis的key），一旦锁被占有而有另外一方尝试插入数据，会被唯一键报错。

并且并发场景，由mysql事务（innodb引擎）实现原子性加锁。

##### 死锁解决（问题2->问题3）

对于mysql解锁死锁没有啥好办法。

而在redis中可以为了预防某个机器拥有锁的同时宕机，**可以在插入kv对的时候设置一个expire过期时间**。这样就算宕机，也会因为expire到期而自动释放锁。**防止了死锁问题**。

但是这个expire过期时间，其实是根据业务的情况而去人为预测拟定不精准的。**于是这样的方案进一步有需要解决的问题。**

比如当业务方A在过期时间后，仍然在业务中。此时锁已经被释放，另一个业务方b取得锁，而业务a误以为仍然拥有锁，或许对锁进行释放操作时，释放的是b的锁。这样就存在并发安全。

对此，**分布式锁组件redisson给出了看门狗策略**。这个方法可以主动续期锁的时间，防止出现以上情况。解决问题3。

##### 弱一致性问题。（问题4）

由于分布式场景的CAP理论（C：一致性，A：可用性：P：分区容错性），三者只得其二。那么redis选择放弃了强一致性，只实现了弱一致性。走的AP路线。

对于redis，有主节点和从节点。从节点是为了防止主节点宕机流量爆炸，而备用的一个节点在需要时顶替。

每一份数据都会写入主节点和从节点，**但是是异步的先写主节点，再写从节点，两者之间有延迟**。

那么假设一个场景：

1.锁的数据写入主节点，redis拥有锁。

2.下一刻主节点宕机，因为是异步有延迟，锁的数据还没来得及写入从节点。

3.从节点顶替主节点运行，但是锁的数据是丢失的。

4.于是其他组件又抢锁，导致归属权乱套。

对于以上这个问题，**redis红锁机制可以解决**

#### 技术选型（监听回调型）

比如基于etcd这个组件。同样用kv对的形式来加锁，加锁的一方有义务最后解锁删除数据。

与主动轮询型不同的是，一旦一方尝试加锁发现key存在有数据，**他并不会持续轮询，而是会开启一个监听**，监听锁删除事件后再尝试占用锁。

那么etcd是一个分布式kv存储组件，底层基于raft协议实现了高一致性和可用性。etcd实现了watch机制，通过grpc长连接的方式持续监听变更事件。

etcd本身提供锁的**续约机制**解决**死锁问题**，相当于redis中的看门狗，而且通过锁数据写入时的版本revision机制解决惊群效应（避免多个节点争抢锁而浪费资源的情况。）

***

zookeeper，用分布式共识算法zab协议数据强一致性和高可用性。

##### 租约机制

etcd在占有锁的时候有一个截止时间，同时提供一个lease续约机制。

*   用户可以申请一份租约，设定好约定的截止时间
*   异步启动一个续约机制，在业务没完成前的时间点，有节奏的去续约。
*   单独的lease对象，截止时间绑定锁的kv对，保证key和过期时间的一致性。

由于有续约机制，那么在最开始设定这个截止时间时不用那么保守，可以选择一个相对少的时间。

在etcd监听回调型，锁释放后，可能会有多个组件同时收到抢锁的唤醒。从而产生一些锁的归属权不清晰问题。

etcd提供**prefix前缀机制和revision机制**，和zookeeper的临时顺序节点机制有类似。

*   那么在抢锁锁的时候，多个组件都会记录下来，同一把锁的key拥有同一个前缀

*   每个组件把同一个prefix结合自身的身份标识（租约id），组成一个lock key，每个lock key所有有相同前缀和不同后缀，他们**都可以把锁数据记录到etcd中**

*   每个取锁方，插入数据后，根据**先后顺序**获得一个递增的版本号（revision）

*   在插入数据后，没有完全加锁成功，而是需要检查自身的版本号是最低的才加锁成功。否则则监听那个**最接近且小于自身版本**的版本号解锁时间。

```go
func retry(ctx context.Context, strategy RetryStrategy, fn func(context.Context) (bool, error)) error {
	var ticker *time.Ticker
	var done bool
	var err error
	for {
		done, err = fn(ctx)
		if done {
			break
		}

		backoff := strategy.NextBackoff()
		if backoff < 1 {
			break
		}
		if ticker == nil {
			ticker = time.NewTicker(backoff)
			defer ticker.Stop()
		} else {
			ticker.Reset(backoff)
		}
		select {
		case <-ctx.Done():
			...
		case <-ticker.C:
		}
	}
	return err
}
```

##### 先纠一个类比：轮询 ≈ 乐观锁？方向偏了

你博客写“主动轮询↔乐观锁、监听回调↔悲观锁”。这两个维度不是一回事：

| 维度 | 分类 |
|---|---|
| **加锁时机** | 乐观锁（修改时校验版本）、悲观锁（提前占坑） |
| **等待方式** | 主动轮询（polling）、监听回调（notification） |

单机里跟“主动轮询”最贴的是**自旋锁**，跟“监听回调”最贴的是**条件变量 / Monitor**。而乐观锁的真正对应物是 **CAS**——恰好就是 `SET NX` 干的事（“不存在才写入”= 比较后交换）。所以更准的映射是：

- `SET NX PX` ≈ 分布式 CAS（加锁的原子性来源）
- 主动轮询 ≈ 分布式自旋锁（带退避）
- etcd watch ≈ 分布式条件变量

面试时按这个说，比“乐观锁”那套更站得住。

##### 板块 1：加锁 + 主动轮询的源码

###### 1.1 原子性到底从哪来（先看你博客的“问题1”）

【逐行理解】go-redis `SetNX` 的实现（`string_commands.go`）：

```go
func (c cmdable) SetNX(ctx context.Context, key string, value interface{}, expiration time.Duration) *BoolCmd {
	var cmd *BoolCmd
	switch expiration {
	case 0:
		// Use old `SETNX` to support old Redis versions.
		cmd = NewBoolCmd(ctx, "setnx", key, value)
	case KeepTTL:
		cmd = NewBoolCmd(ctx, "set", key, value, "keepttl", "nx")
	default:
		if usePrecise(expiration) {
			cmd = NewBoolCmd(ctx, "set", key, value, "px", formatMs(ctx, expiration), "nx")
		} else {
			cmd = NewBoolCmd(ctx, "set", key, value, "ex", formatSec(ctx, expiration), "nx")
		}
	}
	_ = c(ctx, cmd)
	return cmd
}
```

三个要点：

1. **`expiration > 0` 时发的是 `SET key value PX <ms> NX` 一条命令**，不是“先 SETNX 再 EXPIRE”。Redis 串行执行命令，“判断存在 + 写入 + 设过期”在一次命令内完成，中间不可能插进别的客户端。你博客里“检查 key 不存在→尝试插入必须原子”的答案就在这：**原子性由服务端的单条命令保证，不是靠客户端两次请求拼出来的**。
2. **`expiration == 0` 会退化成老的 `SETNX`**——没有 TTL。这正好把你博客的“问题2（宕机死锁）”又放回来了。所以锁的 TTL 必须 > 0，这是代码强制暴露给你的坑。
3. 返回值是 `BoolCmd`：key 已存在时 Redis 回 nil，go-redis 把它解析成 `false` 而不是 `redis.Nil` 错误。**“锁被别人占着”是正常业务结果，不是 error**——这个设计决定了下面轮询循环的判断分支。

【高频变形原题】“为什么不能先 GET 判断再 SET？”——因为两步之间有窗口，两个客户端能同时 GET 到 nil 然后都 SET 成功。这也是 Redis 官方文档点名 `SET ... NX` 的原因。

###### 1.2 主动轮询的循环（v0.8.0 的 `Obtain`）

【逐行理解】`redislock.go`：

```go
func (c *Client) Obtain(ctx context.Context, key string, ttl time.Duration, opt *Options) (*Lock, error) {
	token, err := c.randomToken()          // ① 归属权凭据
	if err != nil {
		return nil, err
	}
	value := token + opt.getMetadata()
	retry := opt.getRetryStrategy()

	// make sure we don't retry forever
	if _, ok := ctx.Deadline(); !ok {       // ② 没 deadline 就拿 ttl 兜底
		var cancel context.CancelFunc
		ctx, cancel = context.WithDeadline(ctx, time.Now().Add(ttl))
		defer cancel()
	}

	var timer *time.Timer
	for {
		ok, err := c.obtain(ctx, key, value, ttl) // ③ SET NX PX
		if err != nil {
			return nil, err                       // ④ 通信错误 ≠ 锁被占，直接失败
		} else if ok {
			return &Lock{client: c, key: key, value: value}, nil
		}

		backoff := retry.NextBackoff()            // ⑤ 下次等多久
		if backoff < 1 {
			return nil, ErrNotObtained            // ⑥ 0 表示“别等了”
		}

		if timer == nil {
			timer = time.NewTimer(backoff)
			defer timer.Stop()
		} else {
			timer.Reset(backoff)                  // ⑦ 复用 timer
		}

		select {
		case <-ctx.Done():
			return nil, ErrNotObtained            // ⑧ 取消优先
		case <-timer.C:
		}
	}
}
```

拆开讲（每条都值得记）：

- **① 随机 token**：`randomToken()` 用 `crypto/rand` 出 16 字节再 base64。它不是给锁当“名字”，是当**归属权凭据**——解锁/续期时要比对它，防止你博客问题3里“A 释放了 B 的锁”。这里先埋伏笔，下一板块解锁 Lua 全靠它。
- **② ctx 兜底 deadline = ttl**：这行是整个函数最容易被忽略的。`RetryStrategy` 可能是无限退避，调用方又传了 `context.Background()`，那就可能永远轮询下去。作者直接拿 ttl 当“最多等一个锁 TTL”——因为等超过一个 TTL，就算等到了锁也接近过期，没意义。**把“等多久”和“锁活多久”绑在一起，是很有味道的取舍。**
- **④ err 立即返回**：v0.8.0 认为 Redis 通信错误重试无意义。注意 master 版改成了“可重试的瞬时错误”——这是设计观念的变化，后面说。
- **⑤⑥ `backoff < 1` 约定**：`NextBackoff()` 返回 0 就是“停止轮询”。`NoRetry()` 返回 `linearBackoff(0)`，所以默认**只试一次**；`LimitRetry(s, n)` 也是耗尽后返回 0。这个“用 0 当终止信号”的约定很常见，但意味着**策略实现里不能返回 0 表示“立即重试”**。
- **⑦ 复用 `time.Timer` 而不是 `time.Sleep`**：`time.Sleep(backoff)` 期间**无法被 ctx 打断**，哪怕调用方已经超时，你也得睡满。换成 `timer + select ctx.Done()`，取消能立刻生效。这是“可取消的轮询”和“傻等”的分界线。
- **⑧ 取消优先**：`select` 里 `ctx.Done()` 和 `timer.C` 同时就绪时随机选，但语义上这里优先返回取消。老版这里直接返回 `ErrNotObtained`，把真实原因（context deadline exceeded）吞了；master 改成 `errors.Join(err, ctx.Err())` 才修好——**这是能直接抄进你项目的改进**。

【理解】`obtain()` 就一行，`c.client.SetNX(ctx, key, value, ttl).Result()`——轮询的“轮”完全由外层循环驱动，`SetNX` 只负责“试一次”。

###### 1.3 退避策略：轮询的“节奏”在这

【理解】`ExponentialBackoff`（master 与 v0.8 逻辑一致，v0.8 用 `atomic.AddUint64`）：

```go
func (r *exponentialBackoff) NextBackoff() time.Duration {
	cnt := atomic.AddUint64(&r.cnt, 1)

	ms := 2 << 25
	if cnt < 25 {
		ms = 2 << cnt        // cnt=1 -> 4ms, cnt=2 -> 8ms, cnt=3 -> 16ms ...
	}

	if d := time.Duration(ms) * time.Millisecond; d < r.min {
		return r.min
	} else if r.max != 0 && d > r.max {
		return r.max
	} else {
		return d
	}
}
```

- `2 << cnt` 的起点是 **4ms**，不是 1ms；注释里专门写了“想要下界请传 min ≥ 16ms”，因为前几次退避太短，等于没退避。
- `cnt >= 25` 时封顶 `2<<25 ms ≈ 18.6 小时`。所以**一定要配 `LimitRetry` 或 ctx deadline**，否则指数退避会“退”到你怀疑人生（这是 master 注释里写的原话意思）。
- `LimitRetry` 有个版本差异值得注意：v0.8 是先 `atomic.LoadInt64(&r.cnt) >= max` 判断、再 `AddInt64`，两个 goroutine 并发调用时**可能多发一次**；master 改成 `if r.cnt.Add(1) > r.max` 单次原子操作。单机加锁场景通常只有一个 goroutine 调它，所以实际无害，但**策略对象被 `Refresh` 复用**时就暴露了。

【加分拓展】轮询的真正代价：**固定间隔（`LinearBackoff`）响应快，但锁被占期间会持续空转打 Redis；指数退避省资源，但锁释放后你要多等一个退避周期**。主动轮询没有通知机制，只能“猜”别人什么时候释放——这个取舍才是主动轮询 vs etcd watch 的本质差异（你博客后半段那个对比）。Redis 5.0 之后其实可以用 Stream 的阻塞读（`XREAD BLOCK`）做“近似通知”，但不优雅，业界基本不用。

###### 1.4 一句话看版本演进

【略读】master 已经把上面这套重写了：

- 加锁从 `SetNX` 改成 **`obtain.lua` 里的 `MSETNX`**——因为要支持**一次锁多个 key**（`ObtainMulti`），而 `SET NX` 一次只能一个 key，多次 `SET NX` 不原子，必须 Lua。
- 循环抽成 `withRetry`，并把“哪些错误该重试”写成显式契约：`done=true` 停、`done=false & err=nil` 是可重试的“被占”、`done=false & err!=nil` 是可重试的瞬时错误。
- 多了 **fencing token**：每次新获取用 `INCR` 出一个单调递增序号，`Lock.FenceToken()` 返回。这是解决“锁过期后旧持有者还在写”的**存储层兜底**（下游按 token 拒绝旧写），比看门狗更彻底。

**但“轮询”这个模式本身一行没变**：仍然是“试一次 → 失败 → 退避 → 再试 → 直到拿到或放弃”。变的是命令能力和错误语义，不是轮询结构。这也说明：**你博客把“主动轮询”理解成一种模式（而非某条命令）是对的。**

```go
}
```

##### 四、板块 1：原子性（go-redis 源码逐行）

###### 4.1 `SetNX` 到底发了什么命令

【逐行理解】`github.com/redis/go-redis/master/string_commands.go`：

```go
func (c cmdable) SetNX(ctx context.Context, key string, value interface{}, expiration time.Duration) *BoolCmd {
	var cmd *BoolCmd
	switch expiration {
	case 0:
		cmd = NewBoolCmd(ctx, "set", key, value, "nx")          // ← 新版；老版是 "setnx"
	case KeepTTL:
		cmd = NewBoolCmd(ctx, "set", key, value, "keepttl", "nx")
	default:
		if usePrecise(expiration) {
			cmd = NewBoolCmd(ctx, "set", key, value, "px", formatMs(ctx, expiration), "nx")
		} else {
			cmd = NewBoolCmd(ctx, "set", key, value, "ex", formatSec(ctx, expiration), "nx")
		}
	}

	_ = c(ctx, cmd)
	return cmd
}
```

四个知识点：

1. **`expiration > 0` 时只发一条 `SET key value PX <ms> NX`**。“判断 key 不存在 + 写入 + 设置过期”三合一，**原子性来自 Redis 单线程串行执行命令**，不是客户端。你博客“问题1”的答案就在这一个 `switch` 分支里。
2. **`expiration == 0` 时没有 TTL**——不管新旧版都一样。这就是你博客“问题2（宕机死锁）”的复现路径：`SetNX(ctx, key, val, 0)` 一行就能写出一个永久死锁。**代码本身不拦你**，得靠纪律/封装。
3. **`usePrecise`**：判断 `expiration` 是否是整秒。不是整秒就发 `PX`（毫秒），是整秒才发 `EX`（秒）。锁场景基本都走 `PX`。
4. **`KeepTTL`**：`SET key value KEEPTTL NX`——保留原 TTL。给锁做“续期但不改 TTL”时有用，属于冷门分支。

###### 4.2 为什么 `SetNX` 返回 `false` 时不报错（源码级证据）

【逐行理解】`command.go` 的 `BoolCmd.readReply`：

```go
func (cmd *BoolCmd) readReply(rd *proto.Reader) (err error) {
	cmd.val, err = rd.ReadBool()

	// `SET key value NX` returns nil when key already exists. But
	// `SETNX key value` returns bool (0/1). So convert nil to bool.
	if err == Nil {
		cmd.val = false
		err = nil
	}
	return err
}
```

Redis 在 `SET ... NX` 因 key 已存在而失败时，回的是 **nil（RESP2 的 bulk nil）**，理论上 go-redis 会把它当 `redis.Nil` 错误。`BoolCmd` 专门把它**吞成 `false`**，注释直接写了原因。

**这个细节在锁里是好事**：`ok, err := rdb.SetNX(...).Result()` 里，`err != nil` 只代表网络/服务端问题，`ok == false` 才是“锁被占”，轮询分支干干净净。

**但它埋了一个反向陷阱**：如果你不用 `SetNX` 而用 `SetArgs`（`StatusCmd`）或自己 `Eval`，key 已存在时拿到的是 **`redis.Nil` 错误**，不是 false。很多“手写锁”的 bug 就出在这：把 `redis.Nil` 当异常直接 return，锁永远抢不到。

###### 4.3 新版还给了什么（这是你“想讲新版本”的素材）

【理解】master 的 `StringCmdable` 接口里有一批 Redis 8.4+ 的实验性命令：

```go
MSetNX(ctx, values ...interface{}) *BoolCmd
SetIFEQ(ctx, key string, value, matchValue interface{}, expiration time.Duration) *StatusCmd
SetIFNE(...)
SetIFDEQ(ctx, key string, value interface{}, matchDigest uint64, expiration time.Duration) *StatusCmd
DelExArgs(ctx, key string, a DelExArgs) *IntCmd
Digest(ctx, key string) *DigestCmd
```

三个和锁直接相关的：

- **`MSetNX`**：一次给多个 key 原子占坑。`redislock` master 版的 `obtain.lua` 里那句 `redis.call("msetnx", unpack(setArgs))` 就是它——**多资源锁（A 转账要同时锁两个账户）必须靠它，`SET NX` 只能锁一个 key**。
- **`SetIFEQ` / `DelExArgs(IFEQ)`**：Redis 8.4 的 compare-and-set / compare-and-delete。理论上**解锁可以不用 Lua 了**：`DELEX key IFEQ <token>` 一条命令完成“比对 + 删除”。go-redis 注释里明确标了 `NOTE ... still experimental`。
- **`Digest` + `SetIFDEQ`**：用 xxh3 摘要做 CAS，值大时省带宽。

【略读】但**现在别在生产赌这些**：8.4+、实验性、云厂商未必支持。知道“未来解锁可能不需要 Lua”就够了——面试说出来是加分，写进项目是风险。

##### 五、板块 2：主动轮询（go-redis 原语手写版）

go-redis 没有现成轮询，手写出来长这样（这版**故意写成“朴素版”**，方便对照 `redislock`）：

```go
var ErrNotObtained = errors.New("lock: not obtained")

func Lock(ctx context.Context, rdb *redis.Client, key, token string,
	ttl, maxWait time.Duration) error {

	ctx, cancel := context.WithTimeout(ctx, maxWait) // ① 总等待上限
	defer cancel()

	backoff := 4 * time.Millisecond
	for {
		ok, err := rdb.SetNX(ctx, key, token, ttl).Result() // ② 一条 SET NX PX
		if err != nil {
			return err                                  // ③ 通信错误：直接失败
		}
		if ok {
			return nil                                  // ④ 拿到锁
		}

		select {
		case <-ctx.Done():                              // ⑤ 取消优先
			return ErrNotObtained
		case <-time.After(backoff):                     // ⑥ 等下一轮
		}

		backoff *= 2                                    // ⑦ 指数退避
		if backoff > 500*time.Millisecond {
			backoff = 500 * time.Millisecond
		}
	}
}
```

逐点（对照 `redislock` v0.8 的 `Obtain`）：

- **① 总等待上限**：等价于 `redislock` 里“ctx 没 deadline 就用 ttl 兜底”那 5 行。**没有它，一个 `context.Background()` 就能让 goroutine 永远轮询。**
- **② 为什么是 `SetNX` 而不是 `Set NX` 手动拼**：`SetNX` 已经把 `PX` 和 `NX` 拼好了，你拼错顺序（`NX PX` vs `PX NX`）Redis 会直接报语法错误——这是新手第一坑。
- **③ 通信错误不重试**：和 `redislock` v0.8 一致（`if err != nil { return nil, err }`）。master 改成了“瞬时错误可重试”，但那是更复杂的设计，**初学阶段“错就返回”是对的**。
- **⑤⑥⑦ 与 `redislock` 结构完全同构**：`timer + select ctx.Done / timer.C`、`backoff < 1 就停`、指数翻倍。
- **⑥ 这里我用 `time.After` 而不是 `Timer`，是个真实的坑**：循环里每次都 `time.After(backoff)` 会**新建一个 Timer**，前面的没触发就扔在那，高频轮询下 GC 压力明显；而且 ctx 取消后 timer 还活着。`redislock` 用 `time.NewTimer` + `Reset` 复用，就是为了这个。**面试被问“轮询怎么实现”，你主动说“用 Timer.Reset 复用而不是 time.After”就是实现层加分。**
- **缺 jitter**：所有等待者同一个退避节奏，会在同一毫秒一起打 Redis（惊群）。加一行 `backoff += time.Duration(rand.Int63n(int64(backoff/2)))` 就散开了。

对比 `redislock` v0.8 的 `Obtain`：除了多了 `randomToken()`、`Options`、`Lock` 结构体，**循环体逐行等价**。这也回答了你上一个问题：**轮询是“模式”，不是某条命令**；从 `SETNX` → `SET NX PX` → `MSETNX + Lua`，命令换了三代，循环骨架没变一行。

###### 一个必须讲清楚的运行时细节：`Script.Run` 不是一条命令

【理解】`redislock` 的 `Release` 是 `luaRelease.Run(...)`，而 `go-redis/script.go` 的 `Run` 是这样：

```go
func (s *Script) Run(ctx context.Context, c Scripter, keys []string, args ...interface{}) *Cmd {
	r := s.EvalSha(ctx, c, keys, args...)      // 先试 EVALSHA（只传 40 字节 sha1）
	if isNoScriptErr(r.Err()) {                // 服务端脚本缓存里没有
		return s.Eval(ctx, c, keys, args...)   // 回退 EVAL（传整段脚本）
	}
	return r
}
```

含义：

- **第一次解锁是 2 个 RTT**（`EVALSHA` 收到 `NOSCRIPT` → `EVAL`）。之后服务端缓存了这个 sha1，就一直是 1 个 RTT。
- 所以“Lua 脚本很轻”是有前提的：**脚本缓存命中**。Redis 重启 / `SCRIPT FLUSH` / 故障切主后会重新走一遍 2 RTT。
- 想预热可以用 `Script.Load`（`SCRIPT LOAD`）——`redislock` 没这么做，因为它接受第一次的额外开销。
- `isNoScriptErr` 同时认 `NEVER`（`redis.ErrNoScript`）和原始 `NOSCRIPT` 前缀，因为自动 pipelining 路径下错误没被规整过——这是 go-redis 内部的角落，**知道有“两种错误形态”就够了，不用记**。

这个点和你下一个板块（解锁 Lua）是连着的：**Lua 的原子性靠 Redis 单线程执行脚本，但“调用一次 Lua”在网络层可能是两次往返**。这两件事不矛盾，很多人混在一起说错。

### 🤖 助手

**轮询发生在客户端，Redis 自己不会轮询。**

两者属于不同层次：

- **Redis 服务端**：只做“收到一条命令 → 原子执行 → 返回结果”，处理完这条命令就结束，不会替你等锁，也不会通知你锁已释放。
- **go-redis**：命令构造器和网络传输层，负责把 `SetNX` 发出去并解析返回值，不含任何重试逻辑。
- **锁库或你的业务代码**：`for { SetNX; 失败就等待；再试 }` —— 这才是“主动轮询”。

所以“Redis 是主动轮询组件”这个说法把动作的主语弄反了：**Redis 是被轮询的对象**。

关键一点：分布式锁分“主动轮询”和“监听回调”，分类依据是**客户端抢不到锁时怎么等**，与服务端是什么组件无关：

| 等待方式 | 客户端行为 | 谁能做到 |
|---|---|---|
| 主动轮询 | 循环重发 `SET NX` | Redis（只能这样） |
| 监听回调 | 挂一个 watch 长连接等推送 | etcd、ZooKeeper |

为什么 Redis 只能用主动轮询？**它没有可靠的“锁被删除”事件通道**：

- key 过期通知走 pub/sub，会丢消息（客户端断连期间的事件不会补发），不能做锁唤醒；
- Redis 6.0 的 client tracking（RESP3 invalidation）是给客户端缓存用的失效通知，同样会丢，不是业务事件订阅；
- `BLPOP` / `XREAD BLOCK` 能阻塞等待，但那是为队列设计的，不能绑定到任意 key 的生命周期。

所以“Redis 适合做主动轮询式锁”准确的说法是：**Redis 只提供原子原语，客户端只能靠轮询去等，这也正是它不如 etcd watch 的地方**；并且没有现成轮询逻辑，它得自己写。

##### 二、`lockContext`：主动轮询的真正实现

【逐行理解】`mutex.go`：

```go
func (m *Mutex) lockContext(ctx context.Context, tries int) error {
	if ctx == nil {
		ctx = context.Background()
	}

	value, err := m.genValueFunc()          // ① 归属权凭据（随机 base64）
	if err != nil {
		return err
	}

	var timer *time.Timer
	for i := range tries {                  // ② 按"次数"循环
		if i != 0 {                         // ③ 第一次不等待
			if timer == nil {
				timer = time.NewTimer(m.delayFunc(i))
			} else {
				timer.Reset(m.delayFunc(i))
			}

			select {
			case <-ctx.Done():
				timer.Stop()                // ④ 取消时显式 Stop
				return ErrFailed
			case <-timer.C:
			}
		}

		start := time.Now()

		n, err := func() (int, error) {     // ⑤ 一轮尝试 = 所有节点并发
			ctx, cancel := context.WithTimeout(ctx, time.Duration(int64(float64(m.expiry)*m.timeoutFactor)))
			defer cancel()
			return m.actOnPoolsAsync(func(pool redis.Pool) (bool, error) {
				return m.acquire(ctx, pool, value)
			})
		}()

		now := time.Now()
		until := now.Add(m.expiry - now.Sub(start) - time.Duration(int64(float64(m.expiry)*m.driftFactor))) // ⑥
		if n >= m.quorum && now.Before(until) {
			m.value = value
			m.until = until
			return nil
		}
		_, _ = func() (int, error) {        // ⑦ 失败回滚
			ctx, cancel := context.WithTimeout(ctx, time.Duration(int64(float64(m.expiry)*m.timeoutFactor)))
			defer cancel()
			return m.actOnPoolsAsync(func(pool redis.Pool) (bool, error) {
				return m.release(ctx, pool, value)
			})
		}()
		if i == tries-1 && err != nil {     // ⑧
			return err
		}
	}

	return ErrFailed
}
```

七个要点：

**② `for i := range tries`** — Go 1.22+ 的 range over int 语法。`tries` 默认 32，所以 redsync 的轮询是**次数驱动**，不是“等多久”。它和 redislock“退避到 0 就停”正好相反，也决定了 redsync **没有 ctx deadline 兜底**，只能靠调用方传 ctx 或 `WithTries` 限次数。

**③ 第一次不等待** — `TryLockContext` 就是 `lockContext(ctx, 1)`，`LockContext` 是 `lockContext(ctx, m.tries)`。**“试一次”和“轮询”共用同一个循环**，靠 `i != 0` 区分。这个设计比 redislock 的 `NoRetry()` 策略对象更省——不用为“只试一次”单独造一个 `RetryStrategy`。

**④ `timer.Stop()`** — ctx 取消时把 timer 停掉。redislock 那边是 `defer timer.Stop()`（函数返回才停），这里更及时。**两行代码，就是“会不会漏 goroutine 资源”的分界**。

**⑤ `withTimeout(expiry * timeoutFactor)`** — 每轮尝试给一个子 ctx，默认 `8s * 0.05 = 400ms`。含义是：**如果一个节点 400ms 还没回，就不等它了**，这一轮按“这个节点失败”算。没有这一层，一个慢节点能把整轮拖到过期。

**⑥ `until` 的公式** — 这是 Redlock 论文原样翻译：

```
until = now + expiry - 加锁耗时 - drift
```

锁“真正有效到什么时候”不等于 `expiry`，还要减去**加锁花掉的时间**（`now.Sub(start)`）和**时钟漂移**（`driftFactor 0.01`，默认 1%）。**这一步是红锁和单实例锁最本质的区别**——单实例锁（redislock）压根没有 `until` 概念，因为它不考虑“多数派 + 时间窗”。

**⑦ 失败回滚** — 红锁最容易漏的一步：如果 A 节点拿到了、B 节点没拿到，quorum 不够，那 A 上的锁必须删掉。否则就留下一个“幽灵锁”，占着 key 却没人认为自己持有它，直到 TTL 到期。**redislock 单实例没有这个问题，这是红锁独有的复杂度。**

**⑧ 最后一次尝试的错误处理** — 如果最后一轮还带着真实错误（不是“锁被占”），返回那个错误；否则统一 `ErrFailed`。这比 redislock v0.8 的“err 直接 return”更宽容——它允许前几轮出错、后几轮成功。

##### 三、默认退避：redsync 用“随机”，不是“指数”

【理解】`redsync.go` 的 `NewMutex`：

```go
delayFunc: func(tries int) time.Duration {
	return time.Duration(rand.Intn(maxRetryDelayMilliSec-minRetryDelayMilliSec)+minRetryDelayMilliSec) * time.Millisecond
},
// 常量：minRetryDelayMilliSec = 50, maxRetryDelayMilliSec = 250
```

也就是 **每次等 50~250ms 之间的随机值**，且**不随尝试次数增长**（不是指数退避）。

对比两种节奏：

| 策略 | 谁用 | 特点 |
|---|---|---|
| 指数退避 `2<<n ms` | redislock `ExponentialBackoff` | 越等越久，早期快、后期省资源 |
| 固定区间随机 `rand(50,250)ms` | **redsync 默认** | 每次都 50~250ms，**天然防惊群**，最长等待 32×250ms=8s（正好等于默认 expiry） |

注意 redsync 的默认参数是**互相咬合的**：`tries=32`、`delay=50~250ms`、`expiry=8s`。最大轮询时长约 32×150ms ≈ 4.8s，落在 expiry 8s 之内——**不会出现“等得比锁还久”**。这是默认值设计上的一个小心思。

【理解】这几个都可以用 Option 覆盖：`WithTries`、`WithRetryDelay`（固定延迟）、`WithRetryDelayFunc`（自定义，比如你自己写指数退避）。

##### 四、`actOnPoolsAsync`：红锁的“轮询一把”其实是“轮询 N 把”

【理解】`mutex.go`：

```go
func (m *Mutex) actOnPoolsAsync(actFn func(redis.Pool) (bool, error)) (int, error) {
	ch := make(chan result, len(m.pools))
	for node, pool := range m.pools {
		go func(node int, pool redis.Pool) {
			r := result{node: node}
			r.statusOK, r.err = actFn(pool)
			ch <- r
		}(node, pool)
	}
	// ...聚合：n 计数、taken 记录"被占"的节点、err 用 errors.Join 聚合
}
```

- **每轮把所有节点并发打一遍**，成功数 `n` 和 `quorum`（`len(pools)/2+1`）比较。
- `failFast=true` 时：`n >= quorum` 立刻返回（不再等慢节点）；`taken >= quorum` 立刻失败（判定抢不到）。
- 错误分两类：`ErrNodeTaken`（锁被别人占）和 `RedisError`（节点异常），都用 `errors.Join` 攒起来。

代价很直白：**redsync 的一轮轮询成本 = 节点数**。3 节点红锁、32 次重试 = 最多 96 次 `SET NX`。所以红锁不是“更安全的 redislock”，是**用 3 倍成本换一个并不完全的强一致**——这个判断后面 C 板块（红锁争议）再展开。

##### 五、续期：redsync 有 `Extend`，但**不自动**

【理解】`ExtendContext` → `touchScript`（`scripts.go`）：

```lua
-- touchScript
if redis.call("GET", KEYS[1]) == ARGV[1] then
	return redis.call("PEXPIRE", KEYS[1], ARGV[2])
else
	return 0
end
```

- 语义和 redislock 的 `refresh.lua` 一样：**值对得上才续期**。
- 区别：`touchWithSetNXScript`（`WithSetNXOnExtend`）：值对不上时**尝试重新 SET NX**，用于“Redis 频繁重启导致 key 丢了，但业务还想续”的场景。这个选项很偏门，知道有就行。
- **重要**：redsync **没有后台看门狗 goroutine**，`Extend` 要你自己定时调用（`time.Ticker` + 业务结束前停）。很多人以为“用 redsync 就有看门狗”，这是错的理解。
