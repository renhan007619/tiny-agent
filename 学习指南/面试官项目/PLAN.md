# 校招模拟面试官 · 24 天实施计划（压缩版）

> 定位：**一个会记住你盲点、每天告诉你练什么、还会故意施压的 Go 面试教练。**
> 最终形态：**多 Agent 架构**。但起点是单体——理由见第二节。

- 立项：2026-10-29
- 排期：24 个工作日 ≈ 5 周，按 **每天 3-4 小时**（已按"每天多做一点"排满，含 2 天弹性）
- 栈：Go（复用 tiny-agent 底座）+ SQLite + 单页 HTML + OpenAI/Anthropic 兼容 LLM

---

## 一、总体节奏（四阶段，约 95 小时）

| 阶段 | 工作日 | 目标 | 一句话验收 |
|---|---|---|---|
| **A 单体闭环** | D1-D10（41h） | 工作流跑通，能真练、能诊断、能调度 | 打开首页知道今天练什么 |
| **B 语音** | D11-D14（13h） | 说得出、听得见、测得准 | 不打字完成一场面试 |
| **C 多 Agent 拆分** | D15-D20（22h） | 单体拆成 5 个 agent，有对比数据 | 拿出"拆分前后"的延迟/稳定性对比 |
| **D 加固与收尾** | D21-D24（19h） | 抗得住故障，讲得清楚 | 3 分钟演示 + 话术卡 |

**为什么不是一开始就多 agent**：多 agent 的调试成本是单体的 3 倍。边界没被真实数据验证过就拆，拆出来的都是错边界。所以先让单体在真实使用中暴露"哪几块天然独立"，再拆——**拆的是已被验证的边界，不是想象出来的角色**。

## 二、演进路线：单体 → 多 Agent

```
D1-D10   单体                     D15-D20  多 Agent
┌──────────────────┐            ┌─────────────────────────────┐
│  interview 包     │            │      Orchestrator(路由)     │
│  ├ 状态机         │   ===>     │   ├─ Interviewer  实时·轻   │
│  ├ 内联 EVAL      │            │   ├─ Evaluator    异步·重   │
│  ├ 打分/归因      │            │   ├─ Librarian    异步·检索 │
│  ├ 画像/调度      │            │   └─ Coach        离线·调度 │
│  └ 报告           │            │   共享: Event 总线 + 存储   │
└──────────────────┘            └─────────────────────────────┘
```

### 拆分判据（三条同时满足才拆）

| 条件 | 说明 | 反例（别拆） |
|---|---|---|
| ① 上下文该隔离 | 两个角色的 prompt/material 互不污染 | "出题官"和"追问官"——同一份上下文，拆了纯加延迟 |
| ② 延迟可不同 | 一个必须秒回，一个可以跑 10 秒 | 两个都在对话主路径上，拆了反而多一跳 |
| ③ 失败可独立降级 | 挂了不影响主流程 | 评估挂了面试就断，那它不能是真异步 |

按这三条筛，最终拆出 **5 个 agent**：

| Agent | 上下文 | 时序 | 失败影响 | 拆的收益 |
|---|---|---|---|---|
| **Orchestrator** 调度 | 全局事件表 | 实时 | 致命（必须最稳） | 唯一知道全局的，路由逻辑集中 |
| **Interviewer** 面试官 | 简历 + 当前阶段 | 实时 | 致命 | 只带最少上下文 → 输出稳、延迟低 |
| **Evaluator** 评估官 | 单题问答 | 异步 | 可忽略（延后补） | 重模型 + 长 prompt 不拖慢对话 |
| **Librarian** 资料官 | 盲点 + 资料库 | 异步 | 可忽略 | 检索慢不影响面试 |
| **Coach** 教练 | 画像 + SR 状态 | 每日离线 | 可忽略 | 调度不参与对话，根本不该在线 |

### 实现形态：进程内多 Agent（不拆服务）

- 每个 agent = `type XxxAgent struct { llm, prompt }` + `Handle(ctx, Event) ([]Event, error)`
- 总线 = 一个 `chan Event` + `Orchestrator` 路由
- **不拆成多进程/多服务**：边界由 Go interface 定义，不需要网络隔离

> 面试话术：多 agent 的核心是"上下文隔离 + 异步解耦"，不是"进程数"。用 interface + channel 就能拿到全部收益，却不用付序列化、网络、部署的代价。什么时候该拆服务？当某个 agent 需要独立扩缩容时——我这个项目不需要。

### 关键设计：D15 定接口，D16-D18 只搬逻辑

D15 把 `Agent` 接口和 `Event` 模型定下来，**业务逻辑一行不改**。之后每天只是"把已有函数搬进一个实现接口的 struct 里"。这样拆分成本极低，且随时可以退回单体（开关切换）。

### 2.1 工具与提效场景（agent 成色的关键）

**为什么必须有工具**：没有工具调用的项目，面试官第一反应是"这不就是 prompt 链？"。工具是 agent 与非 agent 的分界线之一。

| 工具 | 谁调 / 什么时候调 | 提效点（可量化） | 防滥用 |
|---|---|---|---|
| `read_resume(section)` | Interviewer 准备问某个项目时，只取对应段落 | 简历 3000 字 ≈ 3k token，30 轮全塞 = 90k（直接爆）。按需取每轮 ~300 token，**输入 token 降 80%+** | 同段不重复取（缓存） |
| `search_material(query)` | 你的回答触发新话题、面试官要追深度时 | 62KB 面经不进 prompt；资料更新免重启；能问"你资料里写过 X，刚才怎么没提" | 每轮最多 1 次 |
| `read_history(weak_point)` | 同一盲点第 2 次以上练习，先看历史再开口 | 能说"上次这里失分，这次先问基础"；省人工翻记录 | 只读摘要不读全文 |
| `set_difficulty(level)` | 答得好升压 / 答得差降档 | 压力梯度自动化，不用人手动选 | 每次会话最多 2 次 |

**暂不做的工具**：`lookup_answer`（查标准答案）——会泄题，毁掉面试真实性。

**两个必须提前防的坑**：

1. **工具与 prompt 耦合**（tiny-agent 已踩过，见 `学习指南/项目踩坑/03-工具循环与提示耦合.md`）：加工具不改 system prompt，模型不知道有它，永远不调。每加一个工具必须同步写"触发条件 + 调用方式 + 禁止行为"三条。
2. **工具滥用**：模型可能每句话都查一次，延迟和 token 拉满。必须给**调用预算**（每轮上限、每会话上限），并埋点统计调用次数——面经 #7（工具调用容错）考点。

## 三、tiny-agent 现有代码复用评估

**结论：底座复用约 60%，业务 0%。** 省的是基建（5-7 天），不是闭环。

| 现有文件 | 复用度 | 怎么用 | 面试价值 |
|---|---|---|---|
| `context_assembler.go` | 95% | 整搬 `internal/ctxasm`。30 轮对话 + 简历 + 画像必爆上下文 | ★★★★★ 稀缺能力 |
| `telemetry.go` | 95% | 整搬，每轮延迟、LLM 耗时全靠它 | ★★★★ |
| `agent.go`（LLM 部分） | 60% | 抽 `callModel` + client 初始化；**工具循环不要** | ★★★ |
| `dotenv.go` | 100% | 直接用 | — |
| `memory.go` | 40% | SQLite 连接/CRUD 骨架可用，schema 重做 | ★★★ |
| `resultstore.go` | 10% | 第一版不用 | ★ |
| `tools.go`/`schema.go` | 20% | 工具注册/反射骨架可复用；但面试官的工具走受限单次调用，不走通用循环 | ★★★ |
| `main.go` | 0% | REPL ≠ 状态机，重写 | — |

**为什么工具循环不复用，但工具必须有**：通用工具循环（最多 5 轮）让延迟不可控，面试场景不能接受；但面试官需要 `read_resume` / `search_material` 这类"查一下再问"的能力。所以保留**受限单次工具调用**——每轮最多 1 次，超预算就直接用现有上下文作答。既是 agent 特征，又不牺牲延迟。

### 目录演进

```
tiny-agent/
├── cmd/tinyagent/     现在的 REPL（挪过去，保持能跑）
├── cmd/interview/     面试官入口
└── internal/
    ├── llm/           ← agent.go 抽取
    ├── ctxasm/        ← context_assembler.go 整搬
    ├── store/         ← memory.go 扩展
    ├── telemetry/     ← 整搬
    ├── interview/     ← D1-D14 单体业务
    └── agents/        ← D15+ 多 agent 拆分
```

**保护现场**：D1 第一件事 `git commit`，拆完 `go test ./...` 必须全绿。红了立刻 revert，损失 ≤ 1 小时。

### 阶段 A · 单体闭环（D1-D10，41h）

**D1（4h）· 拆包重构 + 两层信号协议 + 评分 rubric** ⭐地基
- [ ] `git commit` 打底 → 拆 `cmd/` + `internal/` → `go test ./...` 全绿
- [ ] 内联轻信号 `TurnSignal`：只传一个「要不要换话题」的布尔，用词标记**不用 JSON**
- [ ] 事后重信号 `QuestionScore`：score / 四维 / evidence 引用 / weak_points
- [ ] 评分 rubric：从 `学习指南/agent面经.md` 的 must_points + 分档长出来，不凭空编
- [面试-架构] 实时决策与事后评分分层：延迟敏感的和准确敏感的不该在同一层
- [面试-架构] 计算时机 ≠ 呈现时机：算得越早越好，看得越晚越好
- [面试-细节] 一个布尔不值得用 JSON：格式复杂度要与信息量匹配
- [面试-极端] 内联标记没找到 → 默认继续追问，零副作用，不阻塞

**D2（4h）· 五阶段状态机 + CLI 首面**
- [ ] greeting→self_intro→technical→project_deep_dive→reverse_qa
- [ ] 双保险推进：模型判断 + 阶段硬上限 10 题
- [ ] 对话落库 + 终端首次真面
- [面试-架构] 状态机 vs 自由对话：为什么要阶段约束
- [面试-极端] 模型永远说"不推进" → 硬上限兜底，绝不死循环

**D3（4h）· 四维打分 + 诊断报告**

- [ ] 打分失败记「未评分」，绝不填 0
- [面试-架构] 报告是"产物"不是"日志"，它有两个消费者：人和下一轮出题
- [面试-极端] 打分服务挂了 → 面试照常结束，报告标未评分并可重跑

**D4（3h）· Web 单页 + SSE 流式**

- [面试-极端] 用户关页面 → 会话在哪、谁兜底保存

**D5（4h）· 简历/JD 解析（Prep）**

**D6（5h）· 画像两阶段更新 + Interviewer 工具集 v1** ⭐agent 成色
- [ ] Stage1 抽取洞察 → Stage2 LLM 决定 ADD/UPDATE/NOOP
- [ ] 解析失败回退确定性更新
- [ ] 工具 v1：`read_resume(section)` + `search_material(query)`（先用本地文件关键词检索，不上向量库）
- [ ] 受限单次调用：每轮最多 1 次，超预算直接用已有上下文作答
- [ ] system prompt 同步写"触发条件 / 调用方式 / 禁止行为"三条（不加 = 模型永不调用）
- [面试-架构] 无脑 append = 画像膨胀 + 条目重复 + 矛盾并存 = 记忆污染
- [面试-架构] 为什么是受限单次调用而不是通用工具循环：延迟预算决定工具次数
- [面试-极端] 归并失败 → 新条目 + 待复核标记

**D8（3h）· ⭐ 每日任务清单（自用价值拐点）**
- [ ] 今日练什么 = due 弱项 + 新知识点 + 上次失败模式
- [ ] 冷启动策略（新用户无数据）

**D9（4h）· 变式出题 + 掌握度判定**
- [ ] 原题 → 换角度 → 换场景（reps 0/1/2）
- [ ] 三种变式全过 = 掌握

**D10（4h）· 失败模式归因（五类病）**
- [ ] 知识空白 / 结构缺失 / 无量化 / 扛不住追问 / 高压失稳

- [面试-架构] 诊断 > 评分：评分说"差"，诊断说"往哪改"
- [面试-极端] 一句话命中多类 → 用规则定主次，别让 LLM 自由发挥

### 阶段 C · 多 Agent 拆分（D15-D20，22h）

**D15（4h）· Event 模型 + Agent 接口 + 总线** ⭐架构分水岭
- [ ] `Event{Type, SessionID, Payload}` + `Agent` interface
- [ ] 进程内 `chan Event` 总线 + 订阅关系
- [ ] 现有单体逻辑挂成"一个 agent 实现"，先跑通不报错
- [面试-架构] 为什么先定接口再拆：接口是边界契约，先有契约才敢搬逻辑
- [面试-细节] 进程内总线 vs 消息队列：这个规模不值得 MQ

**D16（4h）· 拆 Evaluator（第一个拆，验证收益）**
- [ ] 评估从主流程移到异步 goroutine
- [ ] 结果回写通过事件，不阻塞对话
- [ ] 埋点：拆分前后每轮延迟对比
- [面试-架构] 异步化的前提是"失败可延后补偿"，不是"先扔出去"
- [面试-极端] 评估挂了 → 会话仍继续，事后补跑

**D17（4h）· 拆 Librarian（资料库接入 + 工具集 v2）**
- [ ] 导入 `学习指南/agent面经.md` 等资料 → 切片 → 索引（关键词 + 标签，先不上向量）
- [ ] 盲点 → 检索相关段落 → 注入下次训练
- [ ] 工具 v2：`read_history(weak_point)` + `search_material` 升级为走资料库
- [面试-架构] 不做独立"资料库页面"，做成"盲点的补充材料"——否则和闭环两张皮
- [面试-架构] 工具为什么从"本地关键词"升级到"资料库检索"：数据从 1 个文件变 N 个文件，检索策略必须跟着变
- [面试-极端] 检索无结果 → 明确标注"无材料"，不许编
- [面试-极端] 资料库文件被删/改名 → 索引失效要能自愈重建

**D18（4h）· 拆 Coach + Orchestrator 路由**
- [ ] Coach：每日任务生成（原 D8 逻辑搬过来）
- [ ] Orchestrator：根据事件类型路由到对应 agent
- [面试-架构] 编排器只做路由，不做业务：否则它会长成上帝对象

**D19（3h）· 对比实验：单体 vs 多 Agent** ⭐面试王牌

- [ ] 结论写进文档（含"多 agent 哪里没收益"）
- [面试-架构] 拆分要有数据支撑，否则只是"看起来高级"

**D20（3h）· 多 Agent 架构文档 + 图**
- [ ] 事件流图、上下文隔离图、失败降级图

### 阶段 D · 加固与收尾（D21-D24，19h）

**D21（4h）· 超时 / 重试 / 熔断 / 降级**
- [ ] 每层独立超时；重试防放大
- [面试-极端] 上游 3s 超时 × 下游重试 3 次 = 9s 雪崩
- [面试-架构] 降级决策：先保闭环，再保质量

**D22（4h）· 压力梯度 + 抗压性指标**
- [ ] 三档：追问深度(2/3/4) / 时间预算(不限/120s/90s) / 否定反馈(无/中性/直接)
- [ ] 同题三档分差 = 抗压性

## 七、砍掉清单

## 八、风险与对冲

| 风险 | 表现 | 对冲 |
|---|---|---|
| 排太满崩盘 | 一天没做完 → 全盘推迟 → 摆烂 | 阶段间留弹性；**周排期可滑，D10 闭环不可滑** |
| 想加功能 | "再加个面经爬虫" | 砍掉清单贴首页 |
| LLM 抖动 | 同一回答 4 分和 7 分 | D3 就上规则层，别硬调 prompt |
| 拆包改坏现有代码 | tiny-agent 跑不起来 | 先 commit，`go test ./...` 验收，红就 revert |
| 多 agent 拆过头 | 延迟反而变差 | D19 对比实验，没收益就退回单体（开关切换） |
| 语音卡住 | ASR 三天没通 | 语音整段可后移，闭环不依赖它 |

**最硬一条**：D10 结束闭环没跑通，停止排后续——所有功能都长在闭环上。

## 九、面试话术储备（随进度补）

| 场景 | 一句话答案 |
|---|---|
| 解决什么问题 | 面试的问题不是"没题练"，是"不知道弱在哪、练了没进步"。我做的是诊断 + 调度系统。 |
| 和市面工具有什么不同 | 多数是练完就结束的聊天工具。我抄了 TechSpar 的记忆闭环，加了失败模式归因和双层评分。 |
| 算 agent 项目吗 | 第一版不是，是工作流。但我做了受控自主：模型决定是否推进阶段，硬上限 10 题兜底。第三阶段拆成多 agent 后，自主性体现在路由和并行决策上。 |
| 为什么要拆多 agent | 因为三条判据：上下文该隔离、延迟可不同、失败可独立降级。拆之前量过数据（D19）。 |
| 为什么不用微服务/MQ | 边界用 interface 定义就够了，进程内 channel 拿到同样收益，不用付网络和序列化的代价。 |
| 最难的部分 | 不是写功能，是让 LLM 判断可靠——所以把"判断"换成"取证 + 规则"，可复现、可回归。 |
| 怎么证明有用 | 弱点收敛：某盲点 4 周内是否从高频出现变成不再出现。 |
