## 一、Go 技术点 → 落点

### A 档：真必需（不做功能不成立）

| 技术点 | 落在哪个位置 | 干什么 | 能讲的点 |
|---|---|---|---|
| **goroutine** | 语音流水线、打分 worker、SSE 写回、定时任务 | 让几段活同时跑 | goroutine 便宜（初始栈小），贵的不是它，是外部并发名额 |
| **channel** | ① 音频流→转写的传递 ② 打分任务队列（带缓冲，满了不阻塞主链路）③ agent 之间的命令/事件传递 | 流水线的传输带 | 缓冲大小怎么定；满了该丢还是该等；关闭与广播 |
| **select** | 跳时间上限、用户取消、多路同时到达 | 等待里挑先来的那个 | 超时/取消/默认分支三种用法 |
| **context** | 关页面→停后台打分；每段时间上限；进程退出 | 一层层通知「这事不用做了」 | 取消是向下传播的；不要把 context 塞进结构体 |
| **sync**（Mutex/RWMutex/WaitGroup） | 会话状态读写、弱点表更新 | 防止两边同时改同一份数据 | 并发读写 map 是 fatal error，recover 不了 |
| **map** | 会话表（会话 ID→状态）、进行中的任务表 | 按 ID 找状态 | 量小但会真撞上并发写；扩容与渐进式迁移 |
| **interface** | Agent 接口（面试官/打分员/教练）、Store 接口（SQLite/MySQL）、模型客户端接口 | 定义边界，换实现不改调用方 | 多 agent 拆分的前提就是先把接口立住 |
| **net/http** | HTTP 服务、SSE 流式输出、长连接 | 把字一个个吐给浏览器 | Flusher、写超时、断连检测 |
| **database/sql** | 会话/题目/分数/弱点落库 | 存东西 | 连接池上限、事务、把 context 传进查询 |
| **错误处理** | 每一跳失败要能分类 | 可重试 / 不可重试 / 该降级 | 失败不许伪造成正常值（打分失败≠0 分） |
| **优雅退出** | 收到停止信号时 | 先把排队中的打分跑完再退出 | 退出顺序：停止接新活 → 跑完存量 → 关闭资源 |

### B 档：能做，练手价值大于系统收益

| 技术点 | 落点 | 说明 |
|---|---|---|
| **gin** | 接口层路由 | 省事，但 SSE 那条路手写原生更强 |
| **MySQL 双实现** | Store 接口的第二个实现 | 本地 SQLite，线上 MySQL（腾讯云已有） |
| **pprof** | 一场面试后找慢在哪 | 便宜，且能讲「我怎么定位瓶颈」 |
| **GMP 调度** | 用来解释、不用来改代码 | IO 密集，goroutine 大部分在等网络，调 GOMAXPROCS 没意义 |
| **信号处理** | Ctrl+C 时收尾 | 和优雅退出是同一件事 |
| **表驱动测试** | 状态机不死循环、打分解析容错 | 可靠性讨论的底气 |

### C 档：没有真实落点，别硬塞

| 技术点 | 为什么 |
|---|---|
| **GC 调优** | 自用工具堆压力约等于零，讲调优会很假。只做一件事：看几处逃逸，结论是「不需要调」 |
| **GORM** | 把 SQL 藏起来，面试官问「这条走索引了吗」就哑。查询就那么几条，手写更值 |
| **MQ（RabbitMQ/Kafka）** | 本地自用，收益全是负的，还得部署中间件。队列语义用「channel + 任务表」全拿到 |

## 二、Redis 落点

**前提结论**：单进程自用，下面五件用内存或 SQLite 都能做。Redis 的真实收益只有三条——**进程重启不丢、将来多进程能共享、练手**。属于 B 类设计，加的时候心里要清楚。

| # | 落点 | 用什么结构 | 干什么 | 顺带能讲 |
|---|---|---|---|---|
| 1 | **复习队列** | ZSET（分数 = 下次复习的时间戳） | 取「今天到期的弱点」一条命令捞出来，最难的排在前面 | **底层是跳表**，范围查询 O(logN)；已做过跳表实现，正好接上 |
| 2 | **面试现场** | Hash + 过期时间 | 当前阶段、已问题目、可疑点存进去；重启能接着面，关浏览器再开也接得上 | 过期时间的取值依据；序列化格式与兼容 |
| 3 | **打分任务的身份证** | `SET NX EX` | 同一任务只许一个 worker 干；干完删掉；worker 中途挂了，身份证到期自动失效，任务被别人重新领走 | **分布式锁的正确用法**：防重复劳动 + 防卡死；锁过期时间怎么定 |
| 4 | **工具查询缓存** | String + 过期时间 | 面试官查简历第 2 段、查面经追问链，查过就缓存；20 个请求同时来只穿一次库 | 缓存穿透 / 击穿 / 雪崩，有真实含义不是背书 |
| 5 | **模型调用限流** | `INCR` + 过期 | 每分钟最多调 N 次，超了排队等，别把接口打爆 | 固定窗口 vs 滑动窗口 vs 令牌桶 |

### 加了 Redis 之后多出的两件必做事

**① Redis 挂了不能把面试搞废。**
面试中途 Redis 连不上、会话取不到，整场就白坐了。必须有兜底：不可用时退回进程内存（单机照跑）或退回 SQLite。
→ 面试点：**缓存/状态服务挂掉不影响主流程**。

**② 本地环境怎么跑。**
Windows 上 Redis 官方不支持，得用 Docker、WSL，或直接跑在腾讯云 1.15.224.88 上。这个选择会影响整个开发环境，早定。

## 三、看不见的地基：context / interface / sync / 错误分类

这四样不在「Go 要学的清单」里，但没有它们，上面所有功能都会烂在半路。**它们的特点是：做对了没人看见，做错了全都崩。**

### ① context —— 一层层通知「这事不用做了」

| 场景 | 没有它会怎样 | 有了之后 |
|---|---|---|
| 你关掉浏览器 | 后台还在傻乎乎调模型、烧 token | 请求一断，整条链收到「别做了」，立刻停 |
| 语音转写卡住 | 面试官的下一句永远等不到 | 5 秒没结果，先拿上一段顶上继续 |
| 模型 10 秒没回 | 用户干等到天荒地老 | 超时就走降级话术 |
| 进程退出 | 正在打的半分全丢 | 收信号后先通知所有子任务收工 |

**必记点：context 的取消是向下传播的**——上层取消，下层全部收到。所以每一跳的耗时都必须挂在同一个 context 链上，否则取消不了。
**别做的事**：把 context 存进结构体字段（Go 官方明确反对），要当参数一路传。

### ② interface —— 边界先立住，才敢搬逻辑

三个接口，缺一个都难受：

```
Agent    面试官 / 打分员 / 教练 都实现它 → 这才能把单体拆成多 agent
Store    会话/分数/弱点存取       → 本地 SQLite 和线上 MySQL 才能换着跑
LLM      调模型                   → 换模型、换供应商、加打点，不改业务代码
```

**必记点：先定接口，再搬逻辑。** 反过来（先写散装函数再抽象）就是重写。
这也是「多 agent 拆分成本低」的唯一前提——拆分那天只是把已有函数塞进一个实现接口的 struct 里。

### ③ sync —— 防止两边同时改同一份数据

这个项目里有两处必撞：
- **面试主链路在写**会话状态，**打分 worker 同时在读** → 不加锁就是数据竞争
- **多个 worker 同时更新**同一个弱点条目（TechSpar 就没防这个） → 后写的覆盖先写的

**必记点：并发读写 map 是 fatal error，recover 不了**，整个进程直接挂。所以要么加锁，要么串行化（把更新丢进一个队列，单 goroutine 消费）。
**能讲的取舍**：RWMutex（读多写少）vs 串行队列（更新逻辑复杂、要保序）——这个项目两种都会用到。

### ④ 错误分类 —— 失败不许伪造成正常值

每一跳失败，要分成三类，分别有不同处理：

| 类别 | 例子 | 怎么办 |
|---|---|---|
| **可重试** | 网络抖动、429 限流 | 退避重试，有上限 |
| **不可重试** | 参数错、模型返回格式烂且解析不出 | 直接标记失败，不重试 |
| **该降级** | 转写挂了、检索无结果 | 用兜底继续，功能降级不中断 |

**必记点：打分失败 ≠ 0 分。** 0 分是有效数据，会进弱点统计和复习排期；把失败写成 0 分，等于往数据库里注入一条假事实，一个月后分不清哪道是真 0 分、哪道是系统挂了。**静默失败是最大的敌人。**

## 四、会话记忆设计（面试过程中的记忆）

会话记忆和长期记忆是两件事，别混：

| | 会话记忆（这场面试内） | 长期记忆（跨场次） |
|---|---|---|
| 活多久 | 一场面试，结束就没 | 永久 |
| 存什么 | 问过什么、你答过什么、哪里可疑 | 弱点、掌握度、复习排期 |
| 存哪 | 内存 + Redis | SQLite |
| 谁用 | 面试官（决定下一句问什么） | 教练（决定今天练什么） |

### 4.1 先定效果（这些做到了才算「弄好」）

1. 追问问的是你**刚说的那句话**，不是「你之前好像说过」这种模糊话
2. 一场 30 轮下来**不重复问同一个问题**
3. 你第 8 轮说了「QPS 5 万」，第 20 轮它会拿这个数字压你
4. 关掉浏览器再打开，**它知道你面到哪了**
5. 它**没把你的话记错**

### 4.2 三层记忆（核心设计）

```
L1 原话层   最近 3~4 轮，逐字保留
            └ 支撑「你刚才说 XX，那 YY 呢」这种精确追问
            为什么只留最近几轮：全留会爆上下文，且越早的越不重要

L2 事件层   整场的结构化事实（全程保留）
            ├ 已问题目清单（防重复，硬需求）
            ├ 每个考点的状态：没问 / 问了没答上 / 答上了 / 追问就崩
            ├ 可疑点（面试官标的，带轮次）
            └ 硬事实（你说过的数字、技术名、项目细节）
            为什么必须结构化：30 轮后模型读不了 30 轮原文，但它读得下 30 行事实

L3 摘要层   早期内容的压缩叙述（每超一次预算压一次）
            └ 支撑「前半场聊了什么」的全局感
            注意：压缩有损，所以 L2 是保底，不能只靠摘要
```

**关键决策：什么该记，什么该丢**

| 记 | 丢 |
|---|---|
| 具体事实（数字、技术名、你的判断） | 寒暄、客套 |
| 答崩的那一题（原话 + 追问到第几层崩的） | 重复表述 |
| 面试官标可疑的地方 | 语气词、「嗯」「那个」 |
| 你自己说过的量化成果 | 与考点无关的闲聊 |

### 4.3 每个角色拿到的切片不一样

| 角色 | 拿到什么 |
|---|---|
| 面试官 | L1 + L2 +（L3 按预算给） |
| 打分员 | 只有这一题的问答 + 评分标准，**连 L1 都不给** |
| 教练 | 不给会话记忆，只拿长期画像 |

这就是「上下文隔离」落到记忆上的具体形态。

### 4.4 三个会出错的地方

**① 记错。** 它把「你用了 channel」记成「你用了 mutex」，后面所有追问都建在错的上面。
→ 对策：**每条记忆带来源**（第几轮、原话片段），随时可回查。这和「报告可溯源」是同一个思想。

**② 摘要丢细节。** 压得太狠，追问时说「你刚才那个方案」，但记不清是什么方案。
→ 对策：L2 保底结构不能省；L1 永远保最近几轮原文；压缩只压 L3。

**③ 膨胀。** 40 轮的面试，记忆越滚越大，最后又变回「全塞」。
→ 对策：**按 token 预算触发压缩，不按轮数**。预算到了才压，没到就留着原文。

### 4.5 会话结束时的交接

会话记忆是临时的，它必须变成长期记忆：

```
L2 事件层 ──提炼──> 本场暴露的弱点 ──归并──> 长期画像（去重、计数、改善标记）
                                          └─> 复习排期（Redis ZSET）
```

**这个交接是整个系统最关键的一道桥。** 桥做不好，长期画像就是垃圾——你会攒下几百条互相重复的弱点，然后没人再看得懂它。
→ 归并要用 agent 判断（见第五节 ③），不能用文字匹配糊。

## 五、Agent 技术点 → 落点

### 真亮点（做了能讲深，别人做得差）

**① 上下文隔离：三个角色看三份不同的材料**

| 角色 | 看什么 | 明确不看什么 |
|---|---|---|
| 面试官 | 简历某一段 + L1 原话 + L2 可疑点 | **不看评分标准**（看了会忍不住提示答案） |
| 打分员 | 这一题的问答 + 评分标准 | **不看前面几题**（看了会心软，第 5 题下不去手） |
| 教练 | 全部历史 + 复习队列 | 不需要实时 |

一句话：**多 agent 的价值不在角色多，在于每个角色看到的东西少而准。**

**② 工具化：把「问什么」变成「查什么」**

- `查简历段`：简历 3000 字，20 轮全塞 = 6 万 token；按需取一段约 300 字
- `查面经追问链`：决定往下压时，去自己的面经里找这个考点的追问路线
- `查上次弱点`：同一考点第二次练时才查

面试话术：塞太满模型会抓不住重点。**会主动去取材料，才配叫 agent。**

**③ 弱点归并（最像「记忆系统」的一块，也是最难）**

新弱点进来，要判断：
- 和已有某条是同一个毛病 → 计数加一，保留原复习进度
- 是新的 → 加进来
- 是老毛病但已好转 → 标记改善，不是又加一条

TechSpar 用子串匹配糊过去（`"GMP" in "GMP 理解不深"`），错得很难看。用 agent 判断能直接对上这个软肋，也是「真用两年档案不膨胀」的底气。

### 配套亮点

- **弱点当场抓，不是事后统计**：答得虚，下一句就往这里压，连压三层
- **崩在第几层 = 掌握程度**：是什么 → 为什么 → 边界/代价，崩在第几层对应「没学过 / 背过 / 懂一半」
- **弱点更新与报告生成并行**：结束立刻出报告，画像和复习排期后台慢慢更
- **打分的可靠性可验证**：自洽率（同题三次分差 ≤1 的比例）+ 人工对齐（自标 10 题对上几题）。市面上没人给这两个数

## 六、两类设计要自己分得清

**A 类：需求逼出来的**（不做系统就变差）
三份材料隔离、工具化、异步打分、每跳独立超时、语音并发流水线、context 链

**B 类：为了练手加的**（系统不一定更好，但想练）
MySQL 双实现、gin、pprof、额外端点、**整个 Redis**

面试时直接把界线说出来，比假装每个设计都必需强十倍：

> 这个项目里有两类设计。一类是需求逼出来的，一类是我为了练 Go 和 Redis 加的。我分得清哪些是必要的，哪些是我想练的。

## 七、优先级

```
① 语音流水线 → ② 异步打分 → ③ 工具化 → ④ 弱点归并 → ⑤ 事件总线
```

- 前半段是 Go（并发 + 不卡死），后半段是 agent（隔离 + 工具 + 记忆）
- **东西要下沉到地基**：context 从 ① 就要贯穿；interface 在 ② 之前立；sync 在 ② 撞上；错误分类在 ② 就要分
- **Redis 从 ② 开始挂**：任务身份证（②里就能用）、会话现场（②之后）、复习队列（④之后）、工具缓存（③之后）
- **会话记忆三层在 ④ 之前必须成型**，否则弱点归并拿不到干净的输入
- 存储层、gin、可观测性都是加菜，前面跑顺了再说

## 八、随手记

- 技术是被需求逼出来的，不是反过来。这个项目恰好真被逼到了三处：三个角色要看不同材料（所以要拆）、面试官要临时取材料（所以要有工具）、语音链路要同时跑（所以要有并发）。
- 「全语音」不是亮点，是形态前提；真正的亮点在逻辑可量化、崩在几层、可靠性可验证。
- 用户明确要求把 Redis 也做进去 → 落地位置见第二节，定位为 B 类（练手 + 真实收益混合）。
- 地基四样（context/interface/sync/错误分类）比 Go 学习清单里那几项更必需，因为它们是「做对了没人看见、做错了全都崩」。
- 会话记忆的关键不是「存得多」，是**分层**：原话保最近几轮、事件层全程结构化、摘要层按预算压。以及**会话记忆→长期记忆的归并桥**，那是整个系统最容易烂的地方。
