# 02 · 上下文装配与预算

模块：`context_assembler.go`、`agent.go`（装配与护栏部分）、`main.go`（预算传递）。
一句话：**这个模块的所有坑都是 R1（来源一致）的实例**——预算、口径、配额、账本，同一个事实只能有一个来源。

---

### K-01 单一事实来源（四个真实实例）

| 事实 | 唯一来源 | 反例代价 |
|---|---|---|
| 单次回复上限 | `m.maxTokens`，`req.Budget.MaxTokens` 从它推（`agent.go:146-148`） | 两边各写 2048，改一处漏一处，输出预留漂掉 |
| 工具说明书 | 只生成一次（`agent.go:152-154`），同时是「要发的」和「要记账的」 | 估一套发一套，账本与实际不符 |
| 工具结果配额 | `budget.ToolResultReserve`，`NewResultStore` 第三参也传它（`main.go:71-74`） | 召回页不受同一闸门约束，一次 `read_result` 就能撑爆窗口 |
| 估算口径 | `estimateTextTokens` 的 `len(s)/3 + 1`（`context_assembler.go:63-74`），必须与 `context.go` 的 `estimateTokens` 一致 | 两套口径 → 超限报错互相矛盾 |

- **面试**：为什么注释反复强调「全项目只有一套」？如果两处各写一个 2048 会怎么坏？【高频变形原题】
- **表达方式**：不是「代码要整齐」，而是「同一个事实有两个来源 = 迟早有一次只改了一边」。

### K-02 clamp 之后才入账

`context_assembler.go:231-239`：`msgBudget` 先 clamp 到 0，再写进 `Report.MessageBudget`。

- **原理**：`agent.go` 的工具循环护栏是拿 `historyTokensOf(messages)` 和 `MessageBudget` 比。记 clamp 前的负数，护栏会在第一轮就误报（或永远不响），**护栏等于没有**。
- **面试**：记账为什么要放在修正之后？【实现层追问】

### K-03 护栏必须默认可见（三个设计点全在 `agent.go:174-195`）

1. **比 `MessageBudget`，不是比 `Available`**——拿段比池子，得等 messages 把 tools/system 的份额也吃掉才响，护栏形同虚设。
2. **第 1 轮不比**——那时 messages 就是装配结果，必然不超；真有增量信息的只有第 2 轮起的 tool_result。
3. **告警默认打 stderr**，不能只塞进 `res.Context.Warnings`——没开 `TINY_AGENT_DEBUG_CONTEXT` 就完全静默，护栏静默等于不存在。

- **面试**：护栏和告警的区别是什么？为什么「只记在报告里」等于没做？【实现层追问】

### K-04 宁超不切半轮 + 头部裁剪 = 缓存前缀失效

- `TrimHistory` 的底线（`context_assembler.go:250-253`）：宁可超预算，也不把一轮 tool_use 和它的 tool_result 拆开——拆开的半轮会让 API 直接报错，比超预算严重得多。
- 从头部删消息（`context_assembler.go:254-261`）：**删除位置 = 缓存前缀失效位置**。prompt cache 匹配的是字节流开头，头部一删，后面全部前移，messages 段缓存需重建。
- 这条告警是「缓存省了多少」的唯一线索，也是将来做**滞后裁剪**（超到 110% 才裁回 90%，用可控超额换裁剪频率下降）的观测依据。
- **面试**：滑动窗口怎么裁？为什么从头部裁会伤缓存？【高频变形原题 + 加分拓展】

### K-05 预算兜底只兜「全零」

`agent.go:141-145`：只对 `Budget{}` 全零结构体填默认值。

- **原理**：半给（比如只填了 `Window`）是调用方 bug；兜底会把它悄悄变成一个合法配置，症状表现为「工具循环静默不执行」这类灵异现象，排查代价极高。
- **面试**：什么时候该兜底、什么时候该暴露？【实现层追问】——原则：**兜底只兜「没给」，不兜「给错」**。

### K-06 外置量必须记账（真实踩过的盲区）

- 类型与理由：`context_assembler.go:109-135`。注释写得很直接：09-26 实测「账本实占 282 token，实际丢掉了 20649 token，没有任何数字记录，事后答不出到底丢了多少」。
- 记账点：`agent.go:276` 的 `res.Context.addExternalized`。
- 账本要同时回答两个问题：**这轮发出去多少**（`TotalUsed`）、**多少内容被移出窗口**（`Externalized`）。后者是「无损转移」而非「损失」，但只有记下来才能证明。
- **面试**：外置之后还算「无损」吗？怎么证明？【实现层追问】

### K-07 估算回弹：省略号、标记自身也要占额度

估算口径是 `len/3+1`，而截断/外置会**追加标记文本**，于是出现「削完仍超配额」——账本与闸门不同源。三处修正：

- `context_assembler.go:317-324`（fitMemory）：省略号「…」3 字节可能让估算回弹，保守记 `used = maxTokens`。
- `context_assembler.go:379-386`（truncateToolResult）：正文额度 = 配额 − 标记 − **2**。
- `context_assembler.go:397-399`（外置）：正文额度 = 配额 − 标记 − 省略提示 − **8**。

- **面试**：为什么预留 2 和 8？【实现层追问】——答案不是玄学，是「追加的字节也要计入同一口径」。

### K-08 不复用调用方的切片底层数组

`context_assembler.go:287-291`：`make` 新切片再 append，注释写明理由——直接 `append(history, ...)` 会写进共享数组的容量区，与调用方持有的旧切片形成**别名**，这类 bug 调试时极难发现。

- **面试**：Go 切片别名 bug 长什么样？什么情况下 append 会改到别人的数据？【实现层追问】

### K-09 O(n²) 全量重算 token：当前是「简单换正确」的取舍

`context_assembler.go:89-99`：`historyTokensOf` 在工具循环里每轮全量重算，n 是几十条时无所谓；messages 上千条时应改成增量记账。

- **面试**：你知道这里是 O(n²) 吗？为什么不现在优化？【加分拓展】——要点是「知道代价、知道触发条件」，而不是「没意识到」。
