# 04 · 模拟面试官 · 两层信号协议（实时决策 / 事后评分）

模块：`internal/interview/signal.go`（内联轻信号）+ `internal/interview/score.go`（事后重信号）
一句话：**面试进行中只需要一个布尔——要不要换话题；分数全部事后算，算完压着不出。**

> 编号说明：面试官项目独立编号（D- 取舍决策 / K- 已踩坑 / P- 潜在坑）。
> 分档图例沿用 README：`【高频变形原题】/【实现层追问】/【加分拓展】`。

### D-01 实时决策与事后评分分层 ⭐核心取舍

**决策**：把「面试中的即时决策」和「面试后的评价打分」拆成**两套协议、两个时机**，不再塞进同一个 EVAL 块。

| | 面试进行中 `TurnSignal` | 面试结束后 `QuestionScore` |
|---|---|---|
| 信息量 | 一个布尔：要不要换话题 | 分数 + 四维 + 证据引用 + 弱点 |
| 时效 | 下一秒就要用 | 不急 |
| 准度要求 | 不需要准，能跑就行 | 必须准 |
| 失败代价 | 默认「继续追问」，零副作用 | 重试 → 标「未评分」 |

**收益**：主链路延迟不被评分拖累；评分可以拿到干净的上下文（只看单题问答），也可以换成更强的模型、多跑几次。

**代价**（自己先说）：状态要在两处维护（面试中的推进记录 vs 事后的评分记录），得保证它们能对上——报告里"面试官当时一直追问"和"事后给这题 8 分"可能打架，需要能解释。

**原理**：延迟敏感的需求和准确敏感的需求，不该在同一层。塞在一起，两边都做不到极致。

【高频变形原题】面试怎么问：「为什么不在每轮里直接打分？」→ 答：「拆了。实时决策和事后评分对时效、准度的要求相反，放一层就互相拖累。」

### D-02 计算时机 ≠ 呈现时机（这条最容易被面试官记住）

**决策**：用户在答题时，后台已经在算刚结束那一题的分数；但分数**压着不显示**，面试结束才一起出。

```
你答完第1题
 ├─ 面试官立刻出第2题             ← 用户 0 秒等待
 └─ 打分 agent 后台开始想第1题     ← 随便它想多久，没人等

你答完第2题
 ├─ 面试官出第3题
 └─ 打分想第2题；第1题的分早已入库

面试结束
 └─ 报告刷出来（分都算好了，不用现等）
```

**为什么**：如果真等结束才开算，10 题 × 每题 30 秒 = 用户干等 5 分钟。压着不出分是为了体验，不是为了省算力——**算力要提前花掉，结果要压着不透。**

**代价**：并发复杂度上升（打分任务与对话并行跑）；面试很短（3 题）时最后一题可能还没算完，需要「报告生成中」占位 + 轮询兜底。

【加分拓展】话术：「我把评分的『计算时机』和『呈现时机』拆开了——算得越早越好，看得越晚越好。」

### D-03 内联信号用词标记，不用 JSON

**决策**：`TurnSignal` 只传一个布尔，用固定词标记表达（如 `[换话题]`），**不构造 JSON**。

**原理**：格式复杂度应当与信息量匹配。一个布尔值用 JSON 承载，会凭空引入一整条失败链——JSON 转义、括号配对、尾逗号、被截断——每一条都要写代码兜底。用词标记，解析退化成一次 `strings.Contains`。

**收益**：解析代码从几十行降到几行；失败模式从「JSON 坏了」变成「没找到词」，而后者有天然默认值（继续追问）。

**代价**：词标记可能被模型写在正文中间，必须从展示给用户的文本里剪掉；标记词本身要选不可能自然出现的形态（方括号 + 汉字是关键）。

【实现层追问】面试怎么问：「为什么这里不用 JSON？」→ 答：「信息量只有一个布尔，用 JSON 是拿一整条解析链去换一个 bit，不划算。格式复杂度要和信息量匹配。」

### D-04 事后打分的「多思考」= 先取证 + 3 次采样取中位数

**决策**：`QuestionScore` 的每次打分都必须**先引用用户原话当证据，再对照 rubric 给分**；同一答案跑 3 次，取中位数。

| 做法 | 收益 | 成本 |
|---|---|---|
| ① 先取证后给分 ⭐ | 显著压低幻觉式扣分，报告能直接引用用户原话 | 几乎零（多写几十字） |
| ② 3 次采样取中位数 ⭐ | 单次打分的 ±2 分漂移基本消失 | token ×3，可并行 |
| ③ 四维各打一次 | 维度间污染小 | ×4，且失去整体印象 |

**推荐 ①+②**：10 题 × 3 次 = 30 次调用，5 路并行约 1–2 分钟，token 约 6 万。这段时间面试还在进行，是白捡的。

**不做 ③**：四维分开会让「技术好但表达差」这种整体判断消失，而真正要回答的是「这人行不行」。

**必须同时定的东西——rubric**：没有评分标准，模型就是在凭感觉打 7 分。rubric 不凭空编，从 `学习指南/agent面经.md` 里已有的 `must_points + 追问链 + 分档` 长出来。

**验收（不做就等于没准）**：
- 自洽率：同一回答 3 次打分，最大分差 ≤1 的比例，目标 ≥90%
- 人工对齐：自己先标 10 题，模型分与人工分差 ≤1 的题数，目标 ≥7/10

【高频变形原题】面试怎么问：「你凭什么说打分是准的？」→ 拿这两个数答，不要说「模型挺好使的」。

### D-05 打分失败记「未评分」，绝不填 0

**决策**：打分 agent 超时、报错、解析失败时，该题分数写 `NULL` / 明确标记「未评分 + 原因」，**不允许写 0 分**。

**原理**：0 分是有效数据，会进入弱点统计和 SM-2 排期。把失败伪装成 0 分，等于往数据库里注入一条假事实，一个月后分不清哪道是真 0 分、哪道是系统挂了。**静默失败是最大敌人（tiny-agent 的 R3 规律）。**

**连带要求**：报告里「未评分」的题要显式列出，并给重跑入口。

【实现层追问】面试怎么问：「打分服务挂了会怎样？」→ 答：「面试照常结束，报告里那题标未评分并说明原因，可以被重跑。我不会用默认值把它填平。」
