# 项目踩坑记录（tiny-agent）

一句话：这里只记两类东西——**面试会追问的取舍**，和**做项目该提前知道的坑**。按模块一个文件，复盘时按索引找。

## 记录约定

- **时机**：每次讨论项目问题时顺手补，不攒到最后。
- **粒度**：只记「有取舍、有代价、面试会追」的，和「不写会错、且错了难查」的细节。
  操作步骤、环境配置类坑不记（按既定约定，这类不算面试素材）。
- **前缀**：
  - `K-` 已踩的坑（代码里已有对应的修复或注释作证据）
  - `P-` 潜在坑（还没踩，但要提前防）
  - `D-` 取舍决策（不是坑，是「为什么这么选」，面试最常问的就是这类）
- **每条固定字段**：现象/证据（`文件:行`）→ 原理 → 面试怎么问 → 分档。

## 三条根规律

> 单个坑记多了会忘，规律不会。下面每个 K/P 基本都是这三条的实例。面试问「你从项目里学到什么」，答这三条比答十个坑有用。

**R1 来源一致**：同一个事实只能有一个来源，改一处不能漏另一处。
实例：`maxTokens`（`m.maxTokens` vs `Budget.MaxTokens`）、工具说明书（要发的那份 vs 要记账的那份）、`toolResultQuota`（配额来自 `ToolResultReserve` 而非另设）、估算口径（全项目一套 `len/3+1`）。

**R2 语义一致**：同一个概念跨模块、跨层必须同名同义。
实例：`History`（装配器的 history **不含**本轮输入，`messages` 含）、span 名一处定义、账本段名与人读文案分离、span `status` 是 `codes.Error/Unset` 枚举而不是字符串。

**R3 静默失败是最大敌人**：截断、降级、护栏、裁剪、外置失败都必须留痕，而且**默认可见**。
实例：外置 warning 既进 `Report.Warnings` 又打 stderr；落盘失败在标记里写明「完整内容已丢失」；工具循环超预算的 warning 默认可见，不等 `TINY_AGENT_DEBUG_CONTEXT`。

## 使用建议

复习时只做一件事：**把「面试怎么问」那一行盖住，自己先答一遍**。答得出的划掉，答不出的标记——面试只讲得出 3～5 个，其余是后台知识。
