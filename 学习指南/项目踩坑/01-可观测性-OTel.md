# 01 · 可观测性（OTel）

状态：**方案已验证过一轮（曾完整跑通后回滚），截至当前代码里未落地**。落地规划见文末 D 组取舍。

## D-00 先定分工：trace / metric / log 各管什么

- **trace**：单次请求的因果链 → 回答「这一轮为什么慢、慢在哪一段」。
- **metric**：趋势与告警 → 回答「最近有没有变差、水位是不是逼近上限」。
- **log**：细节与上下文 → 回答「具体那条错误、那句话是什么」。

判据：需要把多个步骤**串起来看因果**用 trace；需要看**分布/趋势/告警**用 metric；需要看**具体内容**用 log。三者不互相替代。
本项目的现实动机：`>>> [1] 模型返回 (7.5s)` 这类日志只给出「点」，拼不出「这一轮 22.75s 里，模型 22.74s、装配 0ms、工具 11.7ms」这种归因。

## P 组：潜在坑（还没踩，落地前必须先防）

### P-01 ctx 不往下传 = 断链
- **现象**：父 span 下没有子 span；或子 span 变成另一条独立 trace。
- **证据/修法**：`askCtx, turnSpan := tracer().Start(askCtx, spanTurn)` 返回的**新 ctx** 必须一路传进 `SendMessage` → `callModel` → 工具循环。
- **原理**：父子关系靠 ctx 里的 `SpanContext`，不靠「代码看起来嵌套」。
- **面试**：`Start` 为什么返回新 ctx，而不是在原 ctx 上改？【实现层追问】

### P-02 defer End 放进 for 循环
- **现象**：第 1 轮的 span 耗时 = 后面所有轮次之和，耗时全错。
- **修法**：循环体内显式 `End()`。
- **原理**：`defer` 的作用域是**函数**，不是迭代。`main.go` 的 REPL 和 `agent.go` 的工具循环都是 `for`，两处都踩得到。
- **面试**：span 什么时候才算「结束」？为什么不能靠 defer？【实现层追问】

### P-03 提前 return / continue 前不 End
- **现象**：后端里「工具调用莫名少了几条」，但日志显示执行过。
- **修法**：每个错误分支先 `End()` 再 `continue`/`return`（`agent.go` 工具报错分支、`callModel` 报错分支）。
- **原理**：span 只有 `End()` 之后才会进导出队列；泄漏的 span 永远不会出现，也不报错。
- **面试**：span 泄漏会有什么表现？怎么发现？【实现层追问】

### P-04 Batch 不 Shutdown 就丢最后一批
- **现象**：最后一条 trace（往往是最想排查的那条）在 Jaeger 里没有。
- **修法**：`main` 里 `defer shutdown(5s 独立 ctx)`。
- **原理**：`BatchSpanProcessor` 默认 5s / 512 条才落一次；进程退出时队列还没发。
- **代价**：换 `SimpleSpanProcessor` 不丢，但每次 `End()` 同步导一次网络往返，直接拖慢工具循环。
- **面试**：Batch 与 Simple 怎么选？为什么必须 Shutdown？【高频变形原题 + 实现层追问】

### P-05 属性 key 用中文或动态段名
- **现象**：代码明明 `SetAttributes` 了，后端一条都查不到。
- **证据**：`AssembleReport.Sections[].Name` 的实际值是 `"system(记忆)"`。
- **修法**：`sectionKey()` 映射成 `system_memory` 这类 ASCII key。
- **原理**：属性 key 有字符集约束，**部分后端是静默丢弃而不是报错**——这是「设了但查不到」最典型的成因。
- **面试**：为什么人读的字符串不能直接当 key？【加分拓展】

### P-06 semconv 未定版却把属性名写成散落的字面量
- **现象**：semconv 改名那天，全项目搜索替换，漏一处就是一条永远查不到的属性。
- **修法**：属性 key 集中成一张常量表，改名只改一处。
- **事实**：GenAI 语义约定已从主仓库拆到 `open-telemetry/semantic-conventions-genai`，状态仍是 experimental。
- **面试**：标准在变，你为什么还敢用？【加分拓展】——答案就是「集中隔离 + 只用在语义真对得上的地方」。

### P-07 头部采样会系统性丢失败样本
- **现象**：trace 里几乎看不到失败请求，但用户天天报错。
- **原理**：`ParentBased(TraceIDRatioBased)` 在请求**开始时**掷骰子；而失败请求往往更慢更长，采样决策早已在它失败之前做完了。
- **对策**：本地全采（1.0）；生产在 Collector 做**尾采样**（先全收，再按 status/耗时决定保留）。
- **面试**：采样怎么做？为什么头部采样不适合 agent？【高频变形原题】

### P-08 可观测性组件自己刷屏
- **现象**：后端没起时，每 5 秒一条 `connection refused`，REPL 被淹没，用户索性关掉 trace。
- **修法**：`otel.SetErrorHandler` + `sync.Once`，只提示首次。
- **原理**：可观测性组件不能成为噪音源——它一旦制造噪音，最先被关掉的就是它自己。
- **面试**：可观测性失效时应该怎么表现？【加分拓展】

### P-09 把 prompt / 工具结果全文塞进属性
- **现象**：后端存储暴涨（高基数 + 超大 value），用户内容进了日志系统。
- **修法**：只记长度、token 数、是否截断、外置句柄；全文在 `resultstore` 里按 handle 反查。
- **官方依据**：semconv 对 prompt/completion 内容本身是 **opt-in**，默认不采（文档原话大意：「这个属性可能很大，不推荐默认填充」）。所以这不是洁癖，是标准做法。
- **面试**：trace 里为什么不放 prompt？【高频变形原题】（三个理由：隐私、基数、后端存不下）

### P-10 估算口径与真实 usage 对不上（验收判据）
- **现象**：账本说装了 500 token，API 返回 712，之后所有预算推理都不可信。
- **做法**：把三组数当验收判据对账——`context.section.*.used` 之和、`context.used`、`gen_ai.usage.input_tokens`。方案验证时实测 **531 = 531**，第二轮 712 也能由 531+36+工具结果精确推出。
- **价值**：这是「估算口径可信」的唯一证据，也是发现「多算/少算」的唯一手段。
- **面试**：你怎么证明自己的 token 估算是对的？【实现层追问】

## D 组：取舍

### D-01 span 树怎么切（全方案最关键，没有标准答案）

```
trace: agent.turn                ← 一轮用户输入（root）
├─ context.assemble              ← 装配 + 账本全套属性
├─ gen_ai.chat (round=1)         ← 模型调用，带 token 用量
├─ execute_tool                  ← 工具执行，带外置句柄
└─ gen_ai.chat (round=2)
```

- **`gen_ai.chat` 开在工具循环内部，不是 `SendMessage` 外面**。一次用户输入可能调好几次模型，合成一个 span 就丢了「第几轮开始变慢」的定位能力。实测里第 1 轮 7.5s、第 2 轮 15.3s，这个结论只能从逐轮 span 读出来，纯日志看不出来。
- **不按会话切 trace**：会话可能几十分钟几十轮，trace 太长没法看；会话级关联走 `session.id` 属性。
- **`execute_tool` 不用改工具签名**：`Tool.execute` 是反射调用任意 0/1 参函数，工具本身拿不到 ctx，加参数只得到一个用不上的形参；span 在**调用点**开就够了。等真有工具要发 HTTP，再让 `execute` 支持 ctx 首参——那时才有收益。（这条曾经判断错，已纠正）
- 【实现层追问】

### D-02 账本单开 `context.assemble`，而不是挂到当前 span
挂到父 span 上你只能看到总数；单开才能证明「装配自己的耗时是 0ms」——可归因性来自切分，不来自属性数量。

### D-03 属性 vs event 的分界
- **固定 key 的事实 → 属性**：窗口、各段 used/budget、水位、token 用量。
- **条数不定、追加式的事实 → event**：装配 warning、外置明细。
理由：属性 key 必须固定，event 天生是「带时间点的追加事实」，且不参与索引基数。

### D-04 标准前缀 vs 自研前缀
- `gen_ai.*` 只放语义真对得上的（model、token、operation name）；
- 本项目独有的放 `context.*` / `agent.round` / `tool.result.*`；
- **绝不把自己发明的字段塞进 `gen_ai.` 前缀**：将来定版可能撞名，且后端按前缀归类会把私有字段当官方字段去算。
- 补漏：semconv 要求的 `gen_ai.operation.name`（`chat` / `execute_tool`）方案里漏了，落地要补。
- 【加分拓展】

### D-05 span 名故意偏离建议格式
semconv 建议 span 名写成 `{operation} {model}`（如 `chat claude-sonnet-4`）。本项目用 `gen_ai.chat` + `gen_ai.request.model` 属性，理由是 **span 名带 model 会让名字基数列暴涨**，Jaeger 里按 span 名聚合会裂成多组。
关键不是偏不偏离，而是**偏离时有理由、留了注释**——「有意识地不符合约定」和「不知道有约定」是两回事。

### D-06 可观测性不能做成并列模块
判据：**删掉它业务一行不用改 → 横切关注点**（跟 stderr 日志一样）；删掉它调用顺序要重排 → 纵向模块（记忆、装配器、外置仓库）。
硬做成 `obs.go`，它只能拿到 `SendMessage` 的入参与返回值，永远拆不出「8.2s 里模型 7.1s」。所以产物是 `telemetry.go`（基建 + 语义常量），真正干活的埋点长在 `main.go` / `agent.go`。
【加分拓展】

### D-07 初始化失败降级 ≠ 构造期失败退出
- `ResultStore` 构造失败 → `os.Exit(1)`：涉及磁盘布局/权限，早失败比跑到一半写不进去好。
- `InitTelemetry` 失败 → 只打一行 stderr，继续跑：没有 trace 只是「瞎」，业务功能完整。
- 分界线：**不可用 vs 可用但不可观测**。
